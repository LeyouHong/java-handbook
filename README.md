### MySQL

十篇，按三层组织。层内顺着读，层间跳着读；凡出现 **⤵ 依据** 的地方都指向更底层的那一篇，所以任何一条规范都能追到根。

**① 引擎内部** —— 数据怎么存、事务和锁怎么工作、内存怎么用

| 笔记 | 层次 | 内容 |
|---|---|---|
| [B+ 树原理](mysql/B+树原理.md) | **存储结构** | 为什么不用哈希/红黑树/B 树、用具体数据把树完整拆开（上下层 key 如何对应、叶子页里一行怎么存）、3 层为什么能装 2190 万行、页内 Page Directory 二分、页分裂与自增主键、聚簇索引 vs 二级索引、**联合索引专章**（元组排序、六条 SQL 的树上走位、IN 不截断、ORDER BY 免 filesort、列序三步法、几列才合适与定位列 vs 携带列）、深分页为什么慢 |
| [事务与 MVCC](mysql/事务与MVCC.md) | **事务** | 整个数据库专题的**地基**，从零推导。两个人同时读写同一行 → 全加锁则读也要排队 → 但**读的人要的是「一致」不是「最新」** → 那就改数据时别扔旧值，读的人读旧值 —— **MVCC 的全部动机**；由此逼出三个零件（`trx_id` / `roll_ptr` / undo log）；核心难点「该读哪个版本」先用**脏读反例打掉「读比我编号小的」这个朴素想法**（编号只说明谁先开始，不说明谁先结束），再引出「事务开始时拍一份**谁还没提交的名单**」—— 规则只有一句话，`min/max` 两个数字只是加速手段不是规则；**RC 和 RR 的唯一区别就是名单每次重拍还是只拍一次**，「不可重复读」只是前者的必然结果；写为什么不能读快照（丢失更新）→ 当前读；幻读 vs 不可重复读（行数变了 vs 值变了）与间隙锁；长事务四害全部归因于**旧版本扔不掉**；ACID 放在最后当总结 |
| [InnoDB 锁](mysql/InnoDB锁.md) | **并发** | 行锁不是加在「行」上，是加在**索引记录**上；意向锁为什么存在；三形态（记录锁/间隙锁/临键锁）用数轴画清边界，RR 默认临键锁前开后闭而 RC 没有间隙锁；加锁四规则与**唯一索引等值未命中反而退化成间隙锁**（查一个不存在的行也会挡住别人插入）；二级索引查询会同时锁两棵树——"无关 SQL 互相阻塞"的真因；两类死锁（顺序相反 / 间隙锁互相兼容却与插入意向锁冲突）；死锁日志的阅读顺序、`performance_schema.data_locks` 自测法、MDL 锁导致整表不可用 |
| [InnoDB 的内存](mysql/BufferPool与内存.md) | **内存** | 改良 LRU 的 young/old 分区 + 1 秒规则如何防全表扫描污染缓存；脏页刷盘四时机，redo 写满触发的强制刷 = "数据库莫名卡一下"；`innodb_io_capacity` 默认 200 是机械盘水平；doublewrite 为什么要写两遍；**change buffer 完整定义**与唯一索引为什么用不了（判重必须读页）；`innodb_flush_log_at_trx_commit` 与"双 1"；**全局内存 vs 连接级内存**——`sort_buffer` 16M × 500 连接 = 8G OOM |

**③ 扩展与数据流** —— 单机撑不住之后

| 笔记 | 层次 | 内容 |
|---|---|---|
| [分区表与分库分表](mysql/分区表与分库分表.md) | **拆分** | 从一张订单表 10 万行长到 10 亿行，看每种手段是被哪个痛点逼出来的。先纠正一个误解：**数据涨 100 倍，单行查询只慢一点点**——真正先出问题的是「删不动/改不动/备份久」和「机器到顶」这两类完全不同的问题；删 1000 万行要 4 小时 → **这才引出分区表**（`DROP PARTITION` 一秒，代价是查询不带切分字段时反而更慢、主键必须包含切分字段、唯一性因此被削弱）；分区表救不了磁盘/CPU/连接数——**它只是把一个房间分成几个柜子** → 这才引出分库分表；拆只有两个方向（竖着按列 / 横着按行），**先竖着切往往就够了**（行宽 1.5KB→200B，容量涨 7 倍）；横着切才引出分片键（按什么切、怎么知道去哪张表、不带分片键怎么办、为什么取 2 的幂、全局 ID 的鸡生蛋问题）；分片后失去的五样东西；**十一步决策路径**（能在哪步停就在哪步停）|
| [binlog](mysql/binlog.md) | **数据流** | binlog 把「数据库状态」变成「可订阅的变更流」；先分清 **redo log（怎么改的，只有 InnoDB 看得懂）vs binlog（改成了什么，谁都能消费）** 与两阶段提交；三种格式（`SYSDATE()` 不安全而 `NOW()` 安全、`DELETE ... LIMIT 1` 主从分叉、为什么 CDC 只认 ROW、`binlog_row_image` 别设 MINIMAL、**DDL 永远是 STATEMENT**）；`sync_binlog` 与组提交；**八个用途分两族**——MySQL 自用（复制 / PITR / **误删闪回**）与外部订阅（异构同步 / **缓存一致性**：binlog 是"事务已提交"的凭据 / **替掉分库分表迁移的双写** / 解耦 / 审计）；Canal 伪装成从库的原理 |
| [主从复制与高可用](mysql/主从复制与高可用.md) | **复制** | 复制的能力和毛病都源于「日志要传过去、再重放一遍」。三线程分工（瓶颈几乎总在从库 SQL 线程）；异步/半同步/MGR 的区别只在「提交时等不等从库」，半同步超时会**静默退化成异步**；**`Seconds_Behind_Master` 不可靠**（IO 线程卡住时它显示 0），改用心跳表；六大延迟成因里**表没有主键最隐蔽**——ROW 格式下从库重放每行都全表扫描；并行复制 5.6 按库 → 5.7 组提交 → 8.0 WRITESET；**读写分离「写完读不到」的五种解法**；GTID 为什么让切换变简单、`super_read_only` 为什么必须开；脑裂与 STONITH |

### 存储与检索

三篇讲三种「怎么找得快」，也是三种不同的取舍：**B+ 树牺牲写换精确**（在 MySQL 板块）、**LSM 牺牲读换顺序写**、**向量索引牺牲精确换高维下的速度**。

| 笔记 | 内容 |
|---|---|
| [LSM Tree 原理：从零造一个 KV 存储](storage/LSM树原理.md) | 不讲理论，从最笨的「只往文件末尾追加」开始，十步推导出完整的 LSM：稀疏索引 → SSTable → MemTable（含跳表原理插曲）→ WAL → Compaction → 分层 → 布隆过滤器（含原理插曲：位数组/多哈希/假阳性/为何不能删除）→ 墓碑，每一步都被上一步的问题逼出来，最后对应到 RocksDB 的实际名词和参数；末章补上层 SQL 如何落到 KV（表的保序编码、六条 SQL 逐条走位、哪些 SQL 在 LSM 上特别贵）|
| [pgvector 与向量检索](storage/pgvector与向量检索.md) | 三类索引里**唯一放弃「精确」的那一类**。为什么 B+ 树在高维彻底失效（没有全序 → 不能二分；维度诅咒下所有点距离趋同，精确 KNN 无法优于全扫）→ 只能退让到 ANN，于是多出一个传统数据库没有的指标：**召回率**；四种距离运算符与「用错不报错、只是结果不相干」；**IVFFlat（先聚类再搜几个簇）vs HNSW（跳表思想的高维推广）** 的原理、参数与选型；**过滤 + 向量的候选丢失坑**（结果条数莫名变少）与四种解法（迭代扫描/部分索引/分区/加大候选）；RAG 落地（切块权衡、向量+全文的 RRF 融合、两段式重排）；pgvector 与专用向量库的分界（**最大价值是少一个组件**：同事务、可 JOIN）；运维（1536 维 ≈ 6KB/行必被 TOAST、halfvec 减半、索引放不进内存会崩塌、建索引 2000 维上限）|
