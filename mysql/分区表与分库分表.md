# 分区表与分库分表：一张订单表的十年

> 环境：MySQL 8.0 / InnoDB。本篇 SQL 为**示例**，未附实测输出。
>
> 这篇不先讲概念，也不先做对比。我们从一张**普通的订单表**开始，让它慢慢变大，
> 看它每一步会痛在哪，再看每种手段是被哪个痛点逼出来的。
>
> 读完你应该能回答三个问题：**我的表该不该拆、该用哪种拆法、第一步做什么。**

---

## 我们的表

```sql
CREATE TABLE `order` (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL           COMMENT '下单用户',
  order_no   VARCHAR(32)     NOT NULL           COMMENT '订单号',
  amount     BIGINT          NOT NULL DEFAULT 0 COMMENT '金额，单位分',
  status     TINYINT         NOT NULL DEFAULT 0 COMMENT '0待付 1已付 2已发货 3完成',
  created_at DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_user (user_id),
  UNIQUE KEY uk_order_no (order_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

现在表里有 **10 万行**。一切正常，查询几毫秒返回。

业务开始增长。下面我们让它一路长到 **10 亿行**，看会发生什么。

---

## 第 1 步：数据变多，到底慢在哪

先纠正一个很常见的误解。

**很多人以为"数据涨 100 倍，查询就慢 100 倍"。不是的。**

MySQL 找一行数据的方式，类似查一本带目录的字典：

```
   ┌─────────────────────────────────────┐
   │  第 1 层目录：翻到大致范围            │  ← 读 1 次磁盘
   ├─────────────────────────────────────┤
   │  第 2 层目录：缩小到某一页            │  ← 读 1 次磁盘
   ├─────────────────────────────────────┤
   │  数据页：在这一页里找到那一行          │  ← 读 1 次磁盘
   └─────────────────────────────────────┘
```

关键在于：**目录每多一层，能管的数据量就翻上千倍。**

```
   目录 2 层    大约能装      2 万行
   目录 3 层    大约能装   2000 万行
   目录 4 层    大约能装  200 亿行
```

所以：

```
   10 万行   →  查一次读 3 次磁盘
   2000 万行 →  查一次读 3 次磁盘        ← 涨了 200 倍，一样快
   10 亿行   →  查一次读 4 次磁盘        ← 只多了 1 次
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  结论：单纯"按主键查一行"，数据涨到 10 亿也只慢一点点。    │
   │                                                           │
   │  所以"表大了要拆"，理由【不是】单行查询变慢。              │
   │  真正先出问题的是别的事情 —— 见第 2 步。                   │
   └──────────────────────────────────────────────────────────┘
```

> 这一层的完整推导（为什么一页装 1170 个目录项、3 层为什么正好 2000 万行）
> 在《[B+ 树原理](B+树原理.md)》里。本篇只需要上面这个结论。

## 第 2 步：那到底什么先出问题

订单表涨到 5000 万行时，最先让人受不了的是这几件事：

### ① 删老数据，删不动

```sql
DELETE FROM `order` WHERE created_at < '2023-01-01';
```

```
   1000 万行 ——
   · 跑了 4 个小时
   · 期间数据库压力很大，别的查询跟着变慢
   · 删完了，【磁盘空间还没释放】
```

### ② 改表结构，改不动

```sql
ALTER TABLE `order` ADD COLUMN remark VARCHAR(255);
```

```
   5000 万行 —— 要重建整张表，跑几十分钟到几小时
```

### ③ 备份越来越久

```
   全库备份从 10 分钟变成 3 小时，
   备份期间的 IO 压力影响线上
```

### ④ 然后是另一类问题：机器本身到顶了

```
   磁盘：      单机 2TB，订单数据已经 1.5TB
   内存：      数据装不进内存，查询大量落到磁盘
   CPU：       写入 QPS 上来后，CPU 长期 90%+
   连接数：    应用实例扩到 50 个，数据库连接数打满
```

### 这里要看清一件事

```
   ┌────────────────────────────────────────────────────────┐
   │  ①②③  是「这张表太大」的问题                            │
   │        —— 表还在这台机器上，只是它自己太笨重了            │
   │                                                         │
   │  ④     是「这台机器不够用」的问题                        │
   │        —— 表怎么整理都没用，机器就这么大                  │
   └────────────────────────────────────────────────────────┘
```

**这两类问题的解法完全不同。**接下来两步分别处理它们。

---

## 第 3 步：先解决"删不动"——把一张表切成几个文件

回到那条删了 4 小时的 SQL。它为什么慢？

```
   DELETE 是【一行一行】删的：
     · 每删一行，要记一条回滚日志（万一你要撤销）
     · 每删一行，要更新这一行涉及的所有索引
     · 1000 万行 = 上面这套动作做 1000 万遍
```

那换个想法：**如果 2022 年的订单本来就单独存在一个文件里，直接把那个文件删掉，不就行了？**

这就是**分区表**。

### 它长什么样

```
   之前：一张 order 表 = 一个数据文件
   ┌──────────────────────────────────────────────┐
   │  2022年 + 2023年 + 2024年的订单，全在一起      │
   └──────────────────────────────────────────────┘

   之后：一张 order 表 = 【按月切开的多个文件】
   ┌────────┬────────┬────────┬────────┬────────┐
   │2024-01 │2024-02 │2024-03 │2024-04 │  ...   │
   └────────┴────────┴────────┴────────┴────────┘
```

关键在于：

```
   ┌──────────────────────────────────────────────────────────┐
   │  对你的代码来说，它【还是一张表】。                        │
   │                                                           │
   │  SELECT * FROM `order` WHERE id = 123;                    │
   │       ↑ 一个字都不用改。MySQL 自己知道去哪个文件找。       │
   │                                                           │
   │  只是在磁盘上，它被切成了好几块。                          │
   └──────────────────────────────────────────────────────────┘
```

### 删老数据变成了什么

```sql
ALTER TABLE `order` DROP PARTITION p202201;
```

```
   ┌────────┬────────┬────────┐
   │2022-01 │2022-02 │  ...   │
   └───╳────┴────────┴────────┘
       ↑ 直接把这个文件删掉

   · 【一秒】完成
   · 几乎不产生回滚日志
   · 磁盘空间【立刻】还给操作系统
```

```
   从 4 小时到 1 秒。

   这就是分区表最核心、也常常是【唯一】值得的理由。
```

### 怎么建

```sql
CREATE TABLE `order` (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL,
  amount     BIGINT NOT NULL DEFAULT 0,
  created_at DATETIME(3) NOT NULL,
  PRIMARY KEY (id, created_at)          -- ← 注意这里，第 4 步解释
)
PARTITION BY RANGE (TO_DAYS(created_at)) (      -- 按 created_at 切
  PARTITION p202401 VALUES LESS THAN (TO_DAYS('2024-02-01')),
  PARTITION p202402 VALUES LESS THAN (TO_DAYS('2024-03-01')),
  PARTITION p202403 VALUES LESS THAN (TO_DAYS('2024-04-01'))
);
```

读法很直白：

```
   PARTITION BY RANGE (created_at)          按 created_at 的范围切
   p202401 VALUES LESS THAN '2024-02-01'    小于 2 月 1 号的，放这一格
   p202402 VALUES LESS THAN '2024-03-01'    小于 3 月 1 号的，放这一格
                                             （2 月 1 号之后的自然落这里）
```

```
   插入 created_at = 2024-02-15 的订单
        ↓
   比 2024-02-01 大，比 2024-03-01 小
        ↓
   落进 p202402 这个文件
```

> `TO_DAYS()` 是把日期转成一个整数（从公元 0 年算起的天数）。
> MySQL 要求切分依据最好是整数，所以日期要转一下。仅此而已。

## 第 4 步：分区表的好处和代价

### 好处：查最近的数据，只翻一个文件

```sql
SELECT SUM(amount) FROM `order` WHERE created_at >= '2024-03-01';
```

```
   ┌────────┬────────┬────────┐
   │2024-01 │2024-02 │2024-03 │
   └────────┴────────┴───█────┘
      跳过     跳过    只扫这个

   MySQL 一看条件就知道：2024-01 和 2024-02 里不可能有 3 月的数据，
   直接【整个跳过】。
```

这叫**分区裁剪**。

### 代价：查询不带切分依据时，反而更慢

```sql
SELECT * FROM `order` WHERE order_no = 'X20240315001';
```

```
   ┌────────┬────────┬────────┐
   │2024-01 │2024-02 │2024-03 │
   └───█────┴───█────┴───█────┘
      要扫     要扫     要扫

   条件里没有 created_at → MySQL【无法判断】这个订单号在哪个月
   → 只能【每个文件都翻一遍】
   → 比不分区还慢（多了几次文件切换的开销）
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  这是分区表最重要的一条规矩：                              │
   │                                                           │
   │  你按哪个字段切的，查询就【必须带上那个字段】，            │
   │  否则等于没分区，而且更慢。                                │
   └──────────────────────────────────────────────────────────┘
```

所以订单表按 `created_at` 分区，前提是：**你的查询绝大多数都带时间条件**。如果业务大量按订单号查，分区表就不合适。

### 那个奇怪的主键

回头看建表语句里的 `PRIMARY KEY (id, created_at)`。为什么不能只写 `PRIMARY KEY (id)`？

MySQL 会直接报错。原因是：

```
   每个分区是【互相独立】的，它们不知道对方存了什么。

   假设允许 PRIMARY KEY (id)：
     插入 id=100, created_at=2024-01-05  →  进 p202401
     插入 id=100, created_at=2024-03-05  →  进 p202403
                                             ↑ p202403 里没有 id=100，
                                               检查通过！主键重复了

   要挡住它，就得【每个分区都查一遍】—— 分区多了就很贵。
   MySQL 不干这事，于是要求：
     切分用的字段，必须出现在主键（和每一个唯一索引）里。
```

```
   PRIMARY KEY (id, created_at)
                    ↑ 加上它，相同的主键必然落在同一个分区，
                      只查那一个分区就够了
```

**代价是唯一性被削弱了**：

```
   UNIQUE KEY (order_no, created_at)
   → ('X001', 一月) 和 ('X001', 三月) 都能插进去
   → 订单号"全局唯一"这件事，分区表【保证不了】了
```

这一条经常让人措手不及，建表前一定要想清楚。

## 第 5 步：分区表救不了什么

这一节决定了你会不会误用它。

```
   把 order 表切成 36 个分区之后 ——

   ✓ 删 2022 年的数据          从 4 小时变 1 秒
   ✓ 查最近一个月              只扫一个文件
   ✓ 表变"小"了                每个分区各自有一套目录，树更矮一点

   ─────────────────────────────────────────────

   ✗ 磁盘还是 1.5TB            36 个文件加起来还是那么多
   ✗ CPU 还是那台机器的         所有分区都在同一个 MySQL 里跑
   ✗ 连接数还是那么多           还是同一个实例
   ✗ 机器挂了还是全挂           分区不提供任何冗余
   ✗ 备份还是要备整张表
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  一句话记住分区表：                                        │
   │                                                           │
   │  它是把【一个房间】里的东西分成几个柜子放。                │
   │  东西好找了、扔起来方便了 ——                               │
   │  但房间还是那个房间，装不下就是装不下。                    │
   └──────────────────────────────────────────────────────────┘
```

所以回到第 2 步的分类：

```
   ①②③（表太大：删不动、改不动、备份久）  →  分区表能解决 ✓
   ④  （机器不够：磁盘/CPU/连接数到顶）    →  分区表【完全无效】
```

要解决 ④，只有一条路：**换更多的房间。**

---

## 第 6 步：房间不够了——「拆」有两个方向

现在我们要把数据真正搬到多台机器上。

在动手之前，先把"拆"这个动作想清楚。**一张表本质上是一个矩形**：

```
                 ← 列 →
        ┌──────┬──────┬──────┬──────────────┐
        │  id  │user_id│amount│   备注(很长)  │
        ├──────┼──────┼──────┼──────────────┤
   ↑    │  1   │  7   │ 100  │  ......      │
   行   │  2   │  9   │ 200  │  ......      │
   ↓    │  3   │  7   │ 350  │  ......      │
        │ ...  │      │      │              │
        └──────┴──────┴──────┴──────────────┘
```

一个矩形只有两种切法：

```
        竖着切（按列）                    横着切（按行）
   ┌──────┬──────╎──────────┐      ┌──────────────────────┐
   │  id  │user_id╎ 备注     │      │  id 1 ~ 1000万        │
   │      │      ╎          │      ├──────────────────────┤
   │      │      ╎          │      │  id 1000万 ~ 2000万   │
   └──────┴──────╎──────────┘      ├──────────────────────┤
                                    │  id 2000万 ~ 3000万   │
   叫【垂直拆分】                     └──────────────────────┘
   常用的列一张表                       叫【水平拆分】
   不常用的列另一张表                   每张表结构一样，只是行不同
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  垂直拆分：表【变窄】了，行数没变                          │
   │  水平拆分：行数【变少】了，表结构没变                      │
   └──────────────────────────────────────────────────────────┘
```

还有一个词要顺带说清楚：

```
   分表   拆完的几张表还在【同一个数据库】里
   分库   拆完的表分到【不同的数据库/机器】上

   所以常说的"分库分表"= 先水平拆成很多张表，再把它们分散到多台机器
```

**规矩是：先竖着切，再横着切。**下面两步分别说，你会看到为什么是这个顺序。

---

## 第 7 步：先竖着切——很可能切完就够了

订单表长期演进后，往往变成这样：

```sql
CREATE TABLE `order` (
  id, user_id, order_no, amount, status, created_at,   -- 常用
  receiver_name, receiver_phone, receiver_address,      -- 收货信息
  remark          VARCHAR(500),                         -- 用户备注
  extra_json      TEXT,                                 -- 各种扩展字段
  invoice_title   VARCHAR(200),                         -- 发票抬头
  ...
);
```

关键观察：

```
   99% 的请求（订单列表、订单状态）只用到前 6 个字段
    1% 的请求（订单详情页）才需要后面那些
```

但数据库不管这些——**它读一行就是读一整行**。

### 为什么这件事影响很大

数据库是按"页"读磁盘的，一页固定 16KB。**一行越宽，一页装的行就越少**：

```
   一行 200 字节  →  一页装 80 行
   一行 1.5 KB    →  一页装 10 行
                       ↑ 差 8 倍
```

后果：

```
   查 100 条订单：
     窄表：这 100 行可能只分布在 2 页里   → 读 2 次磁盘
     宽表：要分布在 10 页里              → 读 10 次磁盘
```

而且目录能管的数据量也跟着变：

```
   一行 200 字节   →  3 层目录能装约 1.1 亿行
   一行 1.5 KB     →  3 层目录只能装约 1500 万行
                        ↑ 超了就变 4 层，每次查询多读一次磁盘
```

### 所以竖着切一刀

```sql
-- 主表：99% 的请求只碰它，保持窄
CREATE TABLE order_base (
  id         BIGINT UNSIGNED NOT NULL,
  user_id    BIGINT UNSIGNED NOT NULL,
  order_no   VARCHAR(32) NOT NULL,
  amount     BIGINT NOT NULL DEFAULT 0,
  status     TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME(3) NOT NULL,
  PRIMARY KEY (id)
);

-- 附表：进详情页才读
CREATE TABLE order_detail (
  order_id       BIGINT UNSIGNED NOT NULL,    -- ← 和 order_base.id 相同
  receiver_name  VARCHAR(64)  NOT NULL DEFAULT '',
  receiver_phone VARCHAR(20)  NOT NULL DEFAULT '',
  remark         VARCHAR(500) NOT NULL DEFAULT '',
  extra_json     TEXT,
  PRIMARY KEY (order_id)                       -- ← 主键就是关联键，【不要自增】
);
```

```
   两张表用同一个 id 关联。
   ⚠️ order_detail.order_id 【绝对不能写 AUTO_INCREMENT】——
      它必须等于 order_base 的 id，各自增长就永远对不上了。
```

### 效果

```
   拆之前：一行 1.5 KB  →  3 层目录装 1500 万行
   拆之后：一行 200 字节 →  3 层目录装 1.1 亿行

              容量涨了【7 倍】，一行代码逻辑都没改
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  这就是"先竖着切"的道理：                                  │
   │                                                           │
   │  · 它可能让你【根本不需要】横着切                          │
   │  · 它几乎不改变查询方式（还是普通 SQL）                    │
   │  · 而横着切的复杂度是不可逆的（第 9 步你会看到）           │
   └──────────────────────────────────────────────────────────┘
```

**如果业务只有 3000 万订单，竖着切完就到此为止了。**下面的内容你用不上。

---

## 第 8 步：还是不够，横着切

假设订单真的涨到 10 亿，单机磁盘也装不下了。现在必须横着切，把数据分散到多台机器。

### 第一个问题：按什么切

```
   ┌─ 方案 A：按 id 范围切 ─────────────────────────┐
   │   表0: id 1~1亿    表1: id 1亿~2亿   ...        │
   │                                                 │
   │   ✗ 新订单的 id 永远最大 → 【全打在最后一张表】  │
   │     其他表是死的，等于没分                       │
   └─────────────────────────────────────────────────┘

   ┌─ 方案 B：按 user_id 取模切 ────────────────────┐
   │   user_id % 8 = 0 → 表0                        │
   │   user_id % 8 = 1 → 表1   ...                  │
   │                                                 │
   │   ✓ 用户是均匀分布的 → 数据均匀落到 8 张表      │
   └─────────────────────────────────────────────────┘
```

选 B。于是：

```
                    user_id = 12345
                          │
                   12345 % 8 = 1
                          ↓
   ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
   │ 表0  │ 表1  │ 表2  │ 表3  │ 表4  │ 表5  │ 表6  │ 表7  │
   └──────┴──█───┴──────┴──────┴──────┴──────┴──────┴──────┘
             ↑ 这个用户的所有订单都在这里
```

### 第二个问题：查的时候怎么知道去哪张表

```sql
SELECT * FROM `order` WHERE user_id = 12345;
        ↓
   算一下 12345 % 8 = 1  →  去 order_1 查      ✓ 只查一张表
```

```sql
SELECT * FROM `order` WHERE order_no = 'X20240315001';
        ↓
   订单号算不出 user_id  →  【8 张表全查一遍】  ✗
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  用来决定"数据放哪张表"的那个字段，叫【分片键】。          │
   │                                                           │
   │  查询带分片键  →  直接算出在哪张表，只查一张               │
   │  查询不带     →  只能【所有表都查一遍】再合并结果           │
   │                                                           │
   │  和第 4 步分区表的规矩是同一回事。                         │
   └──────────────────────────────────────────────────────────┘
```

### 所以分片键怎么选：先数一数

**动手拆之前，先统计业务到底怎么查这张表。**

```
   订单表的真实访问情况（举例）：
     90%   用 user_id 查（"我的订单"列表）
      8%   用 order_id / order_no 查（订单详情）
      2%   按时间范围统计（后台报表）
```

```
   → 分片键选 user_id
     因为它能让 90% 的查询只打一张表
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  分片键是整个方案里【最贵】的一个决定 —— 选错了要重构。    │
   │  而它的依据不是拍脑袋，是【访问方式的统计】。              │
   └──────────────────────────────────────────────────────────┘
```

### 那剩下 8% 按订单号查的怎么办

不能不管——订单详情页要是每次都查 8 张表，是不可接受的。

两个常用办法：

```
   ① 映射表（简单可靠）
      单独一张小表：order_no → user_id
      查询变两步：先查这张表拿到 user_id，再算分片
      两次都是主键等值查询，都很快

   ② 把 user_id 藏进订单号（叫"基因法"）
      生成订单号时，把 user_id % 8 的结果拼进订单号的固定位置
      order_no = "20240315" + 序列号 + "1"
                                        ↑ 直接读出来就是分片号
      → 用订单号也能算出去哪张表，不用查映射表
```

### 分几张表：用 2 的幂

```
   ┌─ 分 5 张表，将来扩到 10 张 ────────────────────┐
   │   %5 → %10                                     │
   │   user_id=7  原本在表2，扩容后到表7  → 要搬     │
   │   user_id=12 原本在表2，扩容后到表2  → 不搬     │
   │   → 搬哪些、搬到哪，几乎要【全部重算一遍】       │
   └─────────────────────────────────────────────────┘

   ┌─ 分 8 张表，将来扩到 16 张 ────────────────────┐
   │   %8 → %16                                     │
   │   规律：x%16 要么等于 x%8，要么等于 x%8 + 8     │
   │   → 每张表【正好对半劈开】                      │
   │   → 只搬走一半，而且搬去哪是确定的               │
   └─────────────────────────────────────────────────┘
```

```
   所以分片数取 2 的幂（8、16、32、64），
   并且【一次分够】—— 二次扩容的代价很高。
```

### 主键不能再自增了

```
   8 张表各自 AUTO_INCREMENT：
     order_0 生成 id = 1, 2, 3 ...
     order_1 也生成 id = 1, 2, 3 ...
                    ↑ id 重复了
```

必须换成**全局唯一的 id**，最常用的是**雪花 ID**：

```
   雪花 ID = 时间戳(41位) + 机器号(10位) + 序列号(12位)
             └──── 高位是时间 ⟹ 生成出来的 id 是【递增】的 ────┘

   为什么强调递增？因为主键递增时，新数据总是往表的末尾追加，
   不会插到中间去搅乱已有的数据页。
   随机的 UUID 会让插入到处乱插，性能差很多。
```

还有一个绕不过去的点：

```
   分片键是 user_id，可 id 得先生成才能插入 ——
   而生成 id 又不能靠数据库（各表各自增会撞）

   ⟹ id 必须在【应用层】（或专门的发号服务）先拿到，
      不能依赖数据库生成
```

## 第 9 步：横着切之后，哪些事情做不了了

这一步是"先竖着切"那条规矩的最终理由。

### ① 跨表 JOIN 没了

```sql
SELECT o.*, u.nickname
  FROM `order` o JOIN user u ON o.user_id = u.id;
```

```
   order 在 8 台机器上，user 在另外几台 —— 【JOIN 根本执行不了】

   解法：· 在订单表里冗余一个 nickname 字段
        · 或者分两次查，在应用代码里拼
```

### ② 事务没了

```
   一个事务里改了 order_1 和 order_5 —— 它们在不同的机器上
   数据库的事务管不了跨机器的操作

   解法：改成"最终一致"（本地消息表 / Seata 等），
        接受中间有一小段时间不一致
```

### ③ 分页变得很贵

这个最反直觉：

```
   要查全局第 10001 ~ 10010 条订单（按时间排序），共 8 张表

   ✗ 每张表取 LIMIT 1250, 2
        错的！全局前 10000 条可能集中在某一两张表里

   ✓ 每张表都取 LIMIT 0, 10010
        8 × 10010 = 80080 条全部拉回内存排序，再取中间那 10 条
        → 【表越多越慢，页码越深越慢】
```

```
   实践：禁止深分页，改成"上一页最后一条的 id 往后翻"。
```

### ④ COUNT / ORDER BY / GROUP BY 都要合并

```
   SELECT COUNT(*) → 8 张表各查一次再相加
   统计类查询基本都要走 ES 或数仓，不在 MySQL 里做
```

### ⑤ 唯一约束只在单表内有效

```
   UNIQUE KEY (order_no) 在每张表里都成立，
   但两张不同的表【各插一条相同的 order_no】，谁也发现不了

   解法：· 唯一键里包含分片键
        · 或者用一张不分片的小表来保证全局唯一
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  这五条加起来，就是"能不横着切就别横着切"的理由。          │
   │  它带来的复杂度会跟着这个系统一辈子。                      │
   └──────────────────────────────────────────────────────────┘
```

## 第 10 步：完整的决策路径

把前面九步收成一张路线图。**从上往下走，能在哪一步停就在哪一步停。**

```
   ① 索引建对了吗？
        很多"必须分库分表"其实是某条 SQL 没走索引
        → 先把慢查询日志翻一遍
        还不行 ↓

   ② 老数据能不能直接归档走？
        只查最近 3 个月 → 历史数据挪到 order_history 表
        还不行 ↓

   ③ 痛点只是"删历史数据慢"吗？
        → 【分区表】（第 3 步），到此为止
        还不行 ↓

   ④ 是读扛不住吗？
        → 加从库做读写分离 + 加缓存，不用拆
        还不行 ↓

   ⑤ 表是不是太宽、有大字段？
        → 【垂直拆分】（第 7 步）  ★ 先做这个，可能就够了
        还不行 ↓

   ⑥ 单表行数还是太多？
        → 【水平分表】：拆成多张表，还在一个库里
        还不行 ↓

   ⑦ 机器的磁盘/CPU/连接数到顶了？
        → 【分库】：把表分到多台机器上（第 8 步）
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  ①~⑤ 能解决的，就别走到 ⑥⑦。                              │
   │                                                           │
   │  日活 1000 的内部系统，别一上来就分 128 张表。             │
   │  过度设计的成本是【长期的复杂度】。                        │
   └──────────────────────────────────────────────────────────┘
```

### 一张对照表

| | 分区表 | 分库分表 |
|---|---|---|
| 一句话 | 一个房间里分几个柜子 | 换更多的房间 |
| 代码要改吗 | **完全不用改** | 要改，还要引中间件 |
| 跨机器吗 | 否 | 是 |
| 解决磁盘/CPU 上限 | **不能** | 能 |
| 删历史数据 | **一秒（`DROP PARTITION`）** | 直接 drop 整张表 |
| 运维复杂度 | 低 | **高** |
| 什么时候用 | 按时间存的表，要定期删老数据 | 单机真的撑不住了 |

## 第 11 步：真要做分库分表，怎么落地

不是"停机改造一晚上"，是一个持续几周的过程：

```
   ① 新库建好，开【增量同步】
        订阅老库的变更日志，实时灌进新的分片库
        （业务代码一行不用改）

   ② 迁移存量数据
        用工具把历史数据搬过去，允许慢慢跑

   ③ 等增量追平
        监控同步延迟趋近 0

   ④ 对账
        全量比对 + 抽样比对，确认两边一致

   ⑤ 灰度切读
        1% → 10% → 100%，出问题立刻切回去

   ⑥ 切写
        老库保留一段时间，以便回滚
```

> 第 ① 步的"订阅变更日志"用的是 binlog，具体做法见《[binlog · 5.6](binlog.md)》。

### 中间件

分片路由不用自己写，交给中间件：

```
   ShardingSphere-JDBC   以 jar 包形式嵌在应用里，无额外部署  ← 最常用
   ShardingSphere-Proxy  独立部署成一个"假 MySQL"，各语言都能连
   MyCat                 老牌代理，社区活跃度已下降
```

## 附录 A：分区表的实操细节

正文只用到了最基本的形态。真正落地时会碰到下面这些。

### A.1 四种分区方式

| 方式 | 按什么切 | 什么时候用 |
|---|---|---|
| **RANGE** | 连续区间 | **按时间的表** ← 90% 的场景 |
| **LIST** | 枚举值 | 按地区、渠道等取值固定的列 |
| **HASH** | 哈希取模 | 只想让数据均匀散开 |
| **KEY** | MySQL 自己算哈希 | 同上，但列可以不是整数 |

### A.2 `MAXVALUE` 兜底分区的两难

```sql
PARTITION pmax VALUES LESS THAN (MAXVALUE)   -- 超出所有范围的都进这里
```

```
   ✓ 没有它 → 插入超范围的数据会【直接报错】
   ✗ 有了它 → 【再也不能 ADD PARTITION】
```

```sql
mysql> ALTER TABLE `order` ADD PARTITION (PARTITION p202405 VALUES LESS THAN (...));
ERROR 1481 (HY000): MAXVALUE can only be used in last partition definition
```

因为新分区只能加在最高端，而 `MAXVALUE` 已经把最高端占死了。

两条出路：

```
   路线 A（推荐）：建表时【不要】MAXVALUE，用定时任务每月追加新分区
                  + 提前预建 12 个月当缓冲
                  + 对"剩余分区数"加告警（任务挂了会导致插入失败）

   路线 B：保留 MAXVALUE，需要时用 REORGANIZE 把它劈成两半
```

```sql
-- 路线 A
ALTER TABLE `order` ADD PARTITION (
  PARTITION p202405 VALUES LESS THAN (TO_DAYS('2024-06-01')));

-- 路线 B：把兜底分区一劈为二
ALTER TABLE `order` REORGANIZE PARTITION pmax INTO (
  PARTITION p202405 VALUES LESS THAN (TO_DAYS('2024-06-01')),
  PARTITION pmax    VALUES LESS THAN (MAXVALUE));
```

```
   之前：  … │ p202404 │        pmax (MAXVALUE)       │
                          ↓ REORGANIZE
   之后：  … │ p202404 │ p202405 │   pmax (MAXVALUE)   │
```

> 路线 B 要重建这个分区的数据，只适合"兜底分区平时是空的"的情况。

### A.3 常用命令

```sql
-- 给已有表加分区（⚠️ 这是全表重建，大表上用 gh-ost / pt-osc）
ALTER TABLE `order` PARTITION BY RANGE (TO_DAYS(created_at)) ( ... );

-- 删分区（物理删数据，秒级）
ALTER TABLE `order` DROP PARTITION p202401;

-- 只清空数据、保留分区
ALTER TABLE `order` TRUNCATE PARTITION p202401;

-- 看有哪些分区
SELECT PARTITION_NAME, PARTITION_DESCRIPTION, TABLE_ROWS
  FROM information_schema.PARTITIONS
 WHERE TABLE_NAME = 'order';

-- 确认分区裁剪生效了没
EXPLAIN SELECT ... ;      -- 看 partitions 列，列出了哪几个就扫哪几个
```

### A.4 分区表 Checklist

```
   [ ] 绝大多数查询都带切分字段吗？（不带 = 白分，还更慢）
   [ ] 主键和所有唯一索引都包含切分字段了吗？
   [ ] 接受"唯一约束只在分区内有效"吗？
   [ ] 新分区怎么加？定时任务 + 告警配好了吗？
   [ ] 老分区什么时候删？有定时任务吗？
```
