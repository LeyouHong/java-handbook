# MySQL 分区表与分库分表

> 环境：MySQL 8.0 / InnoDB。本篇是《[数据表设计 · 1.1](数据表设计.md)》里那张「数据量 → 形态」阶梯表的**深入篇**：
>
> ```
>    < 500 万          单表，把索引建对就行
>    500 万 ~ 2000 万  单表 + 冷热分离
>    2000 万 ~ 1 亿    分区表 / 单库分表        ← 本篇第一节
>    > 1 亿            分库分表                 ← 本篇第二节
> ```
>
> **一句话主线：分区表管「整理」，分库分表管「分散」——它们不是同一个量级的手段。**

---

## 零、先分清：两者解决的不是同一个问题

最常见的误解是把分区表当成"分表的轻量版"。**不是。**

```
   ┌─ 分区表 ─────────────────────────────────────────────────┐
   │  逻辑上还是一张表，物理上拆成多个文件                       │
   │  【仍然在同一个 MySQL 实例里】                             │
   │                                                           │
   │  ✓ 应用完全无感，SQL 一行都不用改                          │
   │  ✗ 单机的 CPU / 内存 / 磁盘 IO / 连接数，一点没解决         │
   └───────────────────────────────────────────────────────────┘

   ┌─ 分库分表 ───────────────────────────────────────────────┐
   │  数据真的散到多张表、多个实例                              │
   │                                                           │
   │  ✗ 应用要大改：分片键、全局 ID、中间件、跨库事务……          │
   │  ✓ 压力是【真的】分散了                                    │
   └───────────────────────────────────────────────────────────┘
```

分界线很清楚：

```
   数据量大（存不下、树太高）  →  分区表能帮上忙
   访问量大（QPS / IO 顶不住）  →  只有分库能救，分区表毫无作用
```

# 第一部分：分区表

## 一、四种分区类型

| 类型 | 划分依据 | 典型场景 |
|---|---|---|
| **RANGE** | 连续区间 | **按时间的报表 / 日志表** ← 最常用 |
| **LIST** | 枚举值 | 按地区、渠道等取值有限的列 |
| **HASH** | 你给的哈希表达式 | 让数据均匀散开 |
| **KEY** | MySQL 自己产生哈希值 | 同上，但分区列可以不是整型 |

实际用得最多的是 **RANGE 和 HASH**。下面全部围绕 RANGE 展开——它规则最简单、普适性最强。

## 二、RANGE 分区：规则只有两条

```
   ① 每个分区必须指定范围上界（VALUES LESS THAN）
   ② 所有范围必须【连续、不重叠】
```

还有一条建议：**分区列最好是整型**。所以时间列要先转换：

```
   date / datetime  →  TO_DAYS()
   timestamp        →  UNIX_TIMESTAMP()
```

## 三、建表时指定分区

案例是一张广告花费报表——**报表型数据按天存储，时间天然就是最好的分区键**：

```sql
CREATE TABLE `ad_unit_cost` (
  `user_id` bigint(20) NOT NULL DEFAULT '0' COMMENT '关联所属用户',
  `plan_id` bigint(20) NOT NULL DEFAULT '0' COMMENT '关联推广计划 id',
  `unit_id` bigint(20) NOT NULL DEFAULT '0' COMMENT '关联推广单元 id',
  `cost`    bigint(20) NOT NULL DEFAULT '0' COMMENT '推广单元花费金额',
  `date_`   date       NOT NULL            COMMENT '数据日期，yyyy-MM-dd'
) ENGINE=InnoDB DEFAULT CHARSET=utf8
PARTITION BY RANGE (TO_DAYS(date_)) (
    PARTITION p0 VALUES LESS THAN (TO_DAYS('2019-01-01')),
    PARTITION p1 VALUES LESS THAN (TO_DAYS('2019-02-01')),
    PARTITION p2 VALUES LESS THAN (TO_DAYS('2019-03-01')),
    PARTITION p3 VALUES LESS THAN (TO_DAYS('2019-04-01')),
    PARTITION p4 VALUES LESS THAN (TO_DAYS('2019-05-01')),
    PARTITION p5 VALUES LESS THAN (TO_DAYS('2019-06-01')),
    PARTITION p6 VALUES LESS THAN (MAXVALUE)
);
```

> 新表请用 `CHARSET=utf8mb4`——`utf8` 是 3 字节的假货，存不了 emoji（见《[数据表设计 · 1.3 数据规范](数据表设计.md)》）。

数据落到哪个分区：

```
   date_ = 2018-12-20  ──▶  p0   (< 2019-01-01)
   date_ = 2019-01-15  ──▶  p1   (< 2019-02-01)
   date_ = 2019-03-31  ──▶  p3   (< 2019-04-01)
   date_ = 2019-12-01  ──▶  p6   (MAXVALUE 兜底)

   ┌────┬────┬────┬────┬────┬────┬──────────┐
   │ p0 │ p1 │ p2 │ p3 │ p4 │ p5 │    p6    │  ← 7 个独立的物理结构
   └────┴────┴────┴────┴────┴────┴──────────┘
     ↑ 每一个分区都是一棵【独立的 B+ 树】
```

## 四、`MAXVALUE` 这个坑

`p6` 是兜底分区。它有两面：

```
   ✓ 没有它 → 插入超出所有范围的数据会【直接报错】
   ✗ 有了它 → 【再也不能 ADD PARTITION】
```

第二条是课程里那个报错：

```sql
mysql> ALTER TABLE ad_unit_cost ADD PARTITION(
    ->   PARTITION p3 VALUES LESS THAN (TO_DAYS('2019-04-01')));
ERROR 1481 (HY000): MAXVALUE can only be used in last partition definition
```

原因：RANGE 分区**只能往列表的高端追加**，而 `MAXVALUE` 已经占死了最高端，新分区插不进去。

课程把"怎么加分区"留成了作业，答案有两条路：

### 路线 A：建表时不要 `MAXVALUE`，定期追加（推荐）

```sql
-- 建表时最后一个分区就是 p5，不带 MAXVALUE
-- 然后用定时任务每月月初追加下个月的分区
ALTER TABLE ad_unit_cost ADD PARTITION(
  PARTITION p6 VALUES LESS THAN (TO_DAYS('2019-07-01')));
```

代价：**定时任务一旦挂了，超范围的数据直接插入失败**。所以要预建若干个月的分区当缓冲，并对"剩余分区数"加监控。

### 路线 B：带 `MAXVALUE`，用 `REORGANIZE` 劈开它

```sql
ALTER TABLE ad_unit_cost REORGANIZE PARTITION p6 INTO (
  PARTITION p6   VALUES LESS THAN (TO_DAYS('2019-07-01')),
  PARTITION pmax VALUES LESS THAN (MAXVALUE)
);
```

把兜底分区**一劈为二**：前半段变成正常分区，后半段继续兜底。

```
   之前：  … │ p5 │        p6 (MAXVALUE)        │
                        ↓ REORGANIZE
   之后：  … │ p5 │  p6  │      pmax (MAXVALUE)  │
```

代价：`REORGANIZE` 要**重建这个分区的数据**。如果 MAXVALUE 分区已经堆了很多数据，这一步会很慢。所以路线 B 只适合"兜底分区平时是空的"的场景。

```
   实践建议：路线 A + 提前预建 12 个月 + 剩余分区数告警
```

## 五、为什么这张表没有主键

课程说"加上主键再建分区就会报错"，原因是 MySQL 的一条硬约束：

```
   ┌──────────────────────────────────────────────────────────┐
   │  分区表的【每一个唯一索引（含主键）】                       │
   │  必须包含分区表达式里用到的【所有列】                       │
   └──────────────────────────────────────────────────────────┘
```

```sql
PARTITION BY RANGE (TO_DAYS(date_))      -- 分区表达式用了 date_

PRIMARY KEY (id)                          -- ✗ 里面没有 date_，建不出来
PRIMARY KEY (id, date_)                   -- ✓
UNIQUE KEY  (unit_id)                     -- ✗
UNIQUE KEY  (unit_id, date_)              -- ✓ 但唯一性变味了，见下
```

### 为什么必须这样

> ⤵ **依据**：《[B+ 树原理](B+树原理.md)》——**每个分区是一棵独立的 B+ 树**，分区之间互相不知道对方存了什么。

```
   假设允许 PRIMARY KEY (id) 而分区键是 date_：

   插入 id=100, date_=2019-01-05  →  落在 p1
   插入 id=100, date_=2019-03-05  →  落在 p3
                                      ↑ p3 这棵树里没有 id=100，检查通过！

   要挡住它，就得【每个分区都查一遍】 —— O(分区数) 的代价
   MySQL 不愿意付这个代价，于是反过来要求：
```

```
   分区键 ⊆ 唯一键   ⟹   相同的唯一键必然落在【同一个分区】
                     ⟹   只查那一个分区就够了
```

### 代价：唯一性被削弱

这个约束不是免费的：

```sql
UNIQUE KEY (order_no, date_)
```

```
   ('X001', '2019-01-05')   ✓
   ('X001', '2019-03-05')   ✓  ← 同一个 order_no 又进来了！
```

**唯一约束事实上作废了**——它只保证"同一天内不重复"。

> 这和《[乐观锁与悲观锁 · 5.6 坑四](../concurrency/乐观锁与悲观锁.md)》说的是同一件事：
> **唯一键必须包含分片键，而一旦包含，全局唯一性就没了。**
> 分区表和分库分表在这一点上踩的是同一个坑。

所以案例里那张 `ad_unit_cost` 干脆不定义主键——报表表本来也不需要。

> 顺带一提：InnoDB 表既没有显式主键、**也没有非空唯一索引**时，会自动生成一个 6 字节的隐藏 `row_id` 当聚簇索引——不是真的没有聚簇索引。

## 六、查看分区信息

分区元数据在 `information_schema.PARTITIONS`：

```sql
SELECT TABLE_NAME, PARTITION_NAME, PARTITION_METHOD,
       PARTITION_EXPRESSION, PARTITION_DESCRIPTION
  FROM information_schema.`PARTITIONS`
 WHERE table_name = 'ad_unit_cost';
```

```
+--------------+----------------+------------------+----------------------+-----------------------+
| TABLE_NAME   | PARTITION_NAME | PARTITION_METHOD | PARTITION_EXPRESSION | PARTITION_DESCRIPTION |
+--------------+----------------+------------------+----------------------+-----------------------+
| ad_unit_cost | p0             | RANGE            | TO_DAYS(date_)       | 737425                |
| ad_unit_cost | p1             | RANGE            | TO_DAYS(date_)       | 737456                |
| ad_unit_cost | p2             | RANGE            | TO_DAYS(date_)       | 737484                |
| ad_unit_cost | p3             | RANGE            | TO_DAYS(date_)       | 737515                |
| ad_unit_cost | p4             | RANGE            | TO_DAYS(date_)       | 737545                |
| ad_unit_cost | p5             | RANGE            | TO_DAYS(date_)       | 737576                |
| ad_unit_cost | p6             | RANGE            | TO_DAYS(date_)       | MAXVALUE              |
+--------------+----------------+------------------+----------------------+-----------------------+
```

`PARTITION_DESCRIPTION` 里那串数字就是 `TO_DAYS()` 的返回值——**从公元 0 年算起的天数**：

```
   TO_DAYS('2019-01-01') = 737425
   TO_DAYS('2019-02-01') = 737456   ← 差 31（一月 31 天）
   TO_DAYS('2019-03-01') = 737484   ← 差 28（2019 不是闰年）
   TO_DAYS('2019-04-01') = 737515   ← 差 31
```

**相邻两行的差正好是当月天数**，可以用它快速验证分区边界有没有写错。

## 七、给已有表加分区

```sql
ALTER TABLE ad_unit_cost PARTITION BY RANGE (TO_DAYS(date_)) (
    PARTITION p0 VALUES LESS THAN (TO_DAYS('2019-01-01')),
    ...
);
```

MySQL 会自动把已有数据分配到对应分区。

> ⚠️ **这是一次全表重建**。几百万行以上的表上执行，会长时间占用资源并可能阻塞写入。
> 生产环境用 `pt-online-schema-change` 或 `gh-ost`，别直接 `ALTER`。

## 八、真正的杀手锏：`DROP PARTITION`

```sql
ALTER TABLE ad_unit_cost DROP PARTITION p3;
```

**注意：这会物理删除该分区的所有数据。**这不是缺点，恰恰是它最大的价值：

```
   ┌────────────────────────────────────────────────────────────────┐
   │  DELETE FROM ad_unit_cost WHERE date_ < '2019-04-01';           │
   │                                                                 │
   │  · 逐行删，几百万行要几分钟到几小时                              │
   │  · undo log 暴涨，长事务阻塞 purge（⤵《事务与 MVCC》第九节）    │
   │  · 主从延迟飙升                                                 │
   │  · 删完【空间还不释放】，只是标记可复用                          │
   ├────────────────────────────────────────────────────────────────┤
   │  ALTER TABLE ad_unit_cost DROP PARTITION p3;                    │
   │                                                                 │
   │  · 直接删文件，【秒级】                                          │
   │  · 几乎不产生 undo / binlog 行事件                              │
   │  · 空间【立刻】还给操作系统                                      │
   └────────────────────────────────────────────────────────────────┘
```

```
   判断你该不该用分区表，就问一句：
   「我需要定期成批删除历史数据吗？」
        是  → 分区表非常香
        否  → 大概率不该用它
```

## 九、分区表快在哪：分区裁剪

分区表的性能收益**只来自一件事**——`WHERE` 里带分区键时，MySQL 只扫需要的分区（partition pruning）。

`EXPLAIN` 的 `partitions` 列会告诉你扫了哪些：

```sql
EXPLAIN SELECT SUM(cost) FROM ad_unit_cost WHERE date_ >= '2019-03-01';
--  partitions: p3,p4,p5,p6          ← 裁掉了 p0,p1,p2  ✓

EXPLAIN SELECT SUM(cost) FROM ad_unit_cost WHERE unit_id = 123;
--  partitions: p0,p1,p2,p3,p4,p5,p6 ← 【全扫】         ✗
```

```
   这和最左前缀是一个道理（见《索引优化》第三章）：

   查询不带分区键  =  等于没分区，而且【比不分区更慢】
                     —— 要在每个分区上各查一遍，再把结果合并
```

**所以分区键的选择和分片键一样重要：它必须出现在绝大多数查询的 `WHERE` 里。**

## 十、分区表不解决什么

```
   ✓ 单表行数多导致的树变高
       每个分区一棵独立 B+ 树，1 亿行分 12 个分区 → 每棵树 833 万行
       树高可能从 4 层降回 3 层，每次查询省一次磁盘 IO
       ⤵ 依据《B+ 树原理 · 第四章》

   ✓ 按时间批量删除历史数据（DROP PARTITION）
   ✓ 冷热分离（不同分区放不同磁盘）

   ─────────────────────────────────────────────────

   ✗ 单机 CPU / 内存 / 磁盘 IO 上限   —— 所有分区还在【同一台机器】上
   ✗ 连接数上限                       —— 还是同一个实例
   ✗ 单点故障                         —— 机器挂了全挂
   ✗ 备份体积                         —— 还是要备整张表
   ✗ 唯一约束                         —— 反而被削弱了（第五节）
```

**一句话：分区表是「一台机器内部的整理」，不是「扩容」。**

# 第二部分：分库分表

## 十一、动手之前：先统计业务怎么用这张表

案例是 user 表，一张典型的"越长越胖"的表：

```sql
CREATE TABLE `user` (
  `user_id`         bigint(20)    NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  `user_name`       varchar(128)  NOT NULL DEFAULT '',
  `password`        varchar(128)  NOT NULL DEFAULT '',
  `email`           varchar(128)  NOT NULL DEFAULT '',
  `phone`           varchar(128)  NOT NULL DEFAULT '',
  `gender`          tinyint(4)    NOT NULL DEFAULT '0',
  `age`             tinyint(4)    NOT NULL DEFAULT '0',
  `id_card`         varchar(128)  NOT NULL DEFAULT '',
  `intro`           varchar(1024) NOT NULL DEFAULT '' COMMENT '个人信息',
  `user_company`    varchar(50)   NOT NULL DEFAULT '',
  `user_department` varchar(45)   NOT NULL DEFAULT '',
  `user_duty`       varchar(100)  NOT NULL DEFAULT '',
  `user_industry`   varchar(100)  NOT NULL DEFAULT '',
  `user_status`     int(10)       NOT NULL DEFAULT '0',
  `create_time`     datetime      NOT NULL DEFAULT '1970-01-01 00:00:00',
  `update_time`     datetime      NOT NULL DEFAULT '1970-01-01 00:00:00',
  PRIMARY KEY (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='用户信息表';
```

**这一节最重要的一句话是：「当你想做一件事之前，一定要把前因后果想清楚」。**

具体做法是先统计这张表的访问方式：

```
   99%  用 user_id 查用户信息（各个服务模块都要用户信息）
    1%  用 user_name / email / phone 登录
        （登录后 session 一直在，不需要重复登录）
```

这个统计**直接决定了分片键 = `user_id`**。

```
   分片键的选择是分库分表里最贵的一个决定 —— 选错了要重构。
   而它的依据不是拍脑袋，是【访问方式的统计】。
```

> 呼应《[数据表设计 · 1.1](数据表设计.md)》：「分片键必须出现在绝大多数查询的 `WHERE` 里，否则等于没分。」

## 十二、铁律：先垂直切分，再水平切分

课程把"为什么"留成了思考题。答案有三层，**第一层最有说服力**：

### 理由一：垂直拆分能直接把树变矮，可能根本不用水平拆

> ⤵ **依据**：《[数据表设计 · 1.1](数据表设计.md)》那张表——2000 万不是硬阈值，**是行宽的函数**。

| 单行大小 | 叶子每页行数 | 3 层 B+ 树能装 |
|---|---|---|
| 200 B | 80 | **约 1.1 亿行** |
| 1 KB | 16 | 约 2190 万行 |
| 4 KB | 4 | **约 550 万行** |

现在看 user 表：`intro varchar(1024)`、`user_duty`、`user_industry`、`id_card`、`user_company`……

```
   拆之前：一行 ≈ 1.5 KB  →  3 层树只能装【约 1500 万行】
   拆之后：user_base 一行 ≈ 200 B  →  3 层树能装【约 1.1 亿行】

              ↑ 光是把大字段挪走，容量就涨了 7 倍
                业务如果只有 3000 万用户，垂直拆完就【不需要水平拆了】
```

**这就是"先垂直"的硬道理：它可能让你根本不必付水平拆分的代价。**

### 理由二：垂直拆分几乎不改变查询方式

```
   垂直拆分后：SELECT ... FROM user_base WHERE user_id = ?   ← 还是普通 SQL
   水平拆分后：要引中间件、要全局 ID、要处理跨库事务和分页
```

### 理由三：水平拆分的复杂度是不可逆的

```
   一旦分片，JOIN / 事务 / 分页 / COUNT / 唯一约束 全部要重做（第十五节）
   而且很难退回去
```

```
   ┌──────────────────────────────────────────┐
   │  先垂直：成本低、可能就够了                │
   │  再水平：真不够时才付这个代价              │
   └──────────────────────────────────────────┘
```

## 十三、垂直切分：按「列」拆

按访问频率把 user 一劈为二：

```sql
-- 用户基本信息表：99% 的请求只碰这张，保持窄
CREATE TABLE `user_base` (
  `user_id`     bigint(20)   NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  `user_name`   varchar(128) NOT NULL DEFAULT '',
  `password`    varchar(128) NOT NULL DEFAULT '',
  `email`       varchar(128) NOT NULL DEFAULT '',
  `phone`       varchar(128) NOT NULL DEFAULT '',
  `gender`      tinyint(4)   NOT NULL DEFAULT '0',
  `age`         tinyint(4)   NOT NULL DEFAULT '0',
  `user_status` int(10)      NOT NULL DEFAULT '0',
  `create_time` datetime     NOT NULL DEFAULT '1970-01-01 00:00:00',
  `update_time` datetime     NOT NULL DEFAULT '1970-01-01 00:00:00',
  PRIMARY KEY (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='用户基本信息表';

-- 用户附加信息表：只有进详情页才读
CREATE TABLE `user_extra` (
  `user_id`         bigint(20)    NOT NULL COMMENT '关联 user_base.user_id',
  `id_card`         varchar(128)  NOT NULL DEFAULT '',
  `intro`           varchar(1024) NOT NULL DEFAULT '',
  `user_company`    varchar(50)   NOT NULL DEFAULT '',
  `user_department` varchar(45)   NOT NULL DEFAULT '',
  `user_industry`   varchar(100)  NOT NULL DEFAULT '',
  `user_duty`       varchar(100)  NOT NULL DEFAULT '',
  PRIMARY KEY (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='用户附加信息表';
```

三条要点：

```
   ① 两张表都是原表的【子集】，不重叠
   ② 两张表都有 user_id —— 它既是关联键，也是【未来的分片键】
      "理论上所有的表都需要定义 user_id"，说的就是这个
   ③ user_base 里不放"复杂信息"（大字段、低频字段）
```

### ⚠️ 这里原始 DDL 有一处要改

课程给的 `user_extra` 写的是：

```sql
`user_id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '自增主键',   -- ✗
```

**`user_extra.user_id` 不能自增。**它必须等于 `user_base` 里那个 `user_id`，两边各自增长就永远对不上了：

```
   user_base:   插入用户甲 → user_id = 1001
   user_extra:  插入用户甲 → user_id = 1（自己从 1 开始）
                              ↑ 关联关系直接断了
```

正确写法是：

```sql
`user_id` bigint(20) NOT NULL COMMENT '关联 user_base.user_id',
PRIMARY KEY (`user_id`)
```

> ⤵ **依据**：《[数据表设计 · 1.2](数据表设计.md)》里 1:1 的标准落地方式——
> 从表**主键即外键**，值由主表带过来（那里的 `user_profile` 就是 `PRIMARY KEY (user_id)` 且不自增）。

## 十四、水平切分：按「行」拆

选 **哈希取模**，`user_id` 是天然的划分依据。设计两个哈希函数：

```
   HASH_1(user_id) % 库数   →  落在哪个库
   HASH_2(user_id) % 表数   →  落在哪张表
```

按 1 亿注册用户估算：

```
   1 亿 ÷ 4 个库          = 每库 2500 万
   2500 万 ÷ 每库 5 张表  = 每表 500 万        ← 回到了舒适区
```

```
                        user_id = 12345
                              │
                    HASH_1(user_id) % 4
              ┌───────┬───────┴───────┬───────┐
              ▼       ▼               ▼       ▼
            db0     db1             db2     db3
                     │
              HASH_2(user_id) % 5
        ┌───────┬────┴───┬───────┬───────┐
        ▼       ▼        ▼       ▼       ▼
   user_base_0 ..._1  ..._2  ..._3  ..._4
        ↑ 每张 500 万行
```

### 补充一：分片数最好取 2 的幂

课程取的是 4 库 × 5 表。**5 在扩容时会很难受**：

```
   （以下为看清规律，设 HASH 为恒等函数，直接对 user_id 取模）

   %5 → %10   user_id=7  原本在表 2，扩容后到表 7   → 要迁
              user_id=12 原本在表 2，扩容后到表 2   → 不迁
              → 迁哪些、迁到哪，【几乎要全量重算】

   %4 → %8    x % 8 的结果，要么等于 x % 4，要么等于 x % 4 + 4
              → 每张表【一分为二】，只迁走一半
              → 迁移目标完全确定，可以逐表并行
```

```
   2 的幂的性质：  x % 8 ∈ { x%4 , x%4 + 4 }
                   所以「翻倍扩容」= 「每张表对半劈开」
```

所以工程上更常见的是 **4 库 × 8 表 = 32 片**，而且**一次分够**——分片数的二次调整代价极高。

### 补充二：分库分表后主键不能再用 `AUTO_INCREMENT`

上面 `user_base` 还留着 `AUTO_INCREMENT`。**单表时对，分成 20 张表后就错了**：

```
   user_base_0 自增到 1, 2, 3 ...
   user_base_1 也自增到 1, 2, 3 ...
        ↑ user_id 重复了，而它还是分片键，彻底乱套
```

必须换成全局 ID：

| 方案 | 特点 |
|---|---|
| **雪花 ID（Snowflake）** | `BIGINT`，高位是时间戳 → **趋势递增**，最常用 |
| **号段模式**（美团 Leaf） | 从 DB 批量取一段，本地发放，性能高 |
| ~~UUID~~ | **不要用**——随机值会导致大量页分裂 |

> ⤵ **依据**：《[B+ 树原理 · 第六章](B+树原理.md)》——主键必须**趋势递增**，否则每次插入都可能落在页中间引发页分裂。

还有一个**鸡生蛋问题**：

```
   user_id 是分片键 → 要先知道 user_id 才知道去哪个库
   但 user_id 由数据库自增生成 → 要先插入才知道

   ⟹ ID 必须在【应用层 / 发号服务】先拿到，不能依赖数据库生成
```

## 十五、那 1% 的登录查询怎么办

按 `user_id` 分片之后，这条 SQL 变得很尴尬：

```sql
SELECT * FROM user_base WHERE phone = '138xxxx';   -- WHERE 里没有分片键
```

```
   → 广播到全部 20 张表，20 次查询再归并
   → 量只有 1%，但登录是【不能慢】的接口
```

这是分片键选定之后的经典遗留问题，三种解法：

| 方案 | 做法 | 代价 |
|---|---|---|
| **映射表**（推荐） | 单独一张 `登录标识 → user_id` 的小表 | 多一次查询；要维护一致性 |
| **基因法** | 把 phone 的哈希"种"进 user_id 的低位，让两者算出同一分片 | 只能对**一个**字段生效；ID 生成变复杂 |
| **异构索引** | 同步一份到 ES / HBase，按 phone 建索引 | 多一套组件；最终一致 |

登录场景通常用**映射表**——小、简单、强一致：

```sql
CREATE TABLE `user_login_index` (
  `login_key` varchar(128) NOT NULL COMMENT '手机号 / 邮箱 / 用户名',
  `user_id`   bigint(20)   NOT NULL,
  PRIMARY KEY (`login_key`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

```
   登录流程：
   ① SELECT user_id FROM user_login_index WHERE login_key = '138xxxx'   ← 主键等值
   ② 用 user_id 路由到分片，查 user_base                                 ← 主键等值
        两次查询，都是主键等值，都很快
```

这张表还顺带解决了另一个问题——**它的主键天然保证了手机号/用户名全局唯一**，而分片后的 `user_base` 已经做不到这一点了。

> ⤵ 这正是《[乐观锁与悲观锁 · 5.6 坑四](../concurrency/乐观锁与悲观锁.md)》说的"分片后唯一约束只在片内有效"的标准解法：**用一张不分片的小表来承载全局唯一性**。

## 十六、分库分表之后失去了什么

| 失去的能力 | 为什么 | 怎么办 |
|---|---|---|
| `AUTO_INCREMENT` | 各表各自增会冲突 | 雪花 ID / 号段（十四节） |
| **跨库 JOIN** | 根本做不了 | 冗余字段；或分两次查在应用层拼 |
| **跨库事务** | 本地事务管不了多个库 | 最终一致：本地消息表 / Seata |
| **全局唯一约束** | 只在分片内有效 | 分片键进唯一键；或映射表兜底（十五节） |
| **深分页** | 见下 | 禁止深分页，改游标 `WHERE id > ?` |
| `COUNT` / `ORDER BY` / `GROUP BY` | 要跨片归并 | 汇总表；或走 ES / 数仓 |
| 外键 | 跨库外键无法工作 | 应用层保证 + 对账脚本（《数据表设计》已述） |

### 跨片分页为什么特别贵

```
   要取全局第 10001 ~ 10010 条（按 create_time 排序），共 20 个分片：

   ✗ 每片取 LIMIT 500, 1
        错的！全局前 10000 条可能集中在某一两个分片里

   ✓ 每片取 LIMIT 0, 10010
        20 × 10010 = 200200 条全部拉回内存排序，再取中间 10 条
        → 【分片越多越慢，页码越深越慢】
```

> ⤵ **依据**：《[B+ 树原理 · 5.4 为什么深分页很慢](B+树原理.md)》——单表深分页已经要扫 `offset + n` 行，
> 分片后是**再乘以分片数**。

## 十七、决策顺序：分库分表是最后手段

```
   ① 索引优化过了吗？
        很多"必须分库分表"其实是索引没建对   → 《索引优化》
   ② 冷数据能归档吗？
        只查最近 3 个月，历史挪到 xxx_history
   ③ 痛点只是"删历史数据慢"？
        → 分区表 + DROP PARTITION（第八节），到此为止
   ④ 读多写少扛不住？
        → 读写分离 + 缓存，不用分库
   ⑤ 表太宽 / 有大字段？
        → 【垂直拆分】，先做这个（第十二节）
   ⑥ 单表行数还是太多？
        → 水平分表（单库多表）
   ⑦ 单机 IO / CPU / 连接数到顶？
        → 分库（这才是真正需要多台机器的时候）
```

```
   ┌────────────────────────────────────────────────────────┐
   │  ①~⑤ 能解决的，就别走到 ⑥⑦。                            │
   │  水平分片带来的复杂度，会跟着这个系统一辈子。             │
   └────────────────────────────────────────────────────────┘
```

## 十八、对照速查

### 分区表 vs 分库分表

| | 分区表 | 分库分表 |
|---|---|---|
| 拆的是 | 一张表的物理存储 | 表、库、实例 |
| 应用感知 | **完全透明** | 要中间件 + 改造 |
| 跨机器 | **否** | 是 |
| 解决单机 IO/CPU | **否** | 是 |
| 解决单表树变高 | 是（能裁剪时） | 是 |
| 批量删历史 | **`DROP PARTITION` 秒级** | 直接 drop 整张表 |
| 唯一约束 | 被削弱（分区键必须进唯一键） | 被削弱（同理） |
| 运维复杂度 | 低 | **高** |
| 什么时候用 | 报表/日志表，要定期删历史 | 单机真的撑不住了 |

### RANGE 分区语法

```sql
-- 建表时分区
CREATE TABLE t (...) PARTITION BY RANGE (TO_DAYS(date_)) (
  PARTITION p1 VALUES LESS THAN (TO_DAYS('2019-02-01')),
  ...
);

-- 已有表加分区（全表重建，大表用 gh-ost）
ALTER TABLE t PARTITION BY RANGE (...) (...);

-- 加分区（只能加在高端；有 MAXVALUE 时会报 1481）
ALTER TABLE t ADD PARTITION (PARTITION p9 VALUES LESS THAN (...));

-- 劈开 MAXVALUE 分区（带 MAXVALUE 时用这个）
ALTER TABLE t REORGANIZE PARTITION pmax INTO (
  PARTITION p9   VALUES LESS THAN (...),
  PARTITION pmax VALUES LESS THAN (MAXVALUE));

-- 删分区（物理删数据，秒级）
ALTER TABLE t DROP PARTITION p3;

-- 只清空数据、保留分区
ALTER TABLE t TRUNCATE PARTITION p3;

-- 看分区
SELECT * FROM information_schema.PARTITIONS WHERE table_name = 't';

-- 看裁剪效果
EXPLAIN SELECT ... ;   -- 关注 partitions 列
```

### 分库分表 Checklist

```
   [ ] 统计过访问方式了吗？（哪个字段占了 90% 以上的查询）
   [ ] 分片键定了吗？它在绝大多数 WHERE 里吗？
   [ ] 先做垂直拆分了吗？做完还需要水平拆吗？
   [ ] 分片数是 2 的幂吗？一次分够了吗？
   [ ] 全局 ID 方案定了吗？（雪花 / 号段，不能用 UUID）
   [ ] ID 在应用层生成吗？（分片键不能依赖 DB 自增）
   [ ] 不带分片键的查询怎么办？（映射表 / 基因法 / ES）
   [ ] 唯一约束怎么保证？（映射表兜底）
   [ ] 跨库事务怎么处理？（最终一致）
   [ ] 分页/COUNT 的方案定了吗？
   [ ] 迁移方案：双写 → 迁存量 → 对账 → 灰度读 → 切流
```
