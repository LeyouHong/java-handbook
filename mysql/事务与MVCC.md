# MySQL 事务与 MVCC：读为什么可以不加锁

> 环境：MySQL 8.0 / InnoDB，默认隔离级别 **REPEATABLE READ**。本篇 SQL 为**示例**，未附实测输出。
>
> **一句话主线：MVCC 让「读」不用加锁——代价是每一行都要留着它的历史版本。**
>
> 理解了这一句，隔离级别、快照读、长事务的危害、乐观锁重试为什么会失败，全都是它的推论。

这一篇是其他几篇的**地基**：《[乐观锁与悲观锁](../concurrency/乐观锁与悲观锁.md)》里的"快照读"、"RR 下读不到新值"、"间隙锁"，《[分区表与分库分表](分区表与分库分表.md)》里的"长事务阻塞 purge"，都在这里定义。

## 一、ACID 分别由谁实现

ACID 常被当成四个并列的性质背，其实它们的地位不一样——**三个是手段，一个是结果**：

| | 含义 | 靠什么实现 |
|---|---|---|
| **A** 原子性 | 要么全做，要么全不做 | **undo log**（回滚） |
| **I** 隔离性 | 并发事务互不干扰 | **MVCC + 锁** |
| **D** 持久性 | 提交了就不会丢 | **redo log** |
| **C** 一致性 | 数据始终满足业务约束 | 上面三个 + 业务代码共同保证的**结果** |

```
   ┌────────────────────────────────────────────────┐
   │  A / I / D 是手段，C 是目的。                    │
   │  没有哪个单独的机制"负责一致性"——               │
   │  它是前三者加上你的业务逻辑一起达成的。           │
   └────────────────────────────────────────────────┘
```

> redo log 的细节见《[binlog · 第一节](binlog.md)》——那里讲了它和 binlog 的分工与两阶段提交。
> 本篇的主角是另一份日志：**undo log**。

## 二、并发会读出什么问题

隔离级别是为了防这三类异常。先把它们分清楚，尤其是后两个——**经常被混为一谈**。

### 2.1 脏读：读到了别人还没提交的数据

```
   事务 A                          事务 B
   ─────────────────────────────────────────────────
   BEGIN
   UPDATE t SET age=30 WHERE id=1
                                   BEGIN
                                   SELECT age → 30    ← 读到了未提交的值
   ROLLBACK                        
                                   ↑ B 读到的 30 从来【没有存在过】
```

### 2.2 不可重复读：同一行，两次读值不一样

```
   事务 A                          事务 B
   ─────────────────────────────────────────────────
   BEGIN
   SELECT age WHERE id=1 → 25
                                   UPDATE t SET age=30 WHERE id=1
                                   COMMIT
   SELECT age WHERE id=1 → 30      ← 同一个事务里，同一行，值变了
```

### 2.3 幻读：同一个范围，两次读行数不一样

```
   事务 A                          事务 B
   ─────────────────────────────────────────────────
   BEGIN
   SELECT COUNT(*) WHERE age>20 → 5 行
                                   INSERT INTO t VALUES(...age=25)
                                   COMMIT
   SELECT COUNT(*) WHERE age>20 → 6 行   ← 多出来一行"幻影"
```

### 2.4 后两者的区别

```
   ┌──────────────────────────────────────────────────────────┐
   │  不可重复读  针对【同一行的值】变了      —— 由 UPDATE 造成 │
   │  幻读        针对【满足条件的行数】变了  —— 由 INSERT 造成 │
   └──────────────────────────────────────────────────────────┘

   这个区别不是咬文嚼字：
   · 不可重复读，锁住那几行就能防住
   · 幻读，锁住已有的行【没用】—— 新行还没出生，锁不到它
     所以必须锁住"空隙"，这就是间隙锁存在的理由（第八节）
```

## 三、四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 谁在用 |
|---|---|---|---|---|
| READ UNCOMMITTED | ✗ | ✗ | ✗ | 几乎没人用 |
| **READ COMMITTED** | ✓ | ✗ | ✗ | Oracle / PostgreSQL 默认；**很多公司把 MySQL 也改成这个** |
| **REPEATABLE READ** | ✓ | ✓ | **✓（MySQL 特有）** | **MySQL 默认** |
| SERIALIZABLE | ✓ | ✓ | ✓ | 读也加锁，几乎不用 |

（✓ = 能防住）

两点要单独说：

```
   ① 按 SQL 标准，RR 是【不保证】防幻读的。
      但 MySQL 的 RR 靠【间隙锁】把当前读的幻读也堵上了（第八节），
      所以 MySQL 的 RR 比标准更强。

   ② 为什么很多公司改用 RC？
      · RR 的间隙锁范围大，并发高时锁冲突和死锁明显更多
      · RC 下不匹配的行锁会及时释放（见《乐观锁与悲观锁 3.3》）
      · 主流互联网业务能容忍不可重复读，换来的是更好的并发
      代价：改成 RC 后，依赖"可重复读"的业务逻辑要自己处理。
```

查看和设置：

```sql
SELECT @@transaction_isolation;             -- 会话级
SELECT @@global.transaction_isolation;      -- 全局

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

## 四、MVCC 的三个零件

MVCC = Multi-Version Concurrency Control，多版本并发控制。它靠三样东西工作。

### 4.1 零件一：每行上的两个隐藏列

> ⤵ **依据**：《[B+ 树原理 · 3.2](B+树原理.md)》——把叶子页里一行拆到字节时，主键后面紧跟着的就是这两个列。

```
   ┌──────────┬───────────────┬────────────────┬──────────┬────────┐
   │ 主键 id   │ trx_id (6B)   │ roll_ptr (7B)  │ salary   │ name   │
   └──────────┴───────────────┴────────────────┴──────────┴────────┘
                      ↑                ↑
             最后修改这行的         指向 undo log 里
             事务 id               上一个版本的指针
```

```
   trx_id     这一行是【谁】改的
   roll_ptr   这一行的【上一个版本】在哪
```

> 还有第三个隐藏列 `DB_ROW_ID`（6B），只在表既没有主键也没有非空唯一索引时才生成，和 MVCC 无关。

### 4.2 零件二：undo log 版本链

每次修改，旧值都被复制到 undo log，用 `roll_ptr` 串成一条链：

```
   数据页里的当前行                 undo log 里的历史版本
   ┌──────────────────┐
   │ age=30           │
   │ trx_id=99        │──roll_ptr──▶ ┌──────────────────┐
   │                  │              │ age=28           │
   └──────────────────┘              │ trx_id=80        │──▶ ┌──────────────┐
                                     └──────────────────┘    │ age=25       │
                                                              │ trx_id=52    │──▶ NULL
                                                              └──────────────┘

        最新                          较旧                       最旧
```

```
   ┌──────────────────────────────────────────────────────┐
   │  一行数据在物理上只有一份（在数据页里），                │
   │  但沿着 roll_ptr 能走出它的【全部历史】。               │
   │                                                        │
   │  所谓"多版本"，就是这条链。                             │
   └──────────────────────────────────────────────────────┘
```

### 4.3 零件三：ReadView（读视图）

有了版本链，还缺一个判据：**我该看链上的哪一个版本？**

ReadView 就是这个判据。它在**生成的那一刻**给整个数据库拍一张快照，记下四个东西：

```
   m_ids           生成这一刻，【还活跃（未提交）】的事务 id 列表
   min_trx_id      m_ids 里最小的那个
   max_trx_id      下一个将要分配的事务 id（注意：是"下一个"，不是最大的）
   creator_trx_id  我自己的事务 id
```

## 五、可见性判定：一条数轴讲完

拿到某个版本的 `trx_id`，按下面的规则判断它对我可见吗：

```
                    min_trx_id                      max_trx_id
   ─────────────────────┼──────────────────────────────┼─────────────▶ trx_id
        ① 全部可见       │      ② 要看在不在 m_ids 里     │   ③ 全部不可见
                        │                              │
     生成 ReadView 前    │   生成时可能还活着，也可能已提交  │  生成 ReadView 后
     就已经提交了        │                              │  才开启的事务
```

完整规则：

```
   trx_id == creator_trx_id   →  可见     （自己改的，当然看得见）
   trx_id <  min_trx_id       →  可见     （生成快照前就提交了）
   trx_id >= max_trx_id       →  不可见   （生成快照后才开启的事务）
   min_trx_id <= trx_id < max_trx_id：
        在 m_ids 里            →  不可见   （拍快照时它还没提交）
        不在 m_ids 里          →  可见     （拍快照时它已经提交了）
```

**判定不通过就顺着 `roll_ptr` 往下走一个版本，再判一次，直到找到可见的为止。**

### 一个完整的例子

```
   假设当前活跃事务：{80, 99}，下一个要分配的是 100
   我的事务 id = 99

   ReadView = { m_ids=[80,99], min=80, max=100, creator=99 }

   版本链：  age=30 (trx=99) → age=28 (trx=80) → age=25 (trx=52)
                  │                  │                 │
                  ▼                  ▼                 ▼
             trx==creator        在 m_ids 里        52 < min=80
             【可见】✓            【不可见】✗        【可见】✓

   结果：读到 age=30（自己刚改的）

   ────────────────────────────────────────────────────────────

   换一个事务来读，它的 id = 101，此时 80 已提交、99 已提交
   ReadView = { m_ids=[], min=101, max=102, creator=101 }

   版本链：  age=30 (trx=99)
                  │
                  ▼
             99 < min=101 【可见】✓   → 读到 age=30
```

## 六、RC 和 RR 的唯一区别

这是全篇最值得记的一句话：

```
   ┌──────────────────────────────────────────────────────────────┐
   │  READ COMMITTED    每次 SELECT 都【重新生成】一个 ReadView     │
   │  REPEATABLE READ   第一次快照读时生成，之后【一直复用】        │
   │                                                               │
   │  就这一个区别。其他所有差异都是它的推论。                       │
   └──────────────────────────────────────────────────────────────┘
```

推论一目了然：

```
   RC  每次都是新快照 → 能看到别人刚提交的 → 【不可重复读】
   RR  一直用老快照   → 看不到别人新提交的 → 【可重复读】
```

```
   事务 A（RR）                        事务 B
   ────────────────────────────────────────────────────────
   BEGIN
   SELECT age → 25      ← 【此刻生成 ReadView】
                                       UPDATE age=30; COMMIT
   SELECT age → 25      ← 复用老 ReadView，B 的修改不可见
   SELECT age → 25      ← 还是 25
   COMMIT

   同一个事务里读多少次都是 25 —— 这就是"可重复读"
```

> **注意时机**：RR 的 ReadView 是在**第一次快照读**时生成的，不是 `BEGIN` 时。
> 想让它在开启事务的瞬间就生成，用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

### ⤵ 这直接解释了乐观锁重试的那个坑

《[乐观锁与悲观锁 · 4.6](../concurrency/乐观锁与悲观锁.md)》说"重试不能写在 `@Transactional` 内部，否则必然失败"，原因现在清楚了：

```
   @Transactional
   public void deduct(long id) {
       for (int i = 0; i < 3; i++) {
           Product p = mapper.select(id);      // ← RR 下复用【同一个 ReadView】
           ...                                  //   别人提交的新 version 永远看不见
           if (rows == 1) return;               //   于是三次重试读到的是同一个旧值
       }                                        //   必然全部失败
   }
```

```
   所以重试必须【在事务外面】—— 每次重试开一个新事务，才会有新的 ReadView。
```

## 七、快照读 vs 当前读

MVCC 只作用于**快照读**。这是另一个高频误解点。

| | 语句 | 读什么 | 加锁吗 |
|---|---|---|---|
| **快照读** | 普通 `SELECT` | 走 ReadView 找可见版本 | **不加锁** |
| **当前读** | `SELECT ... FOR UPDATE` / `FOR SHARE` | **最新已提交版本** | **加锁** |
| **当前读** | `UPDATE` / `DELETE` / `INSERT` | **最新已提交版本** | **加锁** |

最后一行最容易被忽略：

```
   ┌──────────────────────────────────────────────────────────┐
   │  UPDATE / DELETE 本身就是【当前读】。                      │
   │  它们读的是最新值，不是你的快照。                          │
   └──────────────────────────────────────────────────────────┘
```

为什么必须这样？想想反例：

```
   如果 UPDATE 也读快照：

   事务 A（快照里 age=25）              事务 B
   ──────────────────────────────────────────────────
                                        UPDATE age=30; COMMIT
   UPDATE t SET age = age + 1
        ↑ 如果基于快照的 25 算，就写成 26
          → B 的修改被【凭空覆盖】了，丢失更新
```

所以当前读必须读最新值。这也解释了另一件事：

```
   ⤵ 《乐观锁与悲观锁 · 4.3》的条件更新为什么安全：

   UPDATE product SET stock = stock - 1 WHERE id=100 AND stock > 0;

   它是当前读 → 读到的 stock 是最新值，不是快照值
   加上 InnoDB 会在这条语句内部加 X 锁完成"比较 + 写入"
   → 不会基于过时数据做判断
```

## 八、RR 是怎么防住幻读的

分两种情况，机制完全不同：

### 8.1 快照读的幻读：MVCC 天然解决

```
   一直复用同一个 ReadView → 别人新 INSERT 的行 trx_id >= max_trx_id
   → 判定为不可见 → 根本看不到新行 → 没有幻读
```

### 8.2 当前读的幻读：靠间隙锁

当前读要读最新数据，MVCC 帮不上忙。这时靠**锁住空隙**：

```sql
SELECT * FROM t WHERE age > 20 FOR UPDATE;
```

```
   现有数据：age = 10, 25, 40

   ────●────────────●────────────●────────▶ age
      10           25           40

   RR 下不只锁住 25 和 40 这两行，
   还锁住了 (20, 25]、(25, 40]、(40, +∞) 这些【区间】
        ↑ 别人想 INSERT 一行 age=30 → 【被间隙锁挡住，只能等】
        → 再查一次，行数不会变 → 没有幻读
```

这就是《[乐观锁与悲观锁 · 5.2](../concurrency/乐观锁与悲观锁.md)》里说的"RR 下的间隙锁确实能挡住重复插入"。

### 8.3 但幻读并没有被彻底消灭

快照读和当前读**混用**时，依然能造出幻读：

```
   事务 A（RR）                        事务 B
   ────────────────────────────────────────────────────────
   BEGIN
   SELECT COUNT(*) WHERE age>20 → 5    ← 快照读，生成 ReadView
                                       INSERT age=25; COMMIT
   SELECT COUNT(*) WHERE age>20 → 5    ← 快照读，还是 5 ✓

   SELECT COUNT(*) WHERE age>20
     FOR UPDATE                → 6     ← 【当前读】，看到了 B 插的行！
                                          幻读出现了
```

```
   结论：RR 挡住了绝大多数幻读，但「先快照读、后当前读」这个组合是漏的。
        真要严格，只能上 SERIALIZABLE，或者一开始就用当前读。
```

## 九、长事务：MVCC 的账单

MVCC 的所有好处都建立在"旧版本还留着"上。**谁来决定旧版本什么时候能扔？**

答案是：**只要还有任何一个 ReadView 可能用到它，就不能扔。**

于是长事务的危害全部来自这一条：

```
   ┌─ ① undo log 无法回收 ──────────────────────────────────┐
   │   一个跑了 3 小时的事务，它的 ReadView 一直活着，        │
   │   → 这 3 小时里所有被修改行的旧版本【全都不能删】        │
   │   → purge 线程干瞪眼，undo 表空间疯涨                    │
   │   → 磁盘被吃满                                          │
   └─────────────────────────────────────────────────────────┘

   ┌─ ② 版本链变长 ────────────────────────────────────────┐
   │   一个热点行被改了 1000 次 → 版本链 1000 长              │
   │   → 老事务读它要沿链走很多步才找到可见版本               │
   │   → 查询越来越慢                                        │
   └─────────────────────────────────────────────────────────┘

   ┌─ ③ 锁持有时间长 ──────────────────────────────────────┐
   │   事务里加的行锁要到 COMMIT 才放                         │
   │   → 别人一直等（见《乐观锁与悲观锁 3.3 坑三》）           │
   └─────────────────────────────────────────────────────────┘

   ┌─ ④ 主从延迟 ──────────────────────────────────────────┐
   │   大事务的 binlog 要等提交才整批写出、整批传给从库       │
   └─────────────────────────────────────────────────────────┘
```

> **purge 线程**就是负责清理不再需要的 undo 版本的后台线程。
> 《[分区表与分库分表 · 第八节](分区表与分库分表.md)》说"`DELETE` 大量数据会 undo 暴涨、长事务阻塞 purge"，指的就是这件事。

### 怎么找出长事务

```sql
-- 当前运行超过 60 秒的事务
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec,
       trx_mysql_thread_id, trx_query
  FROM information_schema.innodb_trx
 WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
 ORDER BY trx_started;
```

```sql
-- 看 undo 有没有堆积（History list length）
SHOW ENGINE INNODB STATUS\G
-- 在 TRANSACTIONS 段里找 "History list length"
-- 这个数字持续增长且下不去，基本就是有长事务卡着 purge
```

### 怎么防

```
   [ ] 把 autocommit 关掉的习惯改回来（SET autocommit=1）
   [ ] 事务里不要有 RPC / HTTP / 大循环（⤵《乐观锁与悲观锁 3.3 坑三》）
   [ ] 大批量 DELETE/UPDATE 拆成小批次，每批一个事务
   [ ] 监控 innodb_trx，对超时事务告警
   [ ] 设 MAX_EXECUTION_TIME 限制单条 SQL
```

## 十、把一个事务从头看到尾

```sql
BEGIN;                                    -- ① 只是标记开始，还没分配 trx_id
SELECT * FROM t WHERE id = 1;             -- ② 【第一次快照读】，生成 ReadView
                                          --    只读事务，仍未分配真正的 trx_id
UPDATE t SET age = 30 WHERE id = 1;       -- ③ 当前读 + 加 X 锁 + 分配 trx_id
                                          --    旧值写入 undo，roll_ptr 指过去
                                          --    改动写 redo log buffer
COMMIT;                                   -- ④ 两阶段提交：
                                          --    redo(prepare) → binlog → redo(commit)
                                          --    释放所有锁
                                          --    ReadView 销毁，它占的旧版本可被 purge
```

```
   几个容易记错的点：

   · trx_id 是【第一次真正修改数据时】才分配的，不是 BEGIN 时
     （所以只读事务不消耗事务 id）
   · ReadView 是【第一次快照读时】生成的，也不是 BEGIN 时
   · 锁全部在 COMMIT 时释放，中间不会提前放
```

## 十一、速查

### 隔离级别

```
   ┌────────────────────────────────────────────────────────────┐
   │  RU  READ UNCOMMITTED  不防任何异常，别用                    │
   │  RC  READ COMMITTED    每次 SELECT 新建 ReadView             │
   │                        防脏读；并发好；很多公司选它           │
   │  RR  REPEATABLE READ   首次快照读建 ReadView 后复用【默认】   │
   │                        防脏读 + 不可重复读 + 大部分幻读       │
   │  SR  SERIALIZABLE      读也加锁，串行                        │
   └────────────────────────────────────────────────────────────┘
```

### MVCC 三件套

```
   隐藏列       trx_id（谁改的）+ roll_ptr（上个版本在哪）
   undo 版本链  沿 roll_ptr 串起来的历史
   ReadView     m_ids / min_trx_id / max_trx_id / creator_trx_id

   可见性：  ==creator → 可见
             < min     → 可见
             >= max    → 不可见
             中间：在 m_ids 里不可见，不在则可见
             不可见就沿 roll_ptr 往下找
```

### 快照读 / 当前读

```
   快照读   普通 SELECT                          走 MVCC，不加锁
   当前读   SELECT...FOR UPDATE / FOR SHARE      读最新，加锁
            UPDATE / DELETE / INSERT             ← 【别忘了这一行】
```

### 排查命令

```sql
SELECT @@transaction_isolation;                    -- 当前隔离级别
SELECT * FROM information_schema.innodb_trx;       -- 正在跑的事务
SHOW ENGINE INNODB STATUS\G                        -- History list length
```
