# 事务与 MVCC：读数据为什么可以不用等

> 环境：MySQL 8.0 / InnoDB。本篇 SQL 为**示例**，未附实测输出。
>
> 这篇不先讲 ACID，也不先背隔离级别。我们从**一个具体的麻烦**出发，
> 一步步把 MVCC 自己推导出来——你会发现每个零件都是被上一步的问题逼出来的。
>
> 读完你应该能回答：**为什么读不用加锁、RR 和 RC 到底差在哪、长事务为什么危险。**

---

## 我们的麻烦

一张商品表，就一行：

```
   id = 1,  stock = 100
```

现在两个人同时操作它：

```
   小明：要读这行（比如展示库存）
   小红：要改这行（比如扣库存）
```

**问题很简单：小明读的时候，小红正在改。小明该看到什么？**

这个问题的答案，就是整篇笔记。

---

## 第 1 步：最笨的办法——所有人排队

最容易想到的办法是加锁：

```
   谁要碰这一行，先拿锁。拿不到就等。
```

```
   小红拿到锁 → 改 stock: 100 → 99 → 提交 → 放锁
                                          ↓
   小明一直在等 ─────────────────────────→ 拿到锁 → 读到 99
```

**这是对的**，小明绝不会读到半成品。

但代价大到无法接受：

```
   ┌──────────────────────────────────────────────────────────┐
   │  一个商品详情页，每秒几千次【读】。                        │
   │  只要有一个人在下单（写），这几千次读【全部排队】。         │
   │                                                           │
   │  而现实是：读远远多于写。                                  │
   │  让绝大多数的读去等极少数的写 —— 这个买卖太亏了。          │
   └──────────────────────────────────────────────────────────┘
```

所以要想办法让**读不用等**。

---

## 第 2 步：一个关键观察

再看小明的需求。他到底要什么？

```
   ✗ 小明【不需要】最新的数据
      —— 商品页显示 100 还是 99，差别不大

   ✓ 小明需要的是【一份不会在他眼皮底下变来变去的数据】
      —— 不能读到一半，stock 突然从 100 变成 99
```

这个区别很关键：

```
   ┌──────────────────────────────────────────────────────────┐
   │  「最新」和「一致」是两回事。                              │
   │                                                           │
   │  小明要的是【一致】，不是【最新】。                        │
   │  而我们之前用锁，是为了保证【最新】—— 用力过猛了。         │
   └──────────────────────────────────────────────────────────┘
```

那能不能给小明一份**旧的、但完整的**数据？

---

## 第 3 步：那就别把旧值扔掉

小红改数据时，我们习惯性地想成"把 100 覆盖成 99"。

换个做法：**别覆盖，把旧值留一份。**

```
   改之前：            stock = 100

   小红改成 99 时：
                       stock = 99      ← 新值，给以后的人看
                          │
                          ↓ 旧值搬到别处存着
                       stock = 100     ← 旧值，给小明看
```

于是：

```
   小红在写新值    ┐
                  ├─ 【互不干扰，谁都不用等谁】
   小明在读旧值    ┘
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  这就是 MVCC 的全部动机。                                  │
   │                                                           │
   │  MVCC = Multi-Version Concurrency Control                 │
   │         多  版本   并发控制                                │
   │                                                           │
   │  「多版本」指的就是：一行数据同时留着好几个历史版本。       │
   └──────────────────────────────────────────────────────────┘
```

接下来的每一步，都是在把这个想法落地时遇到的具体问题。

---

## 第 4 步：旧值放哪、怎么找回来

### 问题 ①：旧值存到哪去？

存到一个专门的地方，叫 **undo log**（回滚日志）。

```
   名字里的"回滚"是它的另一个用途 ——
   事务要撤销时，就是靠它把数据恢复回去。
   这里我们用的是它的第二个身份：【历史版本的仓库】。
```

### 问题 ②：怎么从新值找到旧值？

给每一行加一个指针，指向它的上一个版本：

```
   数据页里的当前行              undo log 里的历史
   ┌──────────────┐
   │ stock = 99   │
   │ 指针 ────────┼──────────▶ ┌──────────────┐
   └──────────────┘            │ stock = 100  │
                               │ 指针 ────────┼──▶ 再往前的版本…
                               └──────────────┘
```

这个指针叫 `roll_ptr`。串起来的这条链叫**版本链**。

### 问题 ③：怎么知道每个版本是谁改的？

再加一个字段，记下**是哪个事务改的**：

```
   每个事务在开始改数据时，会拿到一个【递增的编号】，叫事务 id。
   把它记在版本上。
```

```
   ┌──────────────┐
   │ stock = 99   │
   │ 改它的是 101 │  ← trx_id
   │ 指针 ────────┼──▶ ┌──────────────┐
   └──────────────┘    │ stock = 100  │
                       │ 改它的是  87 │
                       │ 指针 ────────┼──▶ ...
                       └──────────────┘
```

### 于是每一行长这样

```
   ┌────────┬──────────┬──────────┬─────────┐
   │  id=1  │trx_id=101│roll_ptr  │stock=99 │
   └────────┴──────────┴──────────┴─────────┘
              └────── 这两个是 InnoDB 偷偷加的，
                      你 SELECT * 看不到它们 ──────┘
```

```
   零件齐了：
     trx_id     这个版本是谁改的
     roll_ptr   上一个版本在哪
     undo log   旧版本存在哪
```

现在小明可以顺着链条往回走了。**但走到哪一个才停？**

这是最难的一步。

---

## 第 5 步：我该读版本链上的哪一个（核心）

### 5.1 先试一个朴素的想法

```
   小明的事务 id 是 105。
   直觉：读 trx_id 比 105 小的、最新的那个版本。
        （因为编号小 = 比我早开始 = 应该已经完成了）
```

看起来很合理。但它是错的。

### 5.2 反例：编号小 ≠ 已经提交

```
   事务 100：开始，把 stock 改成 50，【但还没提交】（还在犹豫要不要下单）
   事务 105：开始，来读 stock

   按朴素想法：100 < 105  →  可见  →  小明读到 50

   然后事务 100 反悔了，回滚。
   → 小明读到的 50 【从来没有真正存在过】
```

这就是**脏读**——读到了别人还没提交的数据。

```
   ┌──────────────────────────────────────────────────────────┐
   │  问题的根源：                                              │
   │  事务 id 只说明"谁先开始"，【完全不说明"谁先结束"】。       │
   │                                                           │
   │  事务 100 可能跑 3 小时还没提交，                          │
   │  事务 104 可能 1 毫秒就提交了。                            │
   └──────────────────────────────────────────────────────────┘
```

### 5.3 那真正该问的是什么

```
   ┌──────────────────────────────────────────────────────────┐
   │                                                           │
   │   改这个版本的那个事务，                                   │
   │   在【我开始的那一刻】，提交了没有？                        │
   │                                                           │
   │       提交了       →  我看得见                             │
   │       还没提交     →  我看不见                             │
   │       我开始之后    →  我看不见                             │
   │       才出现的                                             │
   │                                                           │
   └──────────────────────────────────────────────────────────┘
```

**整个可见性判断，只有这一句话。** 后面的一切都是为了回答它。

### 5.4 怎么回答：开始时拍一张照

事务一开始（准确说是第一次读的时候），做一件事：

```
   把【此刻还没提交的事务】记成一份名单。
```

```
   小明（事务 105）开始时，数据库里的情况：
       事务 87   已提交 ✓
       事务 100  【还在跑，没提交】
       事务 103  【还在跑，没提交】
       事务 104  已提交 ✓

   小明记下的名单：{ 100, 103 }
              ↑ 就这么简单，一份"当时谁还没干完"的清单
```

有了这份名单，5.3 的问题就能回答了：

```
   看到一个版本，它的 trx_id 是 X：

   ┌─ X 就是我自己           →  看得见（自己改的当然看得见）
   ├─ X 【在名单里】          →  看不见（我开始时它还没提交）
   ├─ X 比我开始时见过的      →  看不见（我开始之后才出现的事务）
   │   所有 id 都大
   └─ 其他情况               →  看得见（我开始前就提交了）
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  这份名单，在 MySQL 源码里叫 ReadView（读视图）。          │
   │                                                           │
   │  别被这个名字唬住 —— 它就是一份                            │
   │  「我开始那一刻，谁还没提交」的清单。                       │
   └──────────────────────────────────────────────────────────┘
```

### 5.5 完整走一遍

```
   小明是事务 105，名单 = { 100, 103 }

   版本链：
   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
   │ stock = 50   │──▶│ stock = 99   │──▶│ stock = 100  │
   │ trx_id = 100 │   │ trx_id = 103 │   │ trx_id = 87  │
   └──────────────┘   └──────────────┘   └──────────────┘
```

一个一个判：

```
   ① stock=50, trx_id=100
        100 在名单里 → 我开始时它还没提交 → 【看不见】，往下走

   ② stock=99, trx_id=103
        103 在名单里 → 同上 → 【看不见】，往下走

   ③ stock=100, trx_id=87
        87 不在名单里，也不比我大 → 我开始前就提交了 → 【看得见】✓

   小明读到 stock = 100。
```

```
   注意这个结果：数据库里现在的"真实最新值"是 50，
   但小明读到的是 100 —— 【这不是 bug，这正是我们要的】。

   小明拿到的是一份「他开始那一刻」的完整快照。
   这种读法就叫【快照读】。
```

### 5.6 关于那两个"加速用"的数字

你在别处会看到 ReadView 有四个字段。除了名单和"我自己是谁"，还有两个数字：

```
   名单里最小的 id      —— 比它还小的，肯定早就提交了，不用翻名单
   下一个待分配的 id    —— 比它大的，肯定是我之后才出现的，不用翻名单
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  这两个数字【不是规则】，只是【加速手段】——                │
   │  让绝大多数版本一眼就能判定，不用真的去遍历名单。          │
   │                                                           │
   │  规则永远只有 5.3 那一句话。                               │
   └──────────────────────────────────────────────────────────┘
```

所以不用背四个字段。记住"一份名单"就够了。

## 第 6 步：名单什么时候拍——这就是隔离级别

现在问一个问题：小明的事务里读了三次，**这份名单要不要重新拍？**

两种选择，各有道理：

```
   ┌─ 选择 A：每次读都【重新拍一张】 ──────────────────────────┐
   │                                                            │
   │   好处：能看到别人最新提交的数据，比较"新鲜"                │
   │   坏处：同一个事务里读两次，结果【可能不一样】              │
   └────────────────────────────────────────────────────────────┘

   ┌─ 选择 B：只在第一次读时拍，之后【一直用那张】 ────────────┐
   │                                                            │
   │   好处：整个事务里看到的世界是【凝固的】，读几次都一样      │
   │   坏处：看不到别人在此期间提交的新数据                      │
   └────────────────────────────────────────────────────────────┘
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  选择 A 就是  READ COMMITTED（读已提交，简称 RC）          │
   │  选择 B 就是  REPEATABLE READ（可重复读，简称 RR）         │
   │                                                           │
   │  这两个隔离级别的区别，【就只有这一个】：                   │
   │  名单是每次重拍，还是只拍一次。                            │
   └──────────────────────────────────────────────────────────┘
```

### 看一遍差别

```
   小明的事务                          小红
   ─────────────────────────────────────────────────────────
   BEGIN
   读 stock  →  100        ← 拍名单
                                       改 stock = 99，提交
   读 stock  →  ？
```

```
   RC（每次重拍）：
      第二次读时重新拍名单，此时小红已提交、不在名单里
      → 读到 99      ← 同一个事务里，两次读的结果【不一样】

   RR（只拍一次）：
      还用第一次那张名单，小红当时在名单里
      → 读到 100     ← 两次一样，"可重复读"这个名字就是这么来的
```

RC 里那个"两次读不一样"的现象，有个专门的名字叫**不可重复读**。

```
   现在你应该能看出来：
   「不可重复读」不是什么高深的概念，
   它就是【每次重拍名单】这个选择的必然结果。
```

### MySQL 默认是 RR

```
   MySQL 默认 REPEATABLE READ
   Oracle / PostgreSQL 默认 READ COMMITTED

   不少公司会把 MySQL 也改成 RC，理由主要是并发更好
   （RR 为了防幻读会加更多锁，见第 8 步）。
   代价是要接受"同一事务里两次读可能不同"。
```

查看和修改：

```sql
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### ⤵ 这解释了一个实际的坑

如果你写过这样的重试代码：

```java
@Transactional                        // ← 事务在外面
public void deduct(long id) {
    for (int i = 0; i < 3; i++) {     // ← 重试在里面
        Product p = mapper.select(id);              // 重新读
        int rows = mapper.updateWithVersion(id, ..., p.getVersion());
        if (rows == 1) return;
        // 失败了，再来一次
    }
    throw new BizException("重试失败");
}
```

**这段代码在 RR 下必然失败三次。**

```
   三次重试都在【同一个事务】里 → 用的是【同一张名单】
   → 别人提交的新 version，这三次都看不见
   → 每次都读到同一个旧值，每次都失败
```

```
   正确写法：重试放在事务【外面】，每次重试开一个新事务
            —— 新事务才有新名单。
```

> 完整的重试写法见《[乐观锁与悲观锁 · 4.6](../concurrency/乐观锁与悲观锁.md)》。

## 第 7 步：那"写"呢？写不能读旧值

小明是读，没问题。但小红要**改**数据，她能基于旧值改吗？

```
   假设小红的名单里，stock 还是 100（因为有别人正在改）

   小红执行：UPDATE product SET stock = stock - 1

   如果基于名单里的 100 算：100 - 1 = 99，写回 99
        ↓
   但别人刚刚已经把它改成 50 了
        ↓
   写回 99 → 【别人的修改凭空消失了】
```

这叫**丢失更新**，是绝对不能接受的。

所以：

```
   ┌──────────────────────────────────────────────────────────┐
   │  改数据时，必须读【最新的真实值】，不能读快照。            │
   │                                                           │
   │  而要保证读到的确实是最新的、且不会立刻被别人改掉，        │
   │  就【必须加锁】。                                          │
   └──────────────────────────────────────────────────────────┘
```

于是 MySQL 里有了两种读：

| | 哪些语句 | 读什么 | 加锁吗 |
|---|---|---|---|
| **快照读** | 普通 `SELECT` | 按名单找可见版本 | **不加锁** |
| **当前读** | `UPDATE` / `DELETE` / `INSERT` | **最新已提交值** | **加锁** |
| **当前读** | `SELECT ... FOR UPDATE`<br>`SELECT ... FOR SHARE` | **最新已提交值** | **加锁** |

第二行最容易被忽略：

```
   ┌──────────────────────────────────────────────────────────┐
   │  UPDATE 和 DELETE 本身就是当前读。                        │
   │                                                           │
   │  哪怕在 RR 事务里，UPDATE 读到的也是最新值，不是你的快照。 │
   └──────────────────────────────────────────────────────────┘
```

第三行是给"我想读最新值"准备的：

```sql
SELECT stock FROM product WHERE id = 1 FOR UPDATE;   -- 排他，别人不能读也不能改
SELECT stock FROM product WHERE id = 1 FOR SHARE;    -- 共享，别人能读不能改
```

```
   所以"读不加锁"这句话要说全：
   【普通的 SELECT】不加锁。
   一旦你要改，或者显式要求读最新值，锁就回来了。
```

## 第 8 步：还剩最后一个问题——幻读

到这里，"同一行数据"的问题都解决了。但还有一类问题：

```
   小明（RR 事务）：
      SELECT COUNT(*) FROM product WHERE price > 50   →  5 件

   小红：
      INSERT 一件 price = 60 的商品，提交

   小明再查：
      SELECT COUNT(*) FROM product WHERE price > 50   →  ？
```

### 8.1 快照读的情况：MVCC 自己就解决了

```
   小红的事务 id 比小明大 → "我开始之后才出现的" → 看不见
   → 小明还是查到 5 件 ✓
```

### 8.2 但当前读呢

```sql
SELECT COUNT(*) FROM product WHERE price > 50 FOR UPDATE;   -- 当前读
```

当前读要看**最新值**，MVCC 帮不上忙。小明会看到 6 件——凭空多出来一行，像幻觉一样。

**这就是幻读。**

### 8.3 幻读和不可重复读的区别

```
   ┌──────────────────────────────────────────────────────────┐
   │  不可重复读   同一行的【值】变了      —— UPDATE 造成       │
   │  幻读         满足条件的【行数】变了  —— INSERT 造成       │
   └──────────────────────────────────────────────────────────┘
```

这个区别不是咬文嚼字，它决定了解法：

```
   不可重复读：把那几行【锁住】就行了

   幻读：      锁住已有的行【没用】——
              新插入的那一行还不存在，你锁不住一个不存在的东西
```

### 8.4 所以 RR 多加了一种锁：锁住"空隙"

```
   现有数据 price = 10, 60, 90

   ────●────────────●────────────●────────▶ price
       10           60           90

   小明查 price > 50 并加锁时，RR 不只锁住 60 和 90 这两行，
   还锁住了【它们之间和之后的空隙】：

   ────●────────────●▓▓▓▓▓▓▓▓▓▓▓●▓▓▓▓▓▓▓▓▶
       10           60           90

   小红想插入 price = 70 → 落在被锁的空隙里 → 【被挡住，只能等】
   → 小明再查，行数不会变 → 没有幻读 ✓
```

这种锁叫**间隙锁**。它是 MySQL 的 RR 比 SQL 标准更强的地方——标准里 RR 是不保证防幻读的。

> 间隙锁的完整形态、以及它带来的死锁问题，见《[InnoDB 锁](InnoDB锁.md)》。

### 8.5 一个诚实的说明：幻读没有被彻底消灭

快照读和当前读**混着用**的时候，还是能造出幻读：

```
   小明（RR）                          小红
   ─────────────────────────────────────────────────────
   BEGIN
   SELECT COUNT(*) ... → 5             ← 快照读，此时拍名单
                                       INSERT 一行; COMMIT
   SELECT COUNT(*) ... → 5             ← 快照读，还是 5  ✓

   SELECT COUNT(*) ... FOR UPDATE → 6  ← 【当前读】，看到了新行！
```

```
   原因：第一次快照读时拍了名单，但没加任何锁（快照读不加锁）
        → 小红的 INSERT 畅通无阻
        → 后来才用当前读，已经晚了

   要严格避免：要么全程用当前读，要么上 SERIALIZABLE（读也加锁，基本不用）。
```

## 第 9 步：旧版本什么时候能扔——长事务为什么危险

MVCC 的一切好处，都建立在"旧版本还留着"上。那**旧版本什么时候能删？**

```
   ┌──────────────────────────────────────────────────────────┐
   │  只要还有【任何一份名单】可能用到它，就不能删。            │
   └──────────────────────────────────────────────────────────┘
```

负责清理的后台线程叫 **purge**。

现在看一个跑了 3 小时的事务：

```
   它在 3 小时前拍了一张名单，而且这张名单一直有效。
        ↓
   这 3 小时里，所有被修改过的行，它们的旧版本【都可能被这张名单用到】
        ↓
   purge 一个都不敢删
```

后果是连锁的：

```
   ① undo log 疯涨
      3 小时的历史版本全堆着 → 磁盘被吃满

   ② 版本链变长
      一个热点行被改了 1000 次 → 链上挂着 1000 个版本
      → 别人读它要沿着链走很多步才找到可见的那个 → 查询越来越慢

   ③ 锁一直不放
      事务里加的锁要到 COMMIT 才释放 → 别人一直等

   ④ 主从延迟
      大事务的日志要等提交才整批传给从库
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  「长事务是万恶之源」这句话，根源就在这里：                │
   │  它让整个数据库的历史版本【都扔不掉】。                    │
   └──────────────────────────────────────────────────────────┘
```

### 怎么查

```sql
-- 跑了超过 60 秒的事务
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS 已运行秒数,
       trx_mysql_thread_id, trx_query
  FROM information_schema.innodb_trx
 WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
 ORDER BY trx_started;
```

```sql
-- 看积压了多少个待清理的旧版本
SHOW ENGINE INNODB STATUS\G
-- 在 TRANSACTIONS 段找 "History list length"
-- 这个数字一直涨、下不去 → 基本就是有长事务卡着 purge
```

### 怎么防

```
   [ ] 事务里【绝对不要】调外部接口（RPC / HTTP / 发消息）
       —— 对方超时 5 秒，你的事务就卡 5 秒
   [ ] 大批量 DELETE / UPDATE 拆成小批，每批一个事务
   [ ] 别把 autocommit 关掉（关掉后每条语句都隐式开事务，很容易忘了提交）
   [ ] 监控 innodb_trx，超时告警
```

## 第 10 步：回头看 ACID

到这里所有机制都出现过了，现在这张表才有意义：

| | 含义 | 靠什么实现 | 在本篇哪一步出现的 |
|---|---|---|---|
| **A** 原子性 | 要么全做，要么全不做 | **undo log**（回滚） | 第 4 步（它的另一个身份） |
| **I** 隔离性 | 并发事务互不干扰 | **MVCC + 锁** | 第 3~8 步（整篇的主线） |
| **D** 持久性 | 提交了就不会丢 | **redo log** | 本篇没讲，见下 |
| **C** 一致性 | 数据始终满足业务约束 | 上面三个 + 你的业务代码 | —— |

```
   ┌──────────────────────────────────────────────────────────┐
   │  A / I / D 是【手段】，C 是【目的】。                      │
   │                                                           │
   │  没有哪个机制单独"负责一致性"——                            │
   │  它是前三者加上你的业务逻辑一起达成的结果。                │
   └──────────────────────────────────────────────────────────┘
```

> redo log 是另一份日志，专门管"提交了就不丢"。
> 它和 undo log 完全是两回事：**undo 存旧值用来回滚和读快照，redo 存改动用来崩溃后重做**。
> 详见《[binlog · 1.3](binlog.md)》。

## 第 11 步：把一个事务从头看到尾

```sql
BEGIN;                                 -- ① 只是打个标记，
                                       --    此时【还没有】事务 id，也没有名单

SELECT * FROM product WHERE id = 1;    -- ② 第一次快照读
                                       --    → 【在这里拍名单】
                                       --    → 仍然没有事务 id（只读不消耗 id）

UPDATE product SET stock = 99          -- ③ 当前读：读最新值 + 加锁
 WHERE id = 1;                         --    → 【在这里才分配事务 id】
                                       --    → 旧值写进 undo，roll_ptr 指过去

COMMIT;                                -- ④ 释放所有锁
                                       --    名单作废，它护着的旧版本可以被 purge 了
```

```
   三个容易记错的时间点：

   · 事务 id  在【第一次真正改数据】时才分配（不是 BEGIN 时）
   · 名单     在【第一次快照读】时才拍（也不是 BEGIN 时）
   · 锁       全部在 COMMIT 时释放，中途不会提前放
```

> 想让名单在开启事务的瞬间就拍，用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

## 速查

### 一句话版本

```
   ┌────────────────────────────────────────────────────────────┐
   │  MVCC：改数据时别扔掉旧值，读的人去读旧值 → 读写不用互相等  │
   │                                                             │
   │  该读哪个旧值？ 事务开始时拍一份「谁还没提交」的名单，       │
   │                 名单里的人改的版本，我都看不见。             │
   │                                                             │
   │  RC vs RR：    名单每次读都重拍（RC），还是只拍一次（RR）。  │
   │                就这一个区别。                                │
   └────────────────────────────────────────────────────────────┘
```

### 三个零件

```
   trx_id      这个版本是谁改的
   roll_ptr    上一个版本在哪
   undo log    旧版本存在哪
```

### 可见性规则

```
   看到一个版本，trx_id = X：

     X 是我自己          →  看得见
     X 在名单里          →  看不见   （我开始时它还没提交）
     X 比我开始时         →  看不见   （我开始之后才出现的）
       见过的都大
     其他                →  看得见   （我开始前就提交了）

   看不见就顺着 roll_ptr 往前找下一个。
```

### 快照读 / 当前读

```
   快照读   普通 SELECT                        按名单找版本，不加锁
   当前读   UPDATE / DELETE / INSERT           读最新值，加锁
            SELECT ... FOR UPDATE / FOR SHARE  读最新值，加锁
                ↑ 别忘了 UPDATE 和 DELETE 也是当前读
```

### 三种读异常

```
   脏读         读到别人【没提交】的        —— RC 和 RR 都防住了
   不可重复读   同一行的【值】变了          —— RR 防住了（名单只拍一次）
   幻读         满足条件的【行数】变了      —— RR 用间隙锁基本防住了
```

### 排查命令

```sql
SELECT @@transaction_isolation;                  -- 当前隔离级别
SELECT * FROM information_schema.innodb_trx;     -- 正在跑的事务（查长事务）
SHOW ENGINE INNODB STATUS\G                      -- 找 History list length
```
