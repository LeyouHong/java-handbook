# InnoDB 锁体系：加在哪、锁多大、怎么排查

> 环境：MySQL 8.0 / InnoDB，默认隔离级别 **REPEATABLE READ**。本篇 SQL 为**示例**，未附实测输出。
>
> **一句话主线：InnoDB 的行锁不是加在「行」上的，是加在「索引记录」上的。**
>
> 这一句能解释本篇八成的现象：为什么没索引会锁一片、为什么间隙也能被锁、为什么两条看似无关的 SQL 会死锁。

**和《[乐观锁与悲观锁](../concurrency/乐观锁与悲观锁.md)》的关系**：

```
   ┌─ 乐观锁与悲观锁 ──┐   应用层    我该用锁，还是用版本号，还是唯一索引
   │                   │            —— 解决"选哪个策略"
   └─────────┬─────────┘
             ▼
   ┌─ InnoDB 锁（本篇）┐   引擎层    我写的这条 SQL，到底加了什么锁、锁了多大范围
   │                   │            —— 解决"实际发生了什么"
   └───────────────────┘
```

前置知识是《[事务与 MVCC](事务与MVCC.md)》——尤其是**当前读**（第七节）和**幻读**（第八节）。

## 一、两个维度：粒度 × 模式

### 1.1 模式：S 锁和 X 锁

```
   S 锁（共享锁 / 读锁）   我在读，别人也能读，但不能改
   X 锁（排他锁 / 写锁）   我在改，别人既不能读（当前读）也不能改
```

| | S | X |
|---|---|---|
| **S** | ✓ 兼容 | ✗ |
| **X** | ✗ | ✗ |

**只有 S-S 兼容**，其余组合都要等。

### 1.2 粒度：表锁和行锁

```
   表锁    锁整张表     开销小、并发差
   行锁    锁索引记录   开销大、并发好     ← InnoDB 的主场
```

### 1.3 意向锁：表级的"里面有人"标记

假设有人要给整张表加 X 锁。怎么知道表里有没有行锁？

```
   ✗ 笨办法：把 1000 万行挨个检查一遍
   ✓ 意向锁：加行锁之前，先在【表级】插一面旗子
```

```
   IS（意向共享锁）  "我要在这张表里加 S 行锁了"
   IX（意向排他锁）  "我要在这张表里加 X 行锁了"

   → 之后想加表锁的人，看一眼表级的旗子就知道要不要等，O(1)
```

完整兼容矩阵：

```
          IS      IX      S       X
   IS     ✓       ✓       ✓       ✗
   IX     ✓       ✓       ✗       ✗
   S      ✓       ✗       ✓       ✗
   X      ✗       ✗       ✗       ✗

   规律：IS/IX 互相全兼容（它们只是"意向"，真正的冲突在行级解决）
        表级 X 和谁都不兼容
```

**意向锁是 InnoDB 自动加的，你不用管它**，知道它为什么存在就够了。

## 二、行锁的三种形态

这是本篇的核心。RR 隔离级别下，行锁有三种形态：

```
   假设 age 索引上现有数据：10, 25, 40

   ────○──────●──────────●──────────●───────────▶ age
      -∞     10         25         40         +∞
```

### 2.1 记录锁 Record Lock：只锁那一行

```
   ────○──────●──────────█──────────●───────────▶
                        25
                        ↑ 只锁住 25 这条索引记录
```

### 2.2 间隙锁 Gap Lock：锁住两条记录之间的空隙

```
   ────○──────●▓▓▓▓▓▓▓▓▓▓●──────────●───────────▶
             10  (10,25)  25
                    ↑ 锁住这个【开区间】，不含 10 和 25 本身
```

```
   间隙锁只干一件事：【不许在这个空隙里插入新记录】。
   它不阻止别人读、也不阻止别人改已有的行。

   → 它是为幻读而生的（⤵《事务与 MVCC · 8.2》）
```

关键性质：**间隙锁之间互相兼容**。

```
   事务 A 锁住 (10,25)，事务 B 也想锁 (10,25) → 【允许】
   因为它们的目的都是"不许别人插入"，目的一致，不冲突
```

> 这条性质是很多死锁的根源，第五节会看到。

### 2.3 临键锁 Next-Key Lock：记录锁 + 前面的间隙

```
   ────○──────●▓▓▓▓▓▓▓▓▓▓█──────────●───────────▶
             10  (10,25] 25
                    ↑ 前开后闭
```

```
   ┌──────────────────────────────────────────────────────┐
   │  RR 隔离级别下，行锁的【默认形态就是临键锁】。          │
   │  记录锁和间隙锁都是它在特定条件下"退化"的结果。         │
   │                                                       │
   │  区间是【前开后闭】：(10, 25]                          │
   └──────────────────────────────────────────────────────┘
```

整张表被临键锁切成这些区间：

```
   (-∞,10]   (10,25]   (25,40]   (40,+∞)
                                     ↑ 最后这个叫 supremum，
                                       锁住它就没人能插入比 40 大的值
```

### 2.4 RC 下没有间隙锁

```
   READ COMMITTED  →  只有记录锁，【没有间隙锁】
                      所以 RC 下并发更好、死锁更少
                      代价：当前读会有幻读
```

这就是《[事务与 MVCC · 第三节](事务与MVCC.md)》里说的"很多公司改用 RC"的一个重要原因。

## 三、加锁的规则

丁奇在《MySQL 实战 45 讲》里总结过一套规则，非常实用：

```
   原则 1  加锁的基本单位是【临键锁】，前开后闭
   原则 2  查找过程中【访问到的对象】才会加锁
   优化 1  等值查询、【唯一索引】上，临键锁退化为【记录锁】
   优化 2  等值查询、向右遍历时，最后一个值不满足等值条件
           → 临键锁退化为【间隙锁】
```

> ⚠️ **版本前提**：这套规则总结自 MySQL 8.0 早期版本的实测。
> 加锁行为在小版本间有过调整，**结论要以你自己那个版本的 `performance_schema.data_locks` 为准**（第六节给了查法）。
> 把它当成"预期"，不要当成"保证"。

### 3.1 原则 2 的实际含义

"访问到的对象才加锁"——注意是**访问到**，不是**匹配上**：

```sql
-- age 上没有索引
SELECT * FROM t WHERE age = 25 FOR UPDATE;
```

```
   没索引 → 全表扫描 → 【每一行都被访问到】→ 每一行都加锁
   → 效果接近锁表
```

> ⤵ 这就是《[乐观锁与悲观锁 · 3.3 坑一](../concurrency/乐观锁与悲观锁.md)》说的"WHERE 没走索引会锁一片"的机制层解释。
> 而 RR 下这些锁**一直持有到提交**，比很多人以为的严重。

### 3.2 优化 1：唯一索引等值查询

```sql
SELECT * FROM t WHERE id = 25 FOR UPDATE;   -- id 是主键
```

```
   按原则 1：应该锁 (10, 25]
   但 id 是唯一的 → 找到 25 就确定不会有第二个 → 不需要防插入
   → 退化成【记录锁】，只锁 25 这一行
```

```
   所以「按主键等值加锁」是范围最小、最安全的加锁方式。
   这也是为什么悲观锁应该尽量用主键定位。
```

**但如果 id=25 不存在**：

```sql
SELECT * FROM t WHERE id = 27 FOR UPDATE;   -- 27 不存在
```

```
   找不到记录 → 没有记录可锁 → 退化成【间隙锁】 (25, 40)
   → 别人插不了 26、27、…、39
```

这解释了一个常见困惑：**查一个不存在的行，居然也会锁住别人的插入。**

### 3.3 优化 2：非唯一索引等值查询

```sql
SELECT * FROM t WHERE age = 25 FOR UPDATE;   -- age 是普通索引
```

```
   age 不唯一 → 可能有多个 25 → 必须往右扫到第一个不是 25 的值为止

   ────●▓▓▓▓▓▓▓█▓▓▓▓▓▓▓▓○──────────▶ age
       10 (10,25] 25 (25,40) 40
          └─ 临键锁 ─┘└间隙锁┘
                        ↑ 扫到 40 发现不等于 25，
                          于是 (25,40] 退化成间隙锁 (25,40)，不锁 40 本身
```

### 3.4 范围查询不会退化

```sql
SELECT * FROM t WHERE id >= 25 AND id < 40 FOR UPDATE;
```

```
   范围查询【没有优化 1】—— 临键锁不退化

   → 锁住 [25] 这条记录 + (25, 40] 这整个临键锁
     注意末尾：虽然条件是 id < 40，但会访问到 40 才知道要停，
     按原则 2，40 也被锁了
```

```
   ┌────────────────────────────────────────────────────┐
   │  范围查询的加锁范围【总是比你写的条件大】。           │
   │  这是悲观锁在高并发下容易死锁的主要来源。             │
   └────────────────────────────────────────────────────┘
```

### 3.5 二级索引：会锁两棵树

```sql
SELECT * FROM t WHERE age = 25 FOR UPDATE;   -- age 是二级索引
```

> ⤵ **依据**：《[B+ 树原理 · 第七章](B+树原理.md)》——二级索引的叶子存的是主键值，取其他列要回表。

```
   ① 在 age 索引树上加锁（临键锁）
   ② 回表拿到 id，【在主键索引树上也加锁】（记录锁）

   → 一条 SQL 锁了两棵树上的记录
   → 所以另一个事务哪怕用 id 去改这一行，也会被挡住
```

这是很多"看起来无关的两条 SQL 却互相阻塞"的真正原因。

## 四、INSERT 的两个特殊锁

### 4.1 插入意向锁 Insert Intention Lock

```
   它是一种【特殊的间隙锁】，表示"我想在这个间隙里插入"。

   插入意向锁之间【互相兼容】—— 只要插入位置不同：
      事务 A 想插 15，事务 B 想插 20，都在 (10,25) 里 → 互不阻塞 ✓

   但它和【间隙锁冲突】：
      事务 A 持有间隙锁 (10,25)，事务 B 想插 15 → 【等待】
```

```
   ┌──────────────────────────────────────────────────────┐
   │  间隙锁 → 挡住插入意向锁 → 这就是防幻读的执行链条。     │
   └──────────────────────────────────────────────────────┘
```

### 4.2 唯一性检查时的临时 S 锁

```sql
INSERT INTO t (order_no) VALUES ('X001');   -- order_no 有唯一索引
```

```
   插入前要检查有没有重复 → 如果发现已存在，会对那条已有记录加 S 锁

   → 并发插入【相同】的重复 key 时，多个事务互相持 S 锁、
     又都想升级成 X 锁 → 【经典死锁场景】
```

> ⤵ 《[乐观锁与悲观锁 · 第五节](../concurrency/乐观锁与悲观锁.md)》推荐用唯一索引做幂等，正常路径没问题；
> 但如果你的业务会**高并发地插入同一个 key**，要预期到这里可能出现死锁，做好重试。

## 五、死锁

### 5.1 最简单的死锁：加锁顺序相反

```
   事务 A                          事务 B
   ─────────────────────────────────────────────
   UPDATE t WHERE id=1   ✓
                                   UPDATE t WHERE id=2   ✓
   UPDATE t WHERE id=2   → 等 B
                                   UPDATE t WHERE id=1   → 等 A
                    └────── 死锁 ──────┘
```

**解法：固定加锁顺序**（永远按主键升序）。

### 5.2 更隐蔽的死锁：间隙锁互相兼容造成的

这个必须懂，因为它没有"顺序相反"的表象：

```
   表里没有 id=15 这条记录

   事务 A                                事务 B
   ────────────────────────────────────────────────────────────
   SELECT ... WHERE id=15 FOR UPDATE
   → 取得间隙锁 (10,25)                  SELECT ... WHERE id=15 FOR UPDATE
                                         → 也取得间隙锁 (10,25)  【兼容，不阻塞】

   INSERT INTO t VALUES(15,...)
   → 需要插入意向锁，被 B 的间隙锁挡住 → 等

                                         INSERT INTO t VALUES(15,...)
                                         → 被 A 的间隙锁挡住 → 等
                            └────────── 死锁 ──────────┘
```

```
   根因：间隙锁【互相兼容】，所以两边都拿到了；
        但插入意向锁和间隙锁【冲突】，于是双双卡死。

   这就是"先查不存在则插入"这种写法的危险之处 ——
   ⤵ 也是《乐观锁与悲观锁 5.3》强调"不要先 SELECT 再 INSERT，
      直接 INSERT 捕获 DuplicateKeyException"的又一个理由。
```

### 5.3 怎么看死锁日志

```sql
SHOW ENGINE INNODB STATUS\G
```

在输出里找 `LATEST DETECTED DEADLOCK` 段。它的结构是固定的（**以下为结构示意，不是真实输出**）：

```
   ------------------------
   LATEST DETECTED DEADLOCK
   ------------------------
   <时间戳>
   *** (1) TRANSACTION:            ← 事务 1 是谁
       …… 它执行的 SQL
   *** (1) HOLDS THE LOCK(S):      ← 它【已经持有】什么锁
       …… index / lock_mode / 具体记录
   *** (1) WAITING FOR THIS LOCK TO BE GRANTED:   ← 它【在等】什么锁
   
   *** (2) TRANSACTION:            ← 事务 2 同上
   *** (2) HOLDS THE LOCK(S):
   *** (2) WAITING FOR THIS LOCK TO BE GRANTED:
   
   *** WE ROLL BACK TRANSACTION (1)   ← InnoDB 选择回滚谁
```

读日志的方法（按这个顺序看，很快能定位）：

```
   ① 先看两个 WAITING —— 它们在等什么，这是冲突点
   ② 再看两个 HOLDS   —— 谁挡着谁
   ③ 看 lock_mode：
        X, GAP              纯间隙锁
        X, REC_NOT_GAP      纯记录锁
        X                   临键锁（记录 + 间隙）
        X, INSERT_INTENTION 插入意向锁
   ④ 看 index：锁加在哪个索引上 —— 常常发现是二级索引和主键交叉锁（3.5）
```

```
   注意：这个段落只保留【最近一次】死锁。
        要长期留存，开 innodb_print_all_deadlocks = ON，死锁会写进错误日志。
```

### 5.4 相关参数

```ini
innodb_deadlock_detect  = ON    # 默认开，发现死锁立刻回滚一个
innodb_lock_wait_timeout = 50   # 秒，等锁超时（不是死锁，是单纯等太久）
innodb_print_all_deadlocks = ON # 建议开，把每次死锁记进错误日志
```

```
   死锁检测本身是有代价的：每个要等锁的事务都要检查一遍等待图，
   热点行上大量并发时，检测本身会烧 CPU。
   但关掉它更危险（只能靠超时），所以正确做法是【别制造热点】。
```

### 5.5 怎么减少死锁

```
   [ ] 固定加锁顺序（多行操作按主键升序）
   [ ] 事务尽量短，别在事务里做 RPC
   [ ] WHERE 一定走索引，缩小加锁范围（第三节）
   [ ] 尽量用主键等值定位（优化 1，退化成记录锁）
   [ ] 别用"先 SELECT 判断再 INSERT"（5.2）
   [ ] 考虑把隔离级别降到 RC（没有间隙锁，死锁大幅减少）
   [ ] 业务上做好死锁重试 —— 死锁是【正常现象】，不是 bug
```

## 六、排查：谁锁了谁

这是最实用的一节。MySQL 8.0 用 `performance_schema`：

```sql
-- ① 当前所有锁（谁持有、什么模式、锁在哪个索引的哪条记录上）
SELECT ENGINE_TRANSACTION_ID AS trx_id,
       OBJECT_NAME           AS tbl,
       INDEX_NAME            AS idx,
       LOCK_TYPE, LOCK_MODE, LOCK_STATUS, LOCK_DATA
  FROM performance_schema.data_locks;

-- ② 谁在等谁（阻塞关系）
SELECT * FROM performance_schema.data_lock_waits;

-- ③ 最直观的一张：sys 库已经帮你 JOIN 好了
SELECT * FROM sys.innodb_lock_waits\G
--   给出：等待的线程、等待时长、阻塞它的线程、
--        以及【直接可用的 KILL 语句】

-- ④ 配合看事务
SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id, trx_query
  FROM information_schema.innodb_trx;

-- ⑤ 实在要救火
KILL <trx_mysql_thread_id>;
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  想知道"我这条 SQL 到底加了什么锁"，不要猜、不要背规则：   │
   │                                                           │
   │    BEGIN;                                                 │
   │    <你要测的 SQL>                                          │
   │    -- 另开一个会话：                                       │
   │    SELECT INDEX_NAME, LOCK_MODE, LOCK_DATA                │
   │      FROM performance_schema.data_locks;                  │
   │    ROLLBACK;                                              │
   │                                                           │
   │  LOCK_MODE 里的 GAP / REC_NOT_GAP 会直接告诉你答案。       │
   │  这比第三节的规则可靠 —— 规则会随版本变，这个是当场实测。   │
   └──────────────────────────────────────────────────────────┘
```

## 七、表级锁（了解即可）

日常几乎用不到，但要知道它们存在：

```
   LOCK TABLES t READ / WRITE     显式表锁，InnoDB 里基本不用
   
   MDL（元数据锁）                 自动加，防止你查表时别人 ALTER
     · 增删改查 → MDL 读锁（互相兼容）
     · ALTER TABLE → MDL 写锁（和谁都不兼容）
     
     ⚠️ 经典事故：
        一个长事务持有 MDL 读锁
        → ALTER TABLE 要等它 → 卡住并【排队在前】
        → 后续所有查询要等这个 ALTER → 【整张表瞬间不可用】
        
        所以线上 DDL 前必须先查 innodb_trx 有没有长事务，
        并给 ALTER 加超时：ALTER TABLE ... WAIT 5 / 用 gh-ost
   
   AUTO-INC 锁                     自增主键分配时的特殊表锁
     innodb_autoinc_lock_mode = 2（8.0 默认）已经基本消除了它的影响
```

MDL 那条是真会出事故的，值得单独记住。

## 八、速查

### 锁的形态

```
   ┌────────────────────────────────────────────────────────────┐
   │  记录锁 Record       锁一条索引记录          [25]           │
   │  间隙锁 Gap          锁一个开区间，防插入     (10,25)        │
   │  临键锁 Next-Key     记录+前间隙，前开后闭    (10,25]  ←默认 │
   │  插入意向锁          特殊间隙锁，互相兼容                    │
   │                                                             │
   │  RC 下【没有间隙锁】，只有记录锁                             │
   └────────────────────────────────────────────────────────────┘
```

### 加锁规则（8.0，以实测为准）

```
   原则1  基本单位是临键锁，前开后闭
   原则2  访问到的对象才加锁（不是匹配到的）
   优化1  唯一索引 + 等值 + 命中  → 退化成记录锁
          唯一索引 + 等值 + 未命中 → 退化成间隙锁
   优化2  普通索引 + 等值，右边界不满足条件 → 该临键锁退化成间隙锁
   范围查询不退化，且会多锁一个边界
```

### 排查三板斧

```sql
SELECT * FROM sys.innodb_lock_waits\G              -- 谁在等谁（最好用）
SELECT * FROM performance_schema.data_locks;        -- 具体锁在哪条记录
SHOW ENGINE INNODB STATUS\G                         -- LATEST DETECTED DEADLOCK
```

### 少死锁 Checklist

```
   [ ] 固定加锁顺序
```
