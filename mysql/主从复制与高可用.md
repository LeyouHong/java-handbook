# MySQL 主从复制与高可用

> 环境：MySQL 8.0 / InnoDB。本篇命令与配置为**示例**，未附实测输出。
>
> **一句话主线：主从复制是 binlog 的第一消费者——它的所有能力和所有毛病，都源于「日志要传过去、再重放一遍」。**
>
> 传输要时间、重放要时间，于是有了**主从延迟**；重放可能失败，于是有了**数据不一致**。
> 这一篇的九成内容是在处理这两件事。

《[binlog](binlog.md)》第五节把主从复制列为八个用途之首但只给了一段，这一篇是它的展开。前置知识是那一篇的**格式选择**（必须 ROW）和 **`sync_binlog`**。

---

## 一、复制是怎么跑起来的

三个线程，一个中间文件：

```
   ┌─ 主库 ────────────┐              ┌─ 从库 ─────────────────────────┐
   │                    │              │                                 │
   │  事务提交           │              │                                 │
   │      ↓             │              │                                 │
   │  写 binlog          │              │                                 │
   │      ↓             │              │                                 │
   │  ┌────────────┐   │   binlog     │   ┌──────────┐                  │
   │  │ dump 线程   │───┼──── 流 ─────▶│   │ IO 线程   │                  │
   │  └────────────┘   │              │   └─────┬────┘                  │
   │                    │              │         ↓ 原样落盘（不解析）      │
   │                    │              │    ┌─────────┐                  │
   │                    │              │    │relay log│                  │
   │                    │              │    └────┬────┘                  │
   │                    │              │         ↓                       │
   │                    │              │   ┌────────────┐                │
   │                    │              │   │ SQL 线程    │ 重放到数据文件  │
   │                    │              │   └────────────┘                │
   └────────────────────┘              └─────────────────────────────────┘
```

```
   dump 线程（主库）  每个从库一个，负责把 binlog 推过去
   IO 线程（从库）    只管【接收和落盘】，不解析、不执行 —— 所以它很快
   SQL 线程（从库）   真正执行 relay log 里的变更 —— 【瓶颈通常在这里】
```

```
   ┌────────────────────────────────────────────────────────┐
   │  记住这个分工，主从延迟的排查就有了方向：                 │
   │                                                         │
   │    IO 线程慢 → 网络问题（少见）                          │
   │    SQL 线程慢 → 重放跟不上（绝大多数情况）               │
   └────────────────────────────────────────────────────────┘
```

## 二、三种复制模式

区别只在一件事：**主库提交时，等不等从库？**

### 2.1 异步复制（默认）

```
   主库：写 binlog → 【立刻返回客户端"成功"】→ 慢慢推给从库
```

```
   ✓ 主库性能不受从库影响
   ✗ 主库刚提交就宕机 → 这个事务【可能从库根本没收到】→ 切换后数据丢了
```

**这是默认行为，也是绝大多数场景的选择。**要清楚它的承诺是"最终会同步"，不是"不丢数据"。

### 2.2 半同步复制

主库提交时，**至少等一个从库确认收到**：

```
   主库：写 binlog → 等从库 ACK → 返回客户端
                        ↑ 只要有一个从库说"我收到并落盘了"就够
```

两种时机，区别很关键：

```
   AFTER_SYNC（默认，推荐）
       写 binlog → 等 ACK → 再提交引擎层 → 返回客户端
       主库崩溃时：客户端没收到成功，从库已有数据 → 【不会丢，也不会幻读到】

   AFTER_COMMIT
       写 binlog → 提交引擎层 → 等 ACK → 返回客户端
       主库在等 ACK 时崩溃：本机已经提交了，别的会话能读到，
       但客户端没收到成功、从库也可能没收到 → 【幻象读】
```

```ini
rpl_semi_sync_source_enabled = 1          # 主库（8.0.26+ 的新命名）
rpl_semi_sync_replica_enabled = 1         # 从库
rpl_semi_sync_source_timeout = 1000       # ms，超时【自动退化成异步】
rpl_semi_sync_source_wait_point = AFTER_SYNC
```

```
   ⚠️ 注意最后那个超时：网络抖一下就退化成异步了，
      而且退化是【静默】的 —— 必须监控 Rpl_semi_sync_source_status，
      否则你以为自己有半同步保护，实际早就没有了。
```

### 2.3 组复制 MGR

```
   基于 Paxos 的多数派协议，一组节点（通常 3 或 5 个）内部投票
   → 强一致、自动选主、自动剔除故障节点
```

```
   ✓ 真正的高可用，不需要外部切换工具
   ✗ 对网络延迟敏感（节点间要低延迟，跨机房吃力）
   ✗ 大事务容易触发流控甚至把节点踢出集群
```

MySQL InnoDB Cluster = MGR + MySQL Router + MySQL Shell，是官方的完整方案。

### 2.4 怎么选

```
   一般业务          异步 + 完善的延迟监控        ← 90% 的场景
   金融/订单核心      半同步（AFTER_SYNC）+ 监控退化
   要求自动切换       MGR / 云厂商 RDS 的高可用版
```

## 三、主从延迟：成因与排查

这是运维主从时 90% 的问题。

### 3.1 先说监控的坑：`Seconds_Behind_Master` 不可靠

```sql
SHOW REPLICA STATUS\G     -- 8.0.22+ 的新命名，旧的是 SHOW SLAVE STATUS
```

它给的 `Seconds_Behind_Master` 有几个致命问题：

```
   ✗ 它算的是"SQL 线程正在执行的事件的时间戳"和"从库当前时间"的差
     → 如果 IO 线程也卡住了（binlog 根本没传过来），
       SQL 线程无事可做，这个值会显示 【0】—— 看起来毫无延迟，实际差很远

   ✗ 主从服务器时钟不同步会直接算错

   ✗ 大事务执行期间，值会先归零再突然跳到很大
```

**正确做法：心跳表。**

```
   主库上一个定时任务，每秒更新一行：
       UPDATE heartbeat SET ts = NOW(3) WHERE id = 1;

   从库读这一行，用 NOW(3) - ts 就是【真实延迟】
       —— 这个值不受 IO 线程状态影响，也不看主库时钟
```

工具：`pt-heartbeat`（Percona Toolkit）就是干这个的，直接用。

辅助判断：

```sql
-- 对比这三个位点，能定位是"没传过来"还是"没执行完"
-- Read_Source_Log_Pos   IO 线程读到哪了
-- Exec_Source_Log_Pos   SQL 线程执行到哪了
-- 两者差距大 → 是【重放】跟不上
-- 两者接近但都落后主库 → 是【传输】跟不上
```

### 3.2 延迟的六个来源

```
   ① 大事务          一个 UPDATE 改 100 万行 → 从库要原样执行 100 万行
                      而且是【提交后才整批传过去】→ 延迟瞬间飙升

   ② 大表 DDL        ALTER TABLE 在从库上是串行执行的，
                      主库用 gh-ost 无锁改完了，从库还在慢慢 ALTER

   ③ 从库配置差      "从库反正只读，用差点的机器" —— 这是延迟的常见根因

   ④ 从库承担了太多查询   读写分离把大量慢查询压到从库，
                          SQL 线程抢不到资源

   ⑤ 从库上有长事务   SQL 线程重放时被锁住（⤵《InnoDB 锁》第六节排查）

   ⑥ 表没有主键      ROW 格式下，从库重放要定位那一行，
                      没有主键就【全表扫描】—— 一行变更扫一次全表
                      这条最隐蔽，也最致命
```

第 ⑥ 条值得单独强调：

```
   ┌────────────────────────────────────────────────────────┐
   │  ROW 格式 + 无主键的表 = 从库重放时每行都全表扫描        │
   │                                                         │
   │  主库删 10 万行只要几秒，从库可能跑几个小时。            │
   │  这就是《数据表设计》要求"每张表必须有主键"的一个硬理由。 │
   └────────────────────────────────────────────────────────┘
```

### 3.3 并行复制：MySQL 的解法演进

从库的 SQL 线程原本是**单线程**的——主库几十个并发写，从库一个线程重放，天然跟不上。

演进路线：

```
   5.6   按【库】并行     只有多个 database 时才有效，
                          单库业务等于没并行

   5.7   LOGICAL_CLOCK    按【组提交】并行 —— 能在主库同一个提交组里的
                          事务，说明它们不冲突，从库就能并行重放
                          ★ 这是质变

   8.0   WRITESET         按【行的哈希】判断冲突 —— 只要两个事务
                          没碰同一行就能并行，比组提交更细
                          ★ 目前最优
```

配置（8.0 推荐）：

```ini
# 主库：让 WRITESET 信息写进 binlog
binlog_transaction_dependency_tracking = WRITESET
transaction_write_set_extraction = XXHASH64

# 从库：开并行
replica_parallel_type    = LOGICAL_CLOCK
replica_parallel_workers = 8            # 通常 = CPU 核数
replica_preserve_commit_order = ON      # 保证提交顺序和主库一致
```

```
   replica_preserve_commit_order = ON 很重要：
   关掉它虽然更快，但从库上的提交顺序可能和主库不同，
   → 读从库时可能看到"后面的事务已生效、前面的还没有"的中间状态
```

### 3.4 治理清单

```
   [ ] 每张表都有主键（3.2 第 ⑥ 条）
   [ ] 禁止大事务，批量操作拆成小批
   [ ] DDL 走 gh-ost / pt-osc
   [ ] 从库配置不低于主库
   [ ] 开 WRITESET 并行复制
   [ ] 用心跳表监控真实延迟，别信 Seconds_Behind_Master
   [ ] 对延迟设告警阈值，超过就把读流量切回主库
```

## 四、读写分离的坑：写完立刻读不到

这是业务侧最常踩的问题：

```java
orderService.create(order);              // 写主库
Order o = orderService.get(order.getId()); // 读从库 → 【查不到！】
```

```
   ────────────────────────────────────────────▶ 时间
   主库  写入 ●
   从库           ● 同步完成
              ↑
         这个窗口内读从库 = 读不到
```

五种解法，按推荐顺序：

### 4.1 强制走主库（最简单，最推荐）

```
   把"写后立刻读"的场景标记出来，强制路由到主库。
   ShardingSphere / MyBatis 插件都支持 hint。
```

```java
@MasterRoute          // 或 HintManager.getInstance().setPrimaryRouteOnly()
public Order getAfterCreate(Long id) { ... }
```

```
   ✓ 简单、确定、无延迟
   ✗ 要人工识别哪些场景需要 —— 但这恰恰是好事，
     它逼你想清楚"这个读到底能不能容忍旧数据"
```

### 4.2 写后短时间内走主库

```
   写完把 userId 记进 Redis，设 TTL = 主从延迟的 P99（比如 1 秒）
   这个 key 存在期间，该用户的所有读都走主库
```

比 4.1 自动，代价是多一次 Redis 查询。

### 4.3 判断延迟再决定

```
   读之前查一下从库延迟：< 阈值走从库，否则走主库
```

```
   ✗ 延迟是"整体"的，不能保证"我这条数据"已经到了
   → 只能算缓解，不能算解决
```

### 4.4 等位点（最精确，但最重）

```sql
-- 主库写完拿到位点
SHOW MASTER STATUS;   -- 得到 File / Position

-- 从库上等这个位点被执行到（最多等 1 秒）
SELECT MASTER_POS_WAIT('binlog.000012', 98765, 1);
--   返回 >= 0：等到了，可以放心读
--   返回 -1：超时 → 降级去读主库
```

GTID 模式下用 `WAIT_FOR_EXECUTED_GTID_SET()`，更方便。

```
   ✓ 语义精确：确实是"我那条数据已经同步过来了"
   ✗ 每次写都要拿位点、每次读都要等，实现复杂、开销大
   → 只用在少数关键链路
```

### 4.5 直接读缓存

写的时候同时更新缓存，读走缓存不走从库。绕过问题而不是解决问题，但很多场景够用。

```
   ⤵ 缓存和数据库怎么保持一致，见《binlog · 5.5》
```

## 五、GTID：让位点管理不再靠人

传统复制靠 `(binlog 文件名, 位点)` 定位，**换主库时这个坐标就失效了**——新主库的 binlog 文件名和位点完全是另一套。

GTID（全局事务标识）把坐标换成了事务本身的身份：

```
   GTID = server_uuid : 事务序号
   例：3E11FA47-71CA-11E1-9E33-C80AA9429562:1-1000
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  每个事务在整个复制拓扑里有【唯一且不变】的编号。          │
   │  从库只要说"我执行到 xxx:1-1000 了"，                      │
   │  任何一个新主库都知道该从哪继续 —— 不用算位点。            │
   └──────────────────────────────────────────────────────────┘
```

```ini
gtid_mode = ON
enforce_gtid_consistency = ON
```

搭建从库时：

```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='10.0.0.1', SOURCE_USER='repl', SOURCE_PASSWORD='xxx',
  SOURCE_AUTO_POSITION = 1;        -- ← 有 GTID 就用它，不用写 FILE/POS
START REPLICA;
```

```
   ✓ 主从切换极大简化，是自动切换工具的前提
   ✓ 能自动跳过已执行过的事务，避免重复执行
   ✗ 不支持某些语句（CREATE TABLE ... SELECT、事务里混用非事务表等）
```

**新搭的库直接开 GTID，没有理由不开。**

## 六、搭一套主从（流程）

```sql
-- ── 主库 ──────────────────────────────────
-- my.cnf: server_id=1, log_bin=binlog, binlog_format=ROW, gtid_mode=ON
CREATE USER 'repl'@'%' IDENTIFIED BY 'xxx';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- ── 导出全量（一致性快照，不锁表）─────────
-- $ mysqldump --all-databases --single-transaction \
--             --source-data=2 --set-gtid-purged=ON > dump.sql
--   --single-transaction  用一个可重复读事务导出（⤵《事务与 MVCC》第六节）
--                          所以不需要 FLUSH TABLES WITH READ LOCK
--   数据量大时改用 XtraBackup 或 clone plugin

-- ── 从库 ──────────────────────────────────
-- my.cnf: server_id=2, gtid_mode=ON, read_only=ON, super_read_only=ON
-- $ mysql < dump.sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='10.0.0.1', SOURCE_USER='repl',
  SOURCE_PASSWORD='xxx', SOURCE_AUTO_POSITION=1;
START REPLICA;

SHOW REPLICA STATUS\G
--  要确认这三行：
--    Replica_IO_Running:  Yes
--    Replica_SQL_Running: Yes
--    Last_Error:          （空）
```

```
   两个别忘：
   · 从库一定要 super_read_only = ON
     （read_only 挡不住有 SUPER 权限的账号，误写从库会让主从彻底分叉）
   · mysqldump 的 --single-transaction 依赖 InnoDB 的可重复读，
     MyISAM 表用它拿不到一致快照
```

## 七、主从切换与高可用架构

### 7.1 切换要做的事

```
   ① 确认从库已追平（Exec_Source_Log_Pos 追上主库）
   ② 主库置为只读，停止写入
   ③ 等从库消化完剩余 relay log
   ④ 从库 STOP REPLICA + RESET REPLICA ALL，解除只读
   ⑤ 【改流量入口】—— VIP / DNS / 中间件配置
   ⑥ 其他从库指向新主库
```

第 ⑤ 步是关键：**数据库切完了，应用得知道往哪连**。这也是各种高可用方案的主要差别所在。

### 7.2 常见方案

| 方案 | 怎么切 | 特点 |
|---|---|---|
| **MHA** | 外部管理节点监控 + 切换 | 老牌，社区维护已停滞 |
| **orchestrator** | 拓扑管理 + 自动故障转移 | 可视化拓扑，GitHub 出品，仍活跃 |
| **MGR / InnoDB Cluster** | 集群内部投票自选 | 官方方案，无需外部组件 |
| **云 RDS 高可用版** | 云厂商托管 | 最省心；生产环境的默认答案 |

```
   自建 MySQL 高可用是个坑很多的活（脑裂、数据分叉、切换抖动）。
   除非有专职 DBA，否则【直接用云厂商的高可用版】通常是最优解。
```

### 7.3 脑裂

```
   网络分区 → 管理节点以为主库挂了 → 提升从库为新主
   → 但老主库其实活着，还在接收写入
   → 【两个主库同时被写】→ 数据永久分叉，只能人工对账

   防范：
   · 用多个仲裁点判断存活（不要单点判断）
   · 切换前对老主库做 STONITH（强制隔离：关机 / 摘 VIP / 改防火墙）
   · MGR 靠多数派天然免疫（少数派会自动变只读）
```

## 八、速查

### 三个线程

```
   dump（主）→ IO（从，只落盘）→ relay log → SQL（从，真执行）
                                                  ↑ 瓶颈通常在这
```

### 复制模式

```
   异步      不等从库             默认，可能丢数据
   半同步    等一个从库 ACK       AFTER_SYNC；注意超时会【静默退化】
   MGR       Paxos 多数派         强一致，网络敏感
```

### 延迟排查

```sql
SHOW REPLICA STATUS\G
--  Replica_IO_Running / Replica_SQL_Running   都要是 Yes
--  Read_Source_Log_Pos vs Exec_Source_Log_Pos 差距大 → 重放跟不上
--  Seconds_Behind_Master                      【不可信，用心跳表】
```

```
   六大成因：大事务 / 大表 DDL / 从库配置差 / 从库查询压力 /
             从库长事务 / 【表没有主键】
```

### 关键参数

```ini
# 主库
server_id, log_bin, binlog_format=ROW, gtid_mode=ON
binlog_transaction_dependency_tracking = WRITESET

# 从库
read_only=ON, super_read_only=ON
replica_parallel_workers = 8
replica_parallel_type = LOGICAL_CLOCK
replica_preserve_commit_order = ON
```

### 读写分离五解法

```
   ① 强制走主库        简单、确定       ← 首选
   ② 写后 N 秒走主库    自动，需 Redis
   ③ 判断延迟          只算缓解
   ④ 等位点            精确但重         ← 关键链路
   ⑤ 读缓存            绕过问题
```
