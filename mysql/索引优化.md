# MySQL 索引优化：最左前缀、覆盖索引与 EXPLAIN 实战

> 环境：MySQL 8.0 / InnoDB。这一篇讲**表已经建好之后**怎么把索引调对。
>
> 一句话主线：**看懂了回表，就知道索引覆盖为什么快；看懂了叶子层的排序方式，就不用背最左前缀。**

**MySQL 三篇的关系**（建议按这个顺序读）：

```
   ┌─ 1. B+ 树原理 ─────┐  为什么     索引长什么样、页怎么组织、回表是什么
   │   （原理层）        │            → 本篇每条规则的依据都在那里
   └────────┬───────────┘
            ▼
   ┌─ 2. 数据表设计 ────┐  建表时     字段、类型、关系、规范
   │   （设计层）        │
   └────────┬───────────┘
            ▼
   ┌─ 3. 索引优化 ──────┐  上线后     最左前缀、覆盖索引、EXPLAIN
   │   （本篇）          │            → 跟着慢查询日志持续迭代
   └────────────────────┘
```

全文三条主线：

```
   ① 索引遵循『最左前缀匹配』原则（多列索引 / 联合索引），但要注意索引字段的顺序
   ② 触发索引覆盖（Using index），不需要回表，速度最优
   ③ 善于使用 explain / desc 分析执行计划
```

本篇里凡是出现 **⤵ 依据** 的地方，都指向《[B+ 树原理](B+树原理.md)》的对应章节；第七节有一张完整对照表。

## 一、开工前：两棵树和回表（30 秒复习）

调索引之前，只需要记住 B+ 树的**两个事实**——完整推导见《[B+ 树原理 · 第三章 / 第七章](B+树原理.md)》。

```
      聚簇索引（主键索引）              二级索引（辅助索引）
      叶子 = 【整行数据】                叶子 = 【主键值】

   ┌────────────────────┐          ┌────────────────────┐
   │ 15,18 ⇄ 20,30 ⇄ …  │          │ biao,fei ⇄ kun,yw ⇄ … │
   │ ↑ salary/name 都在  │          │ ↑ 只有 name + id      │
   └────────────────────┘          └────────────────────┘
      找到主键 = 拿到整行              要别的列 → 回表
```

**回表**——二级索引里没有的列，必须拿主键回聚簇索引再查一棵树：

```sql
SELECT * FROM worker WHERE name = 'yw';
```

```
   ① 走 name 这棵树   3 次 IO  →  拿到 id = 49
   ② 回聚簇索引再查   3 次 IO  →  拿到 type / salary / ...
                                    ↑ 这第二步就是"回表"
   命中 1000 行 = 回表 1000 次【随机 IO】
```

本篇后面所有优化，本质上都在做两件事之一：

```
   ┌─ 让第一棵树能用上（最左前缀、列序、避免索引失效）
   └─ 让第二棵树别走（索引覆盖）
```

## 二、看一张真实的表：worker 的索引有没有优化空间？

```sql
use imooc_ecommerce_data;

CREATE TABLE `worker` (
  `id`      bigint(20) unsigned NOT NULL AUTO_INCREMENT COMMENT 'id',
  `type`    char(64)   NOT NULL DEFAULT ''  COMMENT '员工类型',
  `name`    char(64)   NOT NULL,
  `salary`  bigint(20) unsigned DEFAULT NULL,
  `version` bigint(20) NOT NULL DEFAULT '0' COMMENT '乐观锁版本号',
  PRIMARY KEY (`id`),
  KEY `type_salary_idx`      (`type`,`salary`),
  KEY `type_salary_name_idx` (`type`,`salary`,`name`)
) ENGINE=InnoDB AUTO_INCREMENT=1 DEFAULT CHARSET=utf8 COMMENT='员工表';

-- 也可以建表后再加索引
ALTER TABLE `worker` ADD INDEX name_idx (`name`);
```

### 问题 1（最关键）：`type_salary_idx` 是纯冗余索引

```
   type_salary_name_idx (type, salary, name)
   等价于同时拥有：  (type)
                    (type, salary)     ← 就是 type_salary_idx，完全重复！
                    (type, salary, name)
```

`(type, salary)` 是 `(type, salary, name)` 的**最左前缀**，前者能干的事后者全能干。留着它的代价：

- 每次 `INSERT` 多维护一棵 B+ 树；
- `UPDATE type` 或 `salary` 时多一次索引项的删除+插入；
- 多占一份磁盘；
- 优化器多一个候选，选错的概率上升。

```sql
-- ✓ 直接删掉
ALTER TABLE worker DROP INDEX type_salary_idx;
```

> 判断冗余索引的通用方法：把所有索引的列序列写出来，**如果 A 是 B 的前缀，A 就该删**。
>
> **⤵ 依据**：《[B+ 树原理 · 第七章](B+树原理.md)》——**每个索引都是一棵独立的、完整的 B+ 树**，
> 不是"一列附加信息"。多一个索引 = 多一棵要维护的树：写入时多插一个叶子项、
> 可能多一次页分裂、多占一份磁盘。而 `(type,salary)` 这棵树能定位的范围，
> `(type,salary,name)` 那棵树用最左前缀完全能覆盖——纯属白维护。

### 问题 2：`name_idx` 要不要建，取决于有没有"只按 name 查"的场景

```sql
-- 如果业务只有这类查询 → name_idx 是必需的（联合索引最左是 type，帮不上忙）
SELECT * FROM worker WHERE name = 'qinyi';

-- 如果查询永远带着 type → name_idx 白建，删掉
SELECT * FROM worker WHERE type = 'B' AND name = 'qinyi';
```

**索引是为查询建的，不是为字段建的。** 建之前先把真实 SQL 列出来。

### 问题 3：字段类型拖累了索引效率

| 字段 | 问题 | 改法 |
|---|---|---|
| `type char(64)` | 员工类型最多几十种，却占定长 64 字符。`utf8` 下**索引里每项就是 192 字节** | 改 `TINYINT` + `COMMENT '1正式 2实习 3外包'`，索引项从 192B 降到 1B |
| `name char(64)` | 姓名长度不定，`CHAR` 定长会补空格、浪费；且尾部空格在比较时被忽略，容易出诡异 bug | 改 `VARCHAR(32) NOT NULL DEFAULT ''` |
| `salary ... DEFAULT NULL` | 可为 NULL：`WHERE salary != 1000` 会漏掉 NULL 行；`AVG(salary)` 跳过 NULL；索引项多一个 NULL 标记字节 | 改 `NOT NULL DEFAULT 0`，且金额单位定死（分） |
| `CHARSET=utf8` | MySQL 的 `utf8` 是 3 字节阉割版，存不了 emoji | 改 `utf8mb4` |
| `name` 没有 `COMMENT` | — | 补上 |

**索引列越窄，一页能装的索引项越多，树越矮。** `type` 从 `char(64)` 改成 `TINYINT`，`(type, salary, name)` 这棵树的高度可能直接少一层。

### 优化后的表

```sql
CREATE TABLE `worker` (
  `id`      BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT 'id',
  `type`    TINYINT         NOT NULL DEFAULT 0  COMMENT '员工类型 1正式 2实习 3外包',
  `name`    VARCHAR(32)     NOT NULL DEFAULT '' COMMENT '姓名',
  `salary`  BIGINT UNSIGNED NOT NULL DEFAULT 0  COMMENT '月薪，单位分',
  `version` BIGINT          NOT NULL DEFAULT 0  COMMENT '乐观锁版本号',
  PRIMARY KEY (`id`),
  KEY `idx_type_salary_name` (`type`,`salary`,`name`),   -- 删掉了冗余的 (type,salary)
  KEY `idx_name` (`name`)                                -- 仅当存在"只按姓名查"时保留
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='员工表';
```

## 三、最左前缀匹配：三条 SQL 讲透

用原表的 `type_salary_name_idx (type, salary, name)` 来分析。

### 先理解索引里的数据是怎么排的

联合索引 `(type, salary, name)` 的叶子节点，是**先按 type 排，type 相同再按 salary 排，salary 相同再按 name 排**——就像字典先按第一个字母排：

```
   叶子节点的实际顺序：

   type  salary  name        ← 有序的前提是：前面的列已经确定
   ─────────────────────
    A     1000   li          type=A 这一段里，salary 是有序的 ✓
    A     2000   wang
    A     3000   zhao
    B      500   qian        type 一变，salary 从头开始排
    B     2000   qinyi       ┐ salary=2000 这一段里，name 才有序 ✓
    B     2000   sun         ┘
    B     5000   zhou
    C     1500   wu
```

**所以规则很自然**：只有前面的列取"等值"，后面的列才是有序的、才能用索引定位。前面的列一旦是"范围"，后面的列就散了。

> **⤵ 依据**：《[B+ 树原理 · 第八章](B+树原理.md)》——B+ 树能快，靠的是"有序 → 可二分"。
> 上面这张表就是叶子层的真实排列：`salary` 只在**同一个 type 内部**有序，全局是散的。
> 所以 `WHERE salary=2000` 单独查时，2000 分散在 A、B、C 各段里，整棵树上无法二分定位。
>
> **最左前缀不是一条人为规定，而是排序方式的必然结果**——记住这句就不用背那张匹配表了。

### SQL 1：`type='B' AND salary>2000`

```sql
explain SELECT * FROM worker WHERE type = 'B' AND salary > 2000;
```

```
   type='B'  → 等值，直接定位到 B 那一段        ✓ 用上索引第 1 列
   salary>2000 → B 段内 salary 有序，范围扫描   ✓ 用上索引第 2 列
                                                ✗ 到此为止（范围之后不再定位）
```

EXPLAIN 关键结果：

| 字段 | 值 | 含义 |
|---|---|---|
| `select_type` | `SIMPLE` | 简单 SELECT，没有 UNION 和子查询 |
| `type` | **`range`** | 索引范围扫描——因为用了 `>` |
| `possible_keys` | `type_salary_idx, type_salary_name_idx` | 两个候选（正是冗余的证据） |
| `key` | `type_salary_name_idx` | 实际选中的 |
| `key_len` | **`201`** | 用了索引的前 201 字节 → 见下面的换算 |
| `rows` | 估算扫描行数 | 越小越好，**不是精确值** |
| `Extra` | `Using index condition` | 索引下推，见下文 |

### key_len：判断"到底用上了索引的几列"

这是 EXPLAIN 里最容易被忽略、但信息量最大的字段。算法是：

```
   每列的 key_len = 类型占用字节
                  + 1（如果这列允许 NULL）
                  + 2（如果是 VARCHAR 等变长类型）
```

对 worker 表（`CHARSET=utf8`，一字符 3 字节）：

| 列 | 计算 | key_len |
|---|---|---|
| `type char(64) NOT NULL` | 64 × 3 | **192** |
| `salary bigint DEFAULT NULL` | 8 + 1（可空） | **9** |
| `name char(64) NOT NULL` | 64 × 3 | **192** |

```
   key_len = 192          → 只用上了 type
   key_len = 192 + 9 = 201 → 用上了 type + salary        ← SQL 1 是这个
   key_len = 192+9+192 = 393 → 三列全用上
```

> 实用技巧：怀疑某列没走上索引时，别猜，**用 key_len 去反推**。

### SQL 2：`salary>2000 AND type='B'` —— 和 SQL 1 完全一样

```sql
explain SELECT * FROM worker WHERE salary > 2000 AND type = 'B';
```

**WHERE 里的书写顺序无所谓**，优化器会自动重排条件去匹配索引。

```
   "最左前缀"指的是【索引定义时的列顺序】，
   不是【你写 SQL 时的条件顺序】。
```

要注意的是**索引定义的顺序**——建成 `(salary, type)` 就完全是另一回事了：

```sql
-- ✗ 假如索引建成 (salary, type)
--   salary>2000 是范围 → type 排在它后面 → type 用不上索引定位
--   key_len 只有 9，扫描行数暴涨

-- ✓ 建成 (type, salary)
--   type 等值定位 → salary 在该段内有序 → 范围扫描直接命中
```

**这就是"注意索引字段的顺序"这句话的全部含义：等值列在前，范围/排序列在后。**

### SQL 3：`salary>2000 AND type='B' AND name='qinyi'`

```sql
explain SELECT * FROM worker WHERE salary > 2000 AND type = 'B' AND name = 'qinyi';
```

很多人以为三列都用上了，其实**没有**：

```
   type='B'      等值 → 定位 ✓
   salary>2000   范围 → 定位 ✓，但【到此为止】
   name='qinyi'  ✗ 无法用于定位（salary 已经是范围，name 在这一段里是乱序的）

   key_len 仍然是 201，不是 393
```

但 MySQL 5.6+ 有个补救机制——**索引下推（Index Condition Pushdown, ICP）**，也就是 `Extra` 里的 `Using index condition`：

```
   没有 ICP（旧版本）                     有 ICP（5.6+）
   ┌──────────────────────┐             ┌──────────────────────┐
   │ 引擎层：按 type+salary │             │ 引擎层：按 type+salary │
   │  取出 1000 条索引项    │             │  取出 1000 条索引项    │
   │      ↓ 全部回表 1000 次│             │  顺便用索引里的 name    │
   │ Server 层：再筛 name   │             │  过滤掉 990 条         │
   │  最后只剩 10 条        │             │      ↓ 只回表 10 次    │
   └──────────────────────┘             └──────────────────────┘
        回表 1000 次                          回表 10 次
```

**关键点**：`name` 虽然不能用来"定位"，但它就在索引里，所以能用来"过滤"，从而**大幅减少回表次数**。这就是 `Using index condition` 的价值。

### 一张表记住最左前缀

索引 `(a, b, c)`：

| WHERE 条件 | 用上几列 | 说明 |
|---|---|---|
| `a=1` | a | ✓ |
| `a=1 AND b=2` | a, b | ✓ |
| `a=1 AND b=2 AND c=3` | a, b, c | ✓ 满血 |
| `b=2 AND a=1` | a, b | ✓ 顺序无关，优化器会重排 |
| `a=1 AND b>2 AND c=3` | a, b | c 只能靠 ICP 过滤，不能定位 |
| `a=1 AND c=3` | a | 中间断了，c 只能靠 ICP 过滤 |
| `b=2 AND c=3` | **无** | ✗ 缺最左列 a，索引整个用不上 |
| `a LIKE 'x%'` | a | ✓ 前缀匹配可以走 |
| `a LIKE '%x'` | **无** | ✗ 前导模糊 |

> 补充：`type` 字段的等级从好到差是
> `system > const > eq_ref > ref > range > index > ALL`
> 看到 **`ALL`（全表扫）** 或 `index`（全索引扫）就该警觉了。

**还有两条这张表没覆盖的情况**，都在《[B+ 树原理 · 第八章](B+树原理.md)》里展开讲了：

```
   ✓ WHERE a IN (1,2) AND b=3   → IN 是【多个等值区间】，不截断后面的列，b 能用上！
                                   （对比 a>1 AND b=3，b 就用不上）
   ✓ WHERE a=1 ORDER BY b       → b 在 a 段内天然有序，顺着叶子链表读，免 filesort
```

那一章用 8 行具体数据把联合索引的树画了出来，逐条演示每种 SQL 在树上怎么走位、
列序为什么这么定、`ORDER BY` 什么时候能蹭到索引——**想彻底搞懂联合索引，读那一章**。

## 四、索引覆盖：省掉回表那一半开销

### 什么叫覆盖

**查询需要的所有列，都能在这棵索引树里拿到** → 不用回表 → `Extra: Using index`。

```sql
-- 索引：idx_type_salary_name (type, salary, name)

-- ✓ 覆盖：要的 type/salary/name 都在索引里
explain SELECT type, salary, name FROM worker WHERE type = 'B' AND salary > 2000;
-- Extra: Using index    ← 就查这棵树，一次都不回表

-- ✓ 也覆盖：主键 id 本来就存在辅助索引的叶子里
explain SELECT id, name FROM worker WHERE type = 'B' AND salary > 2000;
-- Extra: Using index

-- ✗ 不覆盖：version 不在索引里，只能回表
explain SELECT type, salary, version FROM worker WHERE type = 'B';
-- Extra: NULL / Using index condition

-- ✗ 最糟：SELECT * 一定要回表
explain SELECT * FROM worker WHERE type = 'B' AND salary > 2000;
```

对照第一节的图看就很清楚：

```
   SELECT type,salary,name          SELECT *
   ┌────────────────────┐          ┌────────────────────┐  ┌──────────────────┐
   │ 辅助索引树          │          │ 辅助索引树          │→ │ 主键索引树        │
   │ 叶子里有 type/salary │          │ 叶子里只有主键 id   │  │ 按 id 逐行捞数据  │
   │ /name → 直接返回     │          └────────────────────┘  └──────────────────┘
   └────────────────────┘                 命中 N 行 = 回表 N 次（随机 IO）
        Using index ✓
```

**命中 1000 行就要回表 1000 次随机 IO**，覆盖索引直接把这部分归零——这是索引优化里性价比最高的一招。

> **⤵ 依据**：《[B+ 树原理 · 3.6](B+树原理.md)》——二级索引叶子里**只有索引列 + 主键**，
> 别的列一个都没有。所以"能不能覆盖"的判断标准非常机械：
>
> ```
>    SELECT 和 WHERE 里出现的每一列  ⊆  索引列 ∪ {主键}   → 覆盖 ✓
>    只要有一列不在这个集合里                              → 回表 ✗
> ```
>
> 这也顺带解释了为什么 `SELECT *` **永远**无法命中覆盖索引。

### 实战：为分页列表专门设计覆盖索引

```sql
-- 场景：列表页只展示姓名和薪资
-- ✗ 回表 20 次
SELECT * FROM worker WHERE type = 'B' ORDER BY salary DESC LIMIT 20;

-- ✓ 只取需要的列，命中覆盖索引，0 次回表
SELECT name, salary FROM worker WHERE type = 'B' ORDER BY salary DESC LIMIT 20;
-- 索引 (type, salary, name)：type 定位 → salary 天然有序（连 filesort 都免了）→ name 顺带拿到
```

这条 SQL 一次拿下三个收益：**索引定位 + 免排序 + 免回表**。

### 关于 `SELECT *`

图里那句话说得很实在：

> 如果数据表本身的字段不多，比如不超过 10 个，且查询的行数也不多，比如 1000 条以内，`select *` 问题也不大。

拆开就是一条判断规则：

```
   SELECT * 的代价 = 行宽 × 命中行数 × (是否回表)

   小表 + 少行  → 无所谓，可读性优先
   宽表 / 大结果集 / 高频接口 → 必须写明字段，争取覆盖索引
```

另外 `SELECT *` 还有两个隐性成本：**加了字段后网络传输和内存悄悄变大**，以及**它永远无法命中覆盖索引**。

## 五、EXPLAIN 字段速查

```sql
EXPLAIN SELECT ...;      -- 或简写 DESC SELECT ...;
EXPLAIN FORMAT=JSON SELECT ...;   -- 想看成本估算细节时用
EXPLAIN ANALYZE SELECT ...;       -- MySQL 8.0.18+，实际执行并给出真实耗时
```

| 字段 | 看什么 | 健康 | 危险 |
|---|---|---|---|
| `select_type` | 查询类型 | `SIMPLE` | `DEPENDENT SUBQUERY`（关联子查询，逐行执行） |
| `table` | 涉及哪张表 | — | — |
| `type` | **访问类型（最重要）** | `const`/`eq_ref`/`ref`/`range` | **`ALL`**、`index` |
| `possible_keys` | 可能用的索引 | — | 有候选却 `key=NULL` → 优化器嫌弃它 |
| `key` | **实际用的索引** | 和预期一致 | `NULL` |
| `key_len` | **用了索引的前几列**（字节数） | 和预期列数吻合 | 比预期短 → 有列没用上 |
| `ref` | 索引和什么做比较 | `const`/字段名 | — |
| `rows` | **估算扫描行数** | 越小越好 | 接近全表行数 |
| `filtered` | 过滤后剩余百分比 | 越大越好 | 很小 → 扫了很多白扫 |
| `Extra` | 附加信息 | `Using index` | `Using filesort`、`Using temporary` |

**`Extra` 的常见取值**：

| 取值 | 含义 | 好坏 |
|---|---|---|
| `Using index` | **索引覆盖**，不回表 | ★ 最好 |
| `Using index condition` | **索引下推 ICP**，在引擎层用索引列先过滤，减少回表 | ✓ 不错 |
| `Using where` | 引擎返回数据后，Server 层还要再过滤 | △ 一般 |
| `Using filesort` | 排序无法用索引完成，要额外排序 | ✗ 想办法让 `ORDER BY` 走索引 |
| `Using temporary` | 用了临时表（常见于 `GROUP BY`、`DISTINCT`） | ✗ 大数据量下很贵 |
| `Using join buffer` | JOIN 没走上索引 | ✗ 给关联字段加索引 |

**排查节奏**：

```
   慢查询日志捞出慢 SQL
        ↓
   EXPLAIN 看 type / key / key_len / rows / Extra
        ↓
   ┌─ type=ALL      → 没索引或索引失效 → 建索引 / 改写 SQL
   ├─ key=NULL      → 优化器不选它 → 看区分度、看类型是否隐式转换
   ├─ key_len 偏短  → 联合索引只用上前几列 → 调整列序
   ├─ rows 很大     → 过滤条件太弱 → 加更有区分度的列
   └─ Extra filesort→ ORDER BY 没走索引 → 把排序列并进联合索引尾部
```

## 六、把三条总结落成动作

### ① 最左前缀匹配，注意索引字段的顺序

```sql
-- 定序三步走
-- 1. 等值条件的列 → 放前面
-- 2. 范围条件 / ORDER BY 的列 → 放最后
-- 3. 等值列内部按区分度从高到低排
SELECT COUNT(DISTINCT type)/COUNT(*), COUNT(DISTINCT name)/COUNT(*) FROM worker;
--     ↑ 越接近 1 区分度越高，越该靠前
```

一个索引尽量服务多条查询：`(type, salary, name)` 一棵树同时覆盖了 `(type)`、`(type,salary)`、`(type,salary,name)` 三种查询——**这也意味着别再单独建它们的前缀索引**。

### ② 触发索引覆盖

```sql
-- 反向设计法：先写查询，再倒推索引
-- 查询：SELECT name, salary FROM worker WHERE type=? ORDER BY salary DESC
--                  ↓          ↓                  ↓              ↓
-- 索引：       想被覆盖    想被覆盖           等值列在前      排序列跟上
-- 结论：KEY (type, salary, name)
```

### ③ 善用 EXPLAIN

```sql
-- 上线前：每条新 SQL 必须 EXPLAIN
-- 上线后：慢查询日志常驻
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;

-- 定期清理零使用的索引（MySQL 8.0）
SELECT object_name, index_name, count_star
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_schema = 'imooc_ecommerce_data'
  AND index_name IS NOT NULL AND count_star = 0;
```

> 最后一个提醒（图里也说了）：**MySQL 索引的选择还与数据量有关**。
> 空表或几十行的表上跑 EXPLAIN，优化器会觉得"全表扫更划算"而不走索引——这不是索引建错了。
> 验证索引效果，**必须先造够数据**（至少几万行），结论才可信。

## 七、每条索引规则的 B+ 树依据

本篇所有规则，都是从 B+ 树的**三个事实**推出来的。对照着看一遍，比背结论牢固得多。

```
   事实 A：树能快，靠"有序 → 可二分"          → 最左前缀、索引失效、列序
   事实 B：二级索引叶子只有【索引列 + 主键】   → 回表、索引覆盖、SELECT *
   事实 C：每个索引 = 一棵独立的完整 B+ 树     → 索引数量、冗余索引、写入代价
```

| 本篇的规则 | 直接原因 | 事实 |
|---|---|---|
| 最左前缀匹配 | 叶子层按列序逐级排序，缺了左边的列就无法二分 | A |
| 联合索引：等值列在前、范围列在后 | 范围列之后的列在该段内是散的，不能再定位 | A |
| `WHERE` 里条件的书写顺序无所谓 | 优化器会重排；决定成败的是**索引定义的列序** | A |
| 列上不能套函数 / 做运算 | 索引里存的是原始值，`DATE(col)` 后的值没有排序关系 | A |
| 不能有隐式类型转换 | 等价于在列上套了转换函数，同上 | A |
| `LIKE '%x'` 失效，`LIKE 'x%'` 可用 | 前缀确定才能定位起点，前导模糊定位不到 | A |
| `key_len` 能反推用了几列 | 每列在索引项里占固定字节，累加即可 | A |
| 争取索引覆盖（`Using index`） | 要的列都在叶子里就不用走第二棵树 | B |
| `SELECT *` 永远无法覆盖 | 二级索引叶子里没有其他列 | B |
| 索引下推 ICP（`Using index condition`） | 无法定位的列**仍在索引里**，可先过滤再回表 | B |
| 不给低区分度列建索引 | 命中行多 → 回表随机 IO 比全表顺序扫还贵 | B |
| 索引数量 ≤ 6 | 每个索引都是一棵要同步维护的树 | C |
| 删掉最左前缀冗余的索引 | 那棵树能做的事，更长的那棵全能做 | C |
| 频繁更新的列不建索引 | 每次更新 = 在树上删旧项 + 插新项 | C |
| 排序列放联合索引尾部可免 `filesort` | 叶子层本来就有序，顺着链表读即可 | A |

**两个"看起来矛盾"的点，用事实一解释就通了**：

```
   Q：为什么建了索引反而不走？
   A：事实 B —— 命中行数超过全表 20~30% 时，
      回表的随机 IO 比全表顺序扫更贵，优化器主动放弃。

   Q：为什么空表上 EXPLAIN 看不到索引生效？
   A：同上 —— 几十行的表全表扫只要一两个页，
      走索引反而要先读 3 层树。这不是索引建错了，是数据量不够。
```

## 八、索引优化 Checklist

**结构层面**
- [ ] 有没有索引是另一个索引的最左前缀？（冗余，删）
- [ ] 每个索引都对应得上一条真实查询吗？
- [ ] 索引列的类型够窄吗？（`char(64)` 当枚举用是典型浪费）
- [ ] 索引数量 ≤ 6？

**查询层面**
- [ ] 联合索引：等值列在前、范围/排序列在后？
- [ ] 高频列表查询能做成覆盖索引吗？（别 `SELECT *`）
- [ ] `ORDER BY` 的列在联合索引尾部，避免 `Using filesort`？
- [ ] 有没有在索引列上套函数 / 做运算 / 隐式类型转换？

**验证层面**
- [ ] 跑过 `EXPLAIN` 吗？`type` 不是 `ALL`？
- [ ] `key_len` 和你预期的列数吻合吗？
- [ ] `Extra` 里有没有 `Using filesort` / `Using temporary`？
- [ ] 验证时表里有足够的数据量吗？（空表的执行计划不作数）

## 九、一句话总纲

> **主键索引的叶子是数据，二级索引的叶子是主键——所以有回表；**
> **联合索引先按第一列排序，所以有最左前缀；**
> **能在索引里拿全数据就不回表，所以要索引覆盖。**
> 其余的，交给 `EXPLAIN` 去验证，别猜。
