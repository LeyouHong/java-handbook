# B+ 树原理：MySQL 索引为什么长这样

> 环境：MySQL 8.0 / InnoDB。这篇回答"**为什么是这个样子**"：为什么不用哈希、不用红黑树、不用 B 树，
> 为什么主键要自增，为什么范围查询能走索引，为什么树只有三层。

## 一、问题的起点：磁盘 IO 才是瓶颈

先建立一个数量级的概念：

```
   CPU 执行一条指令        ≈ 1 ns
   访问一次内存            ≈ 100 ns          （慢 100 倍）
   SSD 随机读一次          ≈ 100 μs = 10万 ns（慢 10 万倍）
   机械硬盘随机读一次       ≈ 10 ms = 1000万 ns（慢 1000 万倍）
```

**数据库的性能问题，本质上是"少读几次磁盘"的问题。** 内存里比较几百次的开销，还不如省下一次磁盘 IO。

所以索引结构的设计目标只有一个：

> **用尽可能少的磁盘 IO 次数，定位到目标数据。**

再看没有索引会怎样：

```sql
SELECT * FROM user WHERE id = 8888888;
```

```
   全表扫描：从第 1 页读到最后一页
   1000 万行 × 1KB = 10 GB = 约 65 万个数据页
   → 最坏要读 65 万次磁盘
```

而有了 B+ 树索引，同样这条查询只需要 **3 次**（还有 2 次通常命中内存）。这就是索引的全部意义。

## 二、结构选型：为什么最后是 B+ 树

数据结构不是凭空选的，是一路淘汰出来的。

### 候选 1：哈希表 —— 等值最快，但只能等值

```
   hash("zhangsan") → 槽位 3 → 直接拿到数据      O(1)，快得不能再快

   ┌───┬───┬───┬───┬───┬───┐
   │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │
   └───┴───┴───┴─┬─┴───┴───┘
                 └→ zhangsan, 25 岁
```

**致命缺陷**：哈希打散了顺序。

```sql
WHERE age > 25              -- ✗ 范围查询做不了，只能全扫
ORDER BY created_at         -- ✗ 排序做不了
WHERE name LIKE 'zhang%'    -- ✗ 前缀匹配做不了
```

> InnoDB 其实**有**哈希索引——"自适应哈希索引"（AHI），由引擎自己判断哪些页访问得频繁而自动建立，
> 你无法手动创建。Memory 引擎才支持显式的 HASH 索引。

### 候选 2：二叉搜索树 —— 会退化成链表

```
   顺序插入 1,2,3,4,5 时：
        1
         \
          2
           \
            3          → 退化成链表，查找 O(n)
             \
              4
```

### 候选 3：平衡二叉树 / 红黑树 —— 树太高

平衡解决了退化问题，但**每个节点只有 2 个分叉**：

```
   1000 万行数据，二叉树高度 = log₂(1000万) ≈ 24 层

   ┌────────────────────────────────────┐
   │  每下降一层 = 一次磁盘随机 IO        │
   │  24 层 = 24 次 IO ≈ 2.4 ms（SSD）   │
   └────────────────────────────────────┘
```

而且更浪费的是：**磁盘的最小读取单位是页（InnoDB 是 16KB）**。红黑树的一个节点只有几十字节，读一次 16KB 的页却只用了其中几十字节，**99.8% 的 IO 都白读了**。

```
   读一个 16KB 的页                     实际用到的
   ┌──────────────────────────────┐    ┌──┐
   │██████████████████████████████│ →  │██│  一个红黑树节点 ≈ 20 字节
   └──────────────────────────────┘    └──┘
              16384 字节                 浪费 99.8%
```

**结论：既然一次必须读 16KB，那就把这 16KB 塞满。** 这就是多路平衡树的动机。

### 候选 4：B 树 —— 方向对了，但还不够

B 树（B-Tree）让每个节点存**多个 key + 多个子指针**，一个节点正好放一页：

```
                    ┌─────────────────────────┐
                    │ [15|data] [56|data] [77|data] │   ← 非叶子节点也存 data
                    └───┬────────┬────────┬───┘
              ┌─────────┘        │        └─────────┐
        ┌─────▼─────┐      ┌─────▼─────┐      ┌─────▼─────┐
        │[5|d] [9|d]│      │[20|d][30|d]│     │[88|d][95|d]│
        └───────────┘      └───────────┘      └───────────┘
```

树高确实降下来了，但有**两个硬伤**：

**硬伤 1：非叶子节点存了数据，扇出被拉低**

```
   一页 16KB 固定不变：

   B 树非叶子节点：  一项 = key(8B) + 页号(6B) + 【整行数据(1KB)】≈ 1KB
                    → 一页只能放 16 项，扇出 = 16

   B+ 树非叶子节点： 一项 = key(8B) + 页号(6B) = 14B     ← 不存数据！
                    → 一页能放 1170 项，扇出 = 1170

                    扇出差 73 倍 → 同样的数据量，树高差好几层
```

**硬伤 2：范围查询要反复回溯**

```
   B 树查 15 ~ 50：
   找到 15（在中间层） → 回到父节点 → 下钻找 20 → 回溯 → 下钻找 30 ...
   中序遍历，来回上下跳，随机 IO
```

### 最终答案：B+ 树

B+ 树在 B 树上改了两处，正好把这两个硬伤都补掉：

```
   改动 ①：数据只存在叶子节点，非叶子节点只当"路标"
   改动 ②：所有叶子节点用双向链表串起来
```

```
   ┌─ 根 ──────────────────────────────────────┐
   │  15   │ 56   │ 77    只有 key + 子页号     │
   └──┬──────┬──────┬──────────────────────────┘
      ▼      ▼      ▼
   ┌─ 中间层 ──────────────────────────────────┐
   │ [15│20│49]  [56│60│70]  [77│88│95]  只有路标│
   └──┬───┬───┬────────────────────────────────┘
      ▼   ▼   ▼
   ┌─ 叶子层 ──────────────────────────────────┐
   │ [15,18] ⇄ [20,30] ⇄ [49,50] ⇄ [56,60] ⇄ … │
   │  ↑ 完整数据都在这一层，从左到右全局有序      │
   └────────────────────────────────────────────┘
```

这张图有两个地方最容易看不懂，下一节用具体数据专门拆开讲：
**① 上层的 key 和下层到底怎么对应；② 叶子页里一行数据具体怎么存。**

**B+ 树带来的四个特性**，正好对应索引的四类用法：

| 特性 | 带来什么 |
|---|---|
| 非叶子只存 key → 扇出极大 | 树高只有 3~4 层，等值查询 3 次 IO |
| 数据全在叶子层 | **每次查询的 IO 次数完全一致**，性能稳定可预测 |
| 叶子层双向链表 | 范围查询 `>` `BETWEEN`、`ORDER BY`、分页只需**顺序扫**，不回溯 |
| 叶子层全局有序 | `ORDER BY` 可以直接免掉 `filesort` |

### 一张对比表收尾

| 结构 | 等值查询 | 范围查询 | 排序 | 树高（1000万行） | MySQL 用它吗 |
|---|---|---|---|---|---|
| 哈希表 | O(1) ★ | ✗ 不支持 | ✗ | — | 自适应哈希索引 / Memory 引擎 |
| 二叉搜索树 | 可能 O(n) | 慢 | ✓ | 最坏 1000 万 | ✗ |
| 红黑树 | O(log₂n) | 慢 | ✓ | ≈ 24 层 | ✗（Java HashMap 用） |
| B 树 | O(log_m n) | 要回溯 | 一般 | ≈ 6~7 层 | MongoDB 用 |
| **B+ 树** | O(log_m n) | **★ 顺序扫** | **★ 天然有序** | **3~4 层** | **✓ InnoDB** |
| 跳表 | O(log n) | ✓ | ✓ | 内存友好但层数多 | Redis ZSet / RocksDB |

> **还有另一条技术路线**：B+ 树是"写的时候就把数据放到该在的位置"，整理成本前置。
> 而 LSM Tree（RocksDB / HBase / TiKV）反过来——**写入只追加到内存和日志就返回，
> 整理全部交给后台慢慢做**。
> 想了解它，见《[LSM Tree 原理：从零造一个 KV 存储](../storage/LSM树原理.md)》。

## 三、把这棵树完整地拆开看

上面那张图是"简笔画"，省略了两个最关键的信息。这一节用一批具体数据把它彻底摊开。

### 3.1 先约定一张表和 6 行数据

```sql
CREATE TABLE worker (
  id     BIGINT      NOT NULL AUTO_INCREMENT,   -- 主键
  salary BIGINT      NOT NULL DEFAULT 0,
  name   VARCHAR(32) NOT NULL DEFAULT '',
  PRIMARY KEY (id)
);
```

表里的数据（**按主键 id 排好序**，B+ 树里就是这个顺序）：

```
   ┌─────┬────────┬──────┐
   │ id  │ salary │ name │
   ├─────┼────────┼──────┤
   │ 15  │   34   │ zhu  │
   │ 18  │   77   │ fei  │
   │ 20  │    5   │ kun  │
   │ 30  │   91   │ biao │
   │ 49  │   22   │ yw   │
   │ 50  │   89   │ yz   │
   └─────┴────────┴──────┘
```

### 3.2 疑问一：叶子页里的"三行"到底是什么

课件（和我上面的简笔画）把叶子页画成三行竖排，非常容易误解：

```
   ✗ 容易误解的画法              这三行【不是三条记录】，
   ┌──────────┐                 而是【一条记录被转置竖着写】：
   │ 15    18 │  ← id           第 1 列 = (15, 34, zhu)
   │ 34    77 │  ← salary       第 2 列 = (18, 77, fei)
   │ zhu  fei │  ← name         整页一共只有【2 条记录】
   └──────────┘
```

**摊平了画才是它真实的样子**——一条记录横着存，一页里若干条记录按主键从小到大排：

```
   ┌────────────── 叶子页 #100（16KB）─────────────────┐
   │                                                    │
   │  记录1: [ id=15 | salary=34 | name='zhu' ]        │
   │              ↓ 页内单向链表                        │
   │  记录2: [ id=18 | salary=77 | name='fei' ]        │
   │                                                    │
   │  （真实的页能放几百上千条，这里只画 2 条示意）        │
   └────────────────────────────────────────────────────┘
```

**一条记录在磁盘上的真实布局**（InnoDB COMPACT 行格式，聚簇索引叶子）：

```
   一条记录在页里，从左到右是这么排的：

   ┌─ 头部信息（存储引擎自用）────────────────────────────────┐
   │  变长字段长度列表  ·  NULL 标志位  ·  记录头 (5 字节)      │
   └──────────────────────────────────────────────────────────┘
   ┌─ 真实数据 ───────────────────────────────────────────────────────┐
   │  主键 id (8B)  ·  trx_id (6B)  ·  roll_ptr (7B)  ·  salary  ·  name │
   └──────────────────────────────────────────────────────────────────┘
        ↑                  └──────────┬──────────┘         └────┬────┘
    主键排在最前         InnoDB 自动加的两个隐藏列        你定义的其余业务列
    （所以按它排序）      事务 id + 回滚指针，MVCC 用
```

所以"叶子节点存整行数据"这句话，落到字节上就是：**主键 + 两个隐藏的事务字段 + 所有其他列，全都躺在这一页里**。查到这条记录，`SELECT *` 要的东西一次性全拿到，不用再去别处找。

### 3.3 疑问二：上层的 key 和下层怎么对应

**核心规则只有一句：**

> **非叶子节点里的每个 key，就是它所指向的那个子页里的最小 key。**

非叶子节点里的每一项，都是一对 `(最小key, 子页号)`。把页号标出来，一层一层看就清楚了。

**第 1 层 → 第 2 层**

```
                             根页 #1
        ┌─────────────────────────────────────────┐
        │ [15 -> #10] [56 -> #11] [77 -> #12]     │
        └───────┬───────────┬───────────┬─────────┘
                ▼           ▼           ▼
           中间页 #10   中间页 #11   中间页 #12
```

```
   根页里的项        指向        这个子页里最小的 key 是
   ─────────────────────────────────────────────────
   [15 -> #10]   ────────→   #10 的最小 key = 15   ✓ 对上了
   [56 -> #11]   ────────→   #11 的最小 key = 56   ✓
   [77 -> #12]   ────────→   #12 的最小 key = 77   ✓
```

**第 2 层 → 第 3 层（以 #10 为例）**

```
                          中间页 #10
        ┌──────────────────────────────────────────┐
        │ [15 -> #100] [20 -> #101] [49 -> #102]   │
        └───────┬────────────┬────────────┬────────┘
                ▼            ▼            ▼
          叶子页 #100   叶子页 #101   叶子页 #102
        ┌──┬──┬────┐ ┌──┬──┬────┐ ┌──┬──┬────┐
        │15│34│zhu │ │20│ 5│kun │ │49│22│yw  │
        │18│77│fei │ │30│91│biao│ │50│89│yz  │
        └──┴──┴────┘ └──┴──┴────┘ └──┴──┴────┘
         id salary name        ↑ 每一【横行】= 一条完整记录

        #100 ⇄ #101 ⇄ #102 ⇄ #103 ...  ← 叶子页之间由双向链表串联
```

```
   中间页 #10 里的项      指向        这个叶子页里最小的 id 是
   ────────────────────────────────────────────────────
   [15 -> #100]   ───────→   #100 的第一条记录 id = 15   ✓
   [20 -> #101]   ───────→   #101 的第一条记录 id = 20   ✓
   [49 -> #102]   ───────→   #102 的第一条记录 id = 49   ✓
```

**上下层的对应关系，就是这么一条一条对起来的**：上层的每个 key，等于它指向的那一页里的第一个（最小的）key。

对着这两组图，之前的困惑就都能解释了：

**Q：为什么根是 `15|56|77`，中间层是 `15|20|49`，看起来对不上？**

因为它们描述的粒度不同：

```
   根页的 3 个指针分别指向 3 个【中间页】
      → 所以根里记的是这 3 个中间页各自的最小 key：15、56、77

   中间页 #10 的 3 个指针分别指向 3 个【叶子页】
      → 所以它记的是这 3 个叶子页各自的最小 key：15、20、49
```

**Q：为什么 15 在三层里都出现了？**

因为 15 是全表最小的 id。最小值会沿着**最左那条路径**一路"冒"到根：#100 的最小值是 15 → #10 的最小值就是 15 → 根的第一项就是 15。同理，如果去看最右边，最大的那个 key 只会出现在叶子层，因为它不是任何子树的"起点"。

**Q：上层的 15、20、49 是数据吗？**

不是。它们只是**路标（分界值）**，只占 `8 字节 key + 6 字节页号 = 14 字节`，没有 `salary` 和 `name`。id=15 这一行的真实数据只有一份，就在叶子页 #100 里。

> 这正是 B+ 树相对 B 树的核心改动：**非叶子节点不存数据，所以一页能塞 1170 个路标**，
> 树才能矮到 3 层。

### 3.4 完整走一遍：`WHERE id = 30`

区间判断规则：**在当前页里找"最后一个 ≤ 目标值的 key"，走它的指针**。

```
   Step 1  读根页 #1：[15→#10] [56→#11] [77→#12]
           30 >= 15 ✓ ， 30 >= 56 ✗
           → 最后一个 ≤ 30 的 key 是 15  → 走 #10
                              │
                              ▼
   Step 2  读中间页 #10：[15→#100] [20→#101] [49→#102]
           30 >= 15 ✓ ， 30 >= 20 ✓ ， 30 >= 49 ✗
           → 最后一个 ≤ 30 的 key 是 20  → 走 #101
                              │
                              ▼
   Step 3  读叶子页 #101：id=20 那条、id=30 那条
           页内定位到 id=30  →  拿到整行 (30, 91, biao)   ✓ 完成

   一共读了 3 个页 = 3 次 IO（前两个几乎必然已在内存）
```

### 3.5 再走一遍范围查询：`WHERE id BETWEEN 18 AND 49`

```
   Step 1~3  和上面一样下钻，定位到起点 id=18 所在的叶子页 #100
   Step 4    从 18 开始，沿【叶子层双向链表】一路向右读：

   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
   │ #100         │ ⇄ │ #101         │ ⇄ │ #102         │
   │ 15 │ 34 │zhu │   │ 20 │  5 │kun │   │ 49 │ 22 │ yw │
   │ 18 │ 77 │fei │   │ 30 │ 91 │biao│   │ 50 │ 89 │ yz │
   └──────────────┘   └──────────────┘   └──────────────┘
          ▲起点18 ───────────→ 20,30 ─────────→ 49 停 ✗50 超了
          └────────── 顺序 IO，不用再回根节点 ──────────┘
```

**这就是叶子层双向链表的全部价值**：找到起点之后，剩下的全是顺序扫，一次都不用再爬回上层。B 树做同样的事要不停地上下回溯。

### 3.6 二级索引的图长什么样

同一张表，如果在 `name` 上再建一个索引，会**再长出一棵独立的 B+ 树**，规则完全一样，只是两处不同：**排序依据变成 name**，**叶子里存的不是整行而是主键 id**。

```
   索引 idx_name 的树（按 name 排序）

                    根：[biao→…] [kun→…] [yw→…]
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
          ┌──────────────────┐  ┌──────────────────┐
          │ biao │ 30 │      │  │ kun  │ 20 │      │   ← 叶子 = (name, 主键id)
          │ fei  │ 18 │      │⇄ │ yw   │ 49 │      │      没有 salary！
          │ zhu  │ 15 │      │  │ yz   │ 50 │      │
          └──────────────────┘  └──────────────────┘
                                        │
   SELECT * FROM worker WHERE name='yw' │ 拿到 id=49
                                        ▼
   ┌──────── 回到聚簇索引那棵树，按 id=49 再查一次 ────────┐
   │  根#1 → 中间#10 → 叶子#102 → (49, 22, yw)  ← 回表    │
   └──────────────────────────────────────────────────────┘
```

**回表 = 走完第一棵树再走第二棵树。** 如果查询只要 `name` 和 `id`（`SELECT id FROM worker WHERE name='yw'`），第一棵树就够了——这就是**索引覆盖**，`EXPLAIN` 里的 `Using index`。

## 四、算一笔账：3 层为什么能装 2000 万行

这个计算值得亲手算一遍，因为它是"单表 2000 万"这个经验数字的来源。

**前提**：InnoDB 页大小 16KB = 16384 字节（`innodb_page_size`，默认值）。

```sql
SHOW VARIABLES LIKE 'innodb_page_size';   -- 16384
```

**第一步：算非叶子节点的扇出（一页能放多少个指针）**

```
   一个索引项 = 主键值 + 子页号
              = BIGINT 8 字节 + 页号 6 字节
              = 14 字节

   扇出 = 16384 / 14 ≈ 1170
```

**第二步：算叶子节点能放多少行**

```
   假设一行数据 1KB（含各字段 + 行头开销）
   一页能放 = 16384 / 1024 = 16 行
```

**第三步：逐层相乘**

```
   ┌─────────────────────────────────────────────────────────┐
   │  1 层（只有根，根即叶子）：            16 行              │
   │                                                          │
   │  2 层：1170 × 16                =  18,720 行 ≈ 1.8 万    │
   │                                                          │
   │  3 层：1170 × 1170 × 16         = 21,902,400 行 ≈ 2190 万 │ ← 常说的 2000 万
   │                                                          │
   │  4 层：1170 × 1170 × 1170 × 16  = 约 256 亿行            │
   └─────────────────────────────────────────────────────────┘
```

**第四步：这意味着什么**

```
   3 层树查一行：
   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │  根页    │ → │  中间页   │ → │  叶子页   │
   │ 常驻内存 │   │ 大概率内存│   │ 可能读盘  │
   └──────────┘   └──────────┘   └──────────┘
      0 次 IO        0 次 IO        1 次 IO

   实际上根节点和中间层加起来才 1170 页 × 16KB ≈ 18 MB，
   Buffer Pool 随便装得下 → 千万级表查一行，通常只有 1 次磁盘 IO。
```

**关键推论：树高是行宽的函数**

| 单行大小 | 叶子每页行数 | 3 层容量 |
|---|---|---|
| 200 B（窄表） | 80 | **约 1.1 亿行** |
| 1 KB | 16 | 约 2190 万行 |
| 4 KB（宽表，塞了 TEXT） | 4 | **约 550 万行** |

> 所以"单表不超过 2000 万"从来不是硬规定，**行越窄，单表能撑的行数越多**。
> 这也解释了《[数据表设计](数据表设计.md)》里"字段不宜过多、大字段拆出主表"那一条的真正原因。

**顺带解释一个限制**：InnoDB 要求一页至少能放下 2 行，所以**单行最大约 8000 字节**（16KB 的一半）。超出部分的 VARCHAR/TEXT 会被挪到溢出页（off-page），行内只留 20 字节的指针。

## 五、查询过程：三层定位 + 页内二分

### 5.1 等值查询 `WHERE id = 30`

```
   Step 1  根页：30 落在 [15, 56) 区间 → 走第 1 个指针
           ┌──────────────────────────┐
           │  15  │  56  │  77  │     │
           └───┬──┴──────┴──────┴─────┘
               │ 30 >= 15 且 < 56
   Step 2  中间页：30 落在 [20, 49) → 走第 2 个指针
           ┌──────────────────────────┐
           │  15  │  20  │  49  │     │
           └──────┴───┬──┴──────┴─────┘
                      │
   Step 3  叶子页：页内查找 id=30，拿到整行
           ┌────────────────┐
           │ 20 │ 30 │ ...  │   ← 找到了
           └────────────────┘
```

### 5.2 页内不是线性扫描：Page Directory 二分查找

一页 16KB 里可能有上百条记录，逐条比较也很慢。InnoDB 在页内做了两层结构：

```
   ┌─────────────── 一个 16KB 数据页 ───────────────────────┐
   │ File Header │ Page Header │                            │
   ├────────────────────────────────────────────────────────┤
   │  User Records（按主键有序的【单向链表】）                 │
   │                                                         │
   │  Infimum → [id=15] → [id=18] → [id=20] → ... → Supremum │
   │              ↑                    ↑                     │
   ├──────────────┼────────────────────┼─────────────────────┤
   │  Page Directory（稀疏槽位，每 4~8 条记录一个槽）          │
   │      slot0 ──┘      slot1 ────────┘      slot2 ...      │
   ├────────────────────────────────────────────────────────┤
   │ File Trailer                                            │
   └────────────────────────────────────────────────────────┘

   页内查找 id=20：
   ① 对 Page Directory 的槽做【二分查找】→ 定位到 slot1 所在的小分组
   ② 在这个 4~8 条记录的小组里沿单向链表【线性扫】→ 命中
```

**所以完整的查找路径是**：树上三次二分下钻 → 页内一次二分 → 组内几次比较。全程内存里的比较很便宜，真正的成本只有那 1~3 次页读取。

### 5.3 范围查询 `WHERE id BETWEEN 20 AND 60`

这是 B+ 树相对 B 树的杀手锏：

```
   Step 1  正常下钻找到 id=20 所在的叶子页（3 次 IO）
   Step 2  沿【叶子层双向链表】一路向右顺序扫，直到超过 60

   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
   │ 15  18 │←→ │ 20  30 │←→ │ 49  50 │←→ │ 56  60 │←→ │ 77 ... │
   └────────┘   └───▲────┘   └────────┘   └───┬────┘
                    │ 起点                     │ 终点
                    └─────── 顺序扫，磁盘顺序 IO ┘
```

**顺序 IO 比随机 IO 快一个数量级**，而且 InnoDB 还会触发预读（read-ahead）提前把后面的页加载进内存。

这同时解释了另外三件事：

```
   ORDER BY id                 → 叶子层本来就有序，直接顺序读，免 filesort
   ORDER BY id DESC            → 双向链表，反向读一样快
   WHERE name LIKE 'zhang%'    → 前缀匹配等价于范围查询，能走索引
   WHERE name LIKE '%zhang'    → 无法确定起点，索引失效
```

### 5.4 为什么深分页很慢

```sql
SELECT * FROM worker ORDER BY id LIMIT 1000000, 10;
```

```
   B+ 树没有"第 N 条"这种随机访问能力，只能从头顺着叶子链表数：
   ┌────┐   ┌────┐        ┌────────┐
   │  1 │→→→│  2 │→→ ... →│1000000 │→ 才开始取 10 条
   └────┘   └────┘        └────────┘
        扫描 + 丢弃 100 万行
```

**优化：改成"用主键定位起点"**，把 offset 换成 where：

```sql
-- ✓ 记住上一页最后一个 id，直接定位（3 次 IO 到起点，再顺序扫 10 条）
SELECT * FROM worker WHERE id > 1000000 ORDER BY id LIMIT 10;

-- ✓ 或用延迟关联：先在索引里翻页（覆盖索引，不回表），再回表取 10 行
SELECT w.* FROM worker w
JOIN (SELECT id FROM worker ORDER BY id LIMIT 1000000, 10) t ON w.id = t.id;
```

## 六、插入与页分裂：为什么主键必须自增

### 6.1 正常插入

插入时先定位到该去的叶子页，页内有空间就直接放进去（并维护页内链表和 Page Directory）。

### 6.2 页满了 → 页分裂

```
   假设一页只能放 4 条（示意），现在要插入 id=25

   分裂前：页已满
   ┌─────────────────────┐
   │ 20 │ 30 │ 40 │ 50 │ │   ← 没地方放 25 了
   └─────────────────────┘

   分裂后：申请新页，搬走一半数据
   ┌───────────┐        ┌───────────┐
   │ 20 │ 25 │ │  ←→    │ 30 │ 40 │ 50 │
   └───────────┘        └───────────┘
        ↑                     ↑
   两个页都只有 50% 填充率 → 空间浪费、树可能长高
   同时还要修改父节点、修改前后页的双向链表指针 → 一次分裂牵动多个页
```

**页分裂的代价**：额外的页申请、数据搬迁、父节点更新、链表指针维护，而且分裂后两个页都是半满的，**磁盘空间利用率掉到 50%**。

### 6.3 自增主键 vs 随机主键（UUID）

```
   自增主键（有序追加）                    UUID / 随机字符串

   ┌──────────┐  ┌──────────┐            ┌──────────┐  ┌──────────┐
   │ 1 2 3 4  │→ │ 5 6 _ _  │            │ a3.. f1..│  │ 2c.. 9b..│
   └──────────┘  └──────▲───┘            └────▲─────┘  └──────────┘
                        │                     │
                 新记录总是追加到          新记录随机插到任何一个
                 最右边的那个页            已经写满的页中间
                        ↓                     ↓
              ✓ 不触发分裂                ✗ 频繁页分裂
              ✓ 只有最右页是"热页"，       ✗ 所有页都可能被写，
                容易常驻内存                 Buffer Pool 命中率低
              ✓ 页填充率接近 100%          ✗ 页填充率长期在 50~70%
              ✓ 磁盘顺序写                 ✗ 磁盘随机写
```

> InnoDB 对顺序插入做了专门优化：检测到是在最右侧追加时，不做 50/50 对半分裂，
> 而是直接开一个新页放新记录，让原页保持满页——这就是自增主键几乎不产生碎片的原因。

**这就是"主键必须单调递增"这条规范的底层依据**。分库分表用不了 `AUTO_INCREMENT` 时，要用**趋势递增**的雪花 ID（高位是时间戳），而不是随机 UUID。

### 6.4 删除与页合并

InnoDB 删除记录时**不立刻搬数据**，只是打一个 `deleted_flag` 标记，把空间挂到页的"空闲链表"上等待复用。

当一个页的填充率低于阈值（`MERGE_THRESHOLD`，默认 50%）时，才会尝试和相邻页合并：

```
   ┌──────────┐  ┌──────────┐          ┌──────────────┐
   │ 20 │  _  │  │ 40 │  _  │    →     │ 20 │ 40 │ _ │ │
   └──────────┘  └──────────┘          └──────────────┘
     各 25% 满，相邻                        合并成一页
```

大量增删后页会变得稀疏（碎片），可以重建表来整理：

```sql
OPTIMIZE TABLE worker;         -- InnoDB 下等价于下面这句
ALTER TABLE worker ENGINE=InnoDB;   -- 重建表，重新紧凑排列
```

## 七、InnoDB 的两棵树：聚簇索引与二级索引

B+ 树在 InnoDB 里有两种用法，区别**只在叶子节点存什么**。

```
        聚簇索引（主键索引）                    二级索引（辅助索引）
        叶子 = 整行数据                          叶子 = 主键值

   ┌──────────────────┐                  ┌──────────────────┐
   │  15 │ 56 │ 77    │                  │ zhu │ kun │ yw   │
   └──┬───┴────┴──────┘                  └──┬──┴─────┴──────┘
      │                                     │
   ┌──▼───────────────┐                  ┌──▼───────────────┐
   │ 15  18 │ 20  30  │                  │ zf  zt │ fx  fy  │
   ├────────┼─────────┤                  ├────────┼─────────┤
   │ 34  77 │  5  91  │  ← salary        │ 32  74 │  4  88  │  ← 主键 id
   │ zhu fei│ kun biao│  ← name          └────────┴─────────┘
   └────────┴─────────┘                       只有主键，
      整行数据都在这里                     其他字段要"回表"
```

**回表**：

```sql
SELECT * FROM worker WHERE name = 'yw';
```

```
   ① 走 name 这棵二级索引树（3 次 IO）→ 拿到 id = 61
   ② 拿 id=61 回聚簇索引树再查一次（3 次 IO）→ 拿到整行
                                              ↑
                                    这第二次就是"回表"
```

**由这个结构直接推出的几条规范**（全都能在《[索引优化](索引优化.md)》里找到用法）：

| 规范 | B+ 树层面的原因 |
|---|---|
| 主键要**短** | 每个二级索引的每个叶子项都存着主键，主键胖 1 字节，所有二级索引全体变胖 |
| 索引列要**窄** | 非叶子节点每项 = 索引列 + 页号，列越窄扇出越大，树越矮 |
| 争取**索引覆盖** | 要的列都在二级索引叶子里 → 省掉整棵聚簇索引树的查找 |
| **必须有主键** | 没有主键时 InnoDB 会用第一个唯一非空索引；再没有就自建 6 字节隐藏 `row_id`，且它全局共享，高并发插入是竞争点 |
| 联合索引有**最左前缀** | 叶子层是按 (a,b,c) 依次排序的，a 不确定时 b、c 在全局就是乱序的，无法二分 |

联合索引怎么排、为什么有最左前缀，单独用下一章展开。

---

## 八、联合索引：把多列拼成一个排序键

联合索引是索引里最容易出错的部分。但只要接受**一个设定**，所有规则都能自己推出来：

> **联合索引的 key 不是"三个列"，而是【一个由三列拼成的元组】。**
> 比较两个 key 时，按字典序逐列比：先比第一列，相等才比第二列，再相等才比第三列。

这和查英文字典一模一样：`(A, 1000, li)` 排在 `(A, 2000, wang)` 前面，因为第一列相等、第二列 1000 < 2000。

### 8.1 示例数据

沿用 worker 表，建索引 `idx_tsn (type, salary, name)`，表里 8 行：

```sql
KEY idx_tsn (type, salary, name)
```

```
   按 (type, salary, name) 排好序后的样子（这就是叶子层的顺序）：

   序号  type  salary  name    id       ← id 是主键，二级索引叶子里必然带着它
   ────────────────────────────────
    ①     A    1000    li      7
    ②     A    2000    wang    3        ┐ type=A 这一段内，salary 有序
    ③     A    3000    zhao    9        ┘
    ④     B     500    qian    1        ← type 变成 B，salary 从 500 重新开始
    ⑤     B    2000    qinyi   5        ┐ salary=2000 这一小段内，
    ⑥     B    2000    sun     2        ┘ name 才有序（qinyi < sun）
    ⑦     B    5000    zhou    8
    ⑧     C    1500    wu      4
```

**三条观察**，后面所有结论都来自它们：

```
   观察 1：type   在【整棵树】上有序          → 可以直接二分定位
   观察 2：salary 只在【同一个 type 内】有序   → 必须先定住 type
   观察 3：name   只在【同一个 (type,salary) 内】有序 → 必须先定住前两列
```

### 8.2 这棵树完整长什么样

联合索引也是二级索引，规则和第三章讲的完全一样，只是 key 变成了元组、叶子里存主键：

```
                              根页
        ┌──────────────────────────────────────────┐
        │ [(A,1000,li) -> #20]  [(B,2000,qinyi) -> #21] │   ← key 是【整个元组】
        └────────┬────────────────────┬────────────┘
                 ▼                    ▼
           叶子页 #20            叶子页 #21
   ┌───────────────────┐  ┌───────────────────┐
   │ A │1000│li   │ 7  │  │ B │2000│qinyi│ 5  │
   │ A │2000│wang │ 3  │⇄ │ B │2000│sun  │ 2  │⇄ …
   │ A │3000│zhao │ 9  │  │ B │5000│zhou │ 8  │
   │ B │ 500│qian │ 1  │  │ C │1500│wu   │ 4  │
   └───────────────────┘  └───────────────────┘
     ↑    ↑    ↑     ↑
   type salary name  主键 id ← 没有其他列！要 version 之类的就得回表
```

注意两点：

- **非叶子节点的 key 也是完整元组**（`(A,1000,li)`），不是只有第一列。所以索引列越多越宽，扇出越小，树越容易长高——这是"联合索引别无脑加列"的物理原因。
- 对**非唯一**的二级索引，InnoDB 会把主键追加进 key 里做唯一化，所以真实的排序键其实是 `(type, salary, name, id)`。这个细节在 8.6 讲 `ORDER BY id` 时会用到。

### 8.3 六条 SQL 在树上的走位

**① `WHERE type = 'B'` —— 满血命中**

```
   ①A,1000  ②A,2000  ③A,3000  ④B,500  ⑤B,2000  ⑥B,2000  ⑦B,5000  ⑧C,1500
                                 └──────────────┬──────────────┘
                                    二分定位到 ④，顺序扫到 ⑦ 停
   type=ALL 的 B 连成【一片连续区间】 → 一次定位 + 顺序扫    ✓
   key_len = type 的长度
```

**② `WHERE type='B' AND salary=2000` —— 定位更精确**

```
   ④B,500   ⑤B,2000  ⑥B,2000  ⑦B,5000
             └────┬────┘
        先按 type 定到 B 段，再在段内按 salary 二分   ✓✓
   key_len = type + salary
```

**③ `WHERE type='B' AND salary=2000 AND name='sun'` —— 三列全用上**

```
   ⑤B,2000,qinyi   ⑥B,2000,sun
                     └─ 在 (B,2000) 这一小段内按 name 二分   ✓✓✓
   key_len = type + salary + name          ← 满血，直接定位到唯一一行
```

**④ `WHERE salary = 2000` —— 索引用不上**

```
   ①A,1000  ②A,2000  ③A,3000  ④B,500  ⑤B,2000  ⑥B,2000  ⑦B,5000  ⑧C,1500
              ★                          ★        ★
              └──── 2000 分散在 A 段和 B 段里，中间隔着 3000、500 ────┘

   整棵树上 salary 不是有序的 → 无法二分 → 索引用不上（type=ALL 全表扫）  ✗
```

这就是"最左前缀"的全部真相：**不是 MySQL 规定你必须带上第一列，而是不带第一列时，后面的列在树上根本没有顺序可言。**

**⑤ `WHERE type='B' AND name='sun'` —— 中间断了一列**

```
   ④B,500,qian   ⑤B,2000,qinyi   ⑥B,2000,sun   ⑦B,5000,zhou
   └──────────── type='B' 能定位到这一片 ────────────┘
                                    ★
        但 name 在 B 段内是乱序的（qian → qinyi → sun → zhou 只是碰巧）
        实际顺序由 salary 主导，name 无法二分   ✗

   结果：type 用于定位（key_len 只含 type），
        name 只能对扫出来的 4 行【逐行过滤】
```

不过 name **就在索引里**，所以 MySQL 5.6+ 会用**索引下推（ICP）**在引擎层先过滤掉不匹配的，再回表：

```
   没有 ICP：扫出 4 行 → 全部回表 4 次 → Server 层筛 name → 剩 1 行
   有  ICP：扫出 4 行 → 在索引里就筛掉 3 行 → 只回表 1 次     ✓
            EXPLAIN 的 Extra 显示 Using index condition
```

**⑥ `WHERE type='B' AND salary>1000 AND name='sun'` —— 范围截断**

```
   ④B,500   ⑤B,2000,qinyi   ⑥B,2000,sun   ⑦B,5000,zhou
             └────────── salary>1000 是一个【范围区间】 ──────────┘

   在这个区间里，salary 有 2000、2000、5000 三种值
   → name 的顺序被 salary 打断（qinyi, sun, zhou 跨了不同的 salary）
   → name 无法用于定位，只能 ICP 过滤   ✗

   key_len = type + salary（不含 name）
```

**规律**：

```
   等值列 = 把范围收窄成"一个点"，后面的列在这个点内仍然有序  → 可以继续用
   范围列 = 把范围拉成"一段"，后面的列跨越多个值，顺序被打断  → 到此为止
```

### 8.4 一张走位总表

索引 `(a, b, c)`：

| WHERE 条件 | 定位用到几列 | `key_len` | 说明 |
|---|---|---|---|
| `a=1` | a | a | ✓ |
| `a=1 AND b=2` | a, b | a+b | ✓ |
| `a=1 AND b=2 AND c=3` | a, b, c | a+b+c | ✓ 满血 |
| `b=2 AND a=1` | a, b | a+b | 书写顺序无关，优化器会重排 |
| `a=1 AND c=3` | a | a | 中间断了，c 只能 ICP 过滤 |
| `a=1 AND b>2 AND c=3` | a, b | a+b | 范围截断，c 只能 ICP 过滤 |
| `a>1 AND b=2` | a | a | 同上，b 只能 ICP 过滤 |
| `b=2 AND c=3` | **无** | — | ✗ 缺最左列，索引整个用不上 |
| `a LIKE 'x%'` | a | a | 前缀匹配 = 范围，可用 |
| `a LIKE '%x'` | **无** | — | ✗ 定位不到起点 |
| `a=1 ORDER BY b` | a | a | ✓ 且免 filesort（见 8.6） |

### 8.5 一个例外：`IN` 不会截断后面的列

这是个很多人不知道、但很实用的细节。

```sql
-- 直觉上以为 IN 是"范围"，后面的列该用不上了
WHERE type IN ('A','B') AND salary = 2000
```

实际上**能用上 salary**：

```
   MySQL 把 IN 拆成【多个等值区间】，每个区间内后续列依然有序：

   区间 1：type='A' → 在 A 段内按 salary 二分 → 找到 ②      ✓
   区间 2：type='B' → 在 B 段内按 salary 二分 → 找到 ⑤⑥     ✓

   EXPLAIN：type=range，但 key_len 包含 type + salary
```

对比一下就很清楚：

```
   ✓ WHERE type IN ('A','B') AND salary=2000    → 2 个点，各自内部有序，salary 可用
   ✗ WHERE type > 'A'        AND salary=2000    → 一整段，跨多个 type，salary 不可用
```

**实用推论**：能写成 `IN` 就别写成范围。比如筛状态时 `status IN (1,2,3)` 比 `status < 4` 更能让后续列用上索引。

### 8.6 `ORDER BY` 怎么蹭这棵树

叶子层本来就有序，排序如果能顺着索引读，就能省掉 `filesort`（一次内存/磁盘排序）。

```sql
-- ✓ 免 filesort：type 定位到 B 段，段内 salary 天然有序，顺着链表读就行
SELECT * FROM worker WHERE type='B' ORDER BY salary;

-- ✓ 也免：全部降序 → 反向扫描叶子链表（双向链表的价值）
SELECT * FROM worker WHERE type='B' ORDER BY salary DESC;

-- ✓ 也免：排序列就是索引的第 2、3 列，顺序一致
SELECT * FROM worker WHERE type='B' ORDER BY salary, name;

-- ✗ 要 filesort：salary 在全树上无序（同 8.3 的 ④）
SELECT * FROM worker ORDER BY salary;

-- ✗ 要 filesort：跳过了 salary，name 在 B 段内是乱的
SELECT * FROM worker WHERE type='B' ORDER BY name;

-- ✗ 要 filesort（MySQL 8.0 之前）：一升一降，扫不出这个顺序
SELECT * FROM worker WHERE type='B' ORDER BY salary ASC, name DESC;
--   MySQL 8.0 可以建降序索引来支持：KEY (type, salary ASC, name DESC)
```

一个容易忽略的点，用到 8.2 里那个"主键被追加进 key"的细节：

```sql
-- ✗ 要 filesort：B 段内先按 salary 排，id 是乱的
SELECT * FROM worker WHERE type='B' ORDER BY id;

-- ✓ 免 filesort：前三列都定死了，真实排序键 (type,salary,name,id) 只剩 id 在动
SELECT * FROM worker WHERE type='B' AND salary=2000 AND name='sun' ORDER BY id;
```

**规律**：`ORDER BY` 的列必须是索引里**紧接在等值列之后**的那几列，且方向一致。

### 8.7 列序怎么定：三步法

```
   第 1 步：等值条件的列  →  放最前面
   第 2 步：范围条件 / ORDER BY 的列  →  放最后
   第 3 步：多个等值列之间，按区分度从高到低排
           SELECT COUNT(DISTINCT col)/COUNT(*) FROM t;   ← 越接近 1 越靠前
```

拿一条真实查询走一遍：

```sql
SELECT * FROM worker WHERE type='B' AND salary>2000 ORDER BY salary;
```

```
   ✗ 建成 (salary, type)
   ───────────────────────────
   salary>2000 是范围 → 后面的 type 被截断，用不上
   而且 salary 的区间横跨所有 type，扫描行数暴涨

   ✓ 建成 (type, salary)
   ───────────────────────────
   type='B' 等值定位 → B 段内 salary 天然有序
   → 范围扫描直接命中，ORDER BY 还顺带免了 filesort

   同一条 SQL，列序反一下就是几十倍的差距。
```

**为什么区分度高的列要靠前**：区分度决定了第一次定位能砍掉多少行。

```
   假设 1000 万行，type 只有 3 种值、name 有 900 万种值

   索引 (type, name)：type='B' 先砍到 ~333 万行，再按 name 定位
   索引 (name, type)：name='sun' 直接砍到 ~1 行             ← 效率高得多
```

（当然前提是查询里真的会用 `name` 做等值条件——**索引永远是为查询建的**。）

### 8.8 一个联合索引顶几个用

```
   索引 (a, b, c) 等价于同时拥有：

   ✓ (a)
   ✓ (a, b)
   ✓ (a, b, c)

   ✗ (b)      ✗ (c)      ✗ (b, c)      ✗ (a, c)   ← 常见误解！
```

**`(a, c)` 用不上**，因为 c 的顺序由 b 主导（就是 8.3 的例子 ⑤）。这条经常被记错。

由此得到两条实用结论：

```
   ① 已经有 (a,b,c) 了，就【别再建】 (a) 和 (a,b) —— 纯冗余，白维护一棵树
   ② 如果确实需要单独按 b 查，那要么新建 (b,...) 索引，
      要么调整列序看能不能一棵树同时满足两类查询
```

### 8.9 联合索引必须是三列吗：几列才合适

不是。前面一直用三列只是举例——**2 列起步（1 列就是普通单列索引），MySQL 上限 16 列**。
真正决定列数的是**查询**，不是某个数字。

**先看查询要什么**

```sql
-- 只有这一类查询 → 2 列就够
SELECT * FROM worker WHERE type=? AND salary>?;
KEY (type, salary)

-- 多了按姓名精确查的场景 → 加到 3 列
SELECT * FROM worker WHERE type=? AND salary=? AND name=?;
KEY (type, salary, name)

-- 单列足够 → 别硬凑成联合索引
SELECT * FROM worker WHERE name=?;
KEY (name)
```

**但列数不是越多越好**——多一列的代价在 B+ 树上是实打实的：

```
   索引项 = 所有索引列 + 主键 + 页号

   (type)               ≈ 1 + 8 + 6      = 15 字节  → 扇出 ~1000
   (type,salary,name)   ≈ 1 + 8 + 32 + 8 + 6 = 55 字节 → 扇出 ~290
   再往上堆 3 列         ≈ 100+ 字节               → 扇出 ~160

   扇出降一半 → 同样的数据量，树更容易长到第 4 层 → 每次查询多一次磁盘 IO
```

再叠加写入成本（每次改动被索引的列都要维护这棵树），所以**实践中 2~3 列最常见，超过 4 列就该停下来问一句**。

**一个关键区分：定位列 vs 携带列**

超过 3 列时，多出来的那些往往不是用来"找数据"的，而是为了**不回表**：

```sql
-- 查询：列表页要显示 name 和 version
SELECT name, version FROM worker WHERE type=? ORDER BY salary;

KEY (type, salary, name, version)
     └──┬──┘  └──┬──┘  └─────┬─────┘
     定位列    排序列       携带列
   （WHERE 用）（免 filesort）（只为触发索引覆盖，不参与定位）
```

判断标准很简单：

```
   这一列出现在 WHERE / ORDER BY / GROUP BY 里吗？
        ├─ 是 → 定位列，位置有讲究（等值在前、范围在后，见 8.7）
        └─ 否 → 携带列，只能放最后，纯粹为了省掉回表
```

> 顺带一提：SQL Server / PostgreSQL 有 `INCLUDE` 语法，能把携带列挂在索引外面
> （不进 key、不参与排序、不影响非叶子节点的扇出）。
> **MySQL 没有这个语法**，携带列只能塞进 key 里，所以在 MySQL 里堆列的代价比那两家更高——
> 这也是"MySQL 的联合索引不宜太长"的一个额外理由。

**三条硬限制**

| 限制 | 值 |
|---|---|
| 单个索引最多列数 | **16** |
| 索引 key 总长度 | **3072 字节**（InnoDB DYNAMIC 行格式） |
| 单列前缀长度 | 同上，`utf8mb4` 下 `VARCHAR(768)` 就顶满了 |

**实用结论**

```
   1~2 列   最常见，先满足最高频的那条查询
   3 列     典型的「等值 + 等值/范围 + 排序」组合
   4~5 列   通常是为了覆盖索引，最后几列是携带列
   > 5 列   停下来想想：是不是该拆成两个索引，或者该少查几个字段
```

### 8.10 用 `key_len` 验证你的判断

前面所有"用上了几列"的结论，都不用猜——`EXPLAIN` 的 `key_len` 会告诉你。

```
   每列的 key_len = 类型字节数
                  + 1（该列允许 NULL）
                  + 2（变长类型如 VARCHAR）
```

以 `worker(type CHAR(64) NOT NULL, salary BIGINT NULL, name CHAR(64) NOT NULL)`、`CHARSET=utf8` 为例：

```
   type   = 64 × 3        = 192
   salary = 8 + 1（可空）  =   9
   name   = 64 × 3        = 192

   key_len = 192  → 只用上 type
   key_len = 201  → 用上 type + salary
   key_len = 393  → 三列全用上
```

```sql
-- 实测：改一改条件，看 key_len 怎么变
EXPLAIN SELECT * FROM worker WHERE type='B';                              -- 192
EXPLAIN SELECT * FROM worker WHERE type='B' AND salary=2000;              -- 201
EXPLAIN SELECT * FROM worker WHERE type='B' AND salary=2000 AND name='s'; -- 393
EXPLAIN SELECT * FROM worker WHERE type='B' AND salary>2000 AND name='s'; -- 201 ← 被范围截断
EXPLAIN SELECT * FROM worker WHERE type IN ('A','B') AND salary=2000;     -- 201 ← IN 不截断
```

**最后一行和倒数第二行的对比，是这一整章最值得记住的实验。**

### 8.11 本章小结

```
   联合索引 = 把多列拼成一个元组，按字典序排成一棵树
        ↓
   ┌─ 前面的列取【等值】 → 范围收窄成一个点 → 后面的列在点内仍有序 → 可继续定位
   ├─ 前面的列取【范围】 → 范围拉成一段     → 后面的列顺序被打断   → 只能 ICP 过滤
   └─ 缺了最左的列       → 整棵树上无序     → 索引完全用不上
        ↓
   列序三步法：等值列在前（按区分度排）→ 范围/排序列在后
        ↓
   用 EXPLAIN 的 key_len 验证，别靠猜
```

## 九、动手观察

### 9.1 看页大小和表的实际空间

```sql
SHOW VARIABLES LIKE 'innodb_page_size';        -- 16384

SELECT table_name,
       table_rows                     AS `估算行数`,
       ROUND(data_length/1024/1024)   AS `数据 MB`,
       ROUND(index_length/1024/1024)  AS `索引 MB`,
       ROUND(data_length/NULLIF(table_rows,0)) AS `平均行字节`
FROM information_schema.tables
WHERE table_schema = 'imooc_ecommerce_data';
```

拿到"平均行字节"后，就能自己套第四章的公式估树高了：

```
   叶子每页行数 = 16384 / 平均行字节
   3 层容量     = 1170 × 1170 × 叶子每页行数
```

### 9.2 从 Buffer Pool 里看索引页

```sql
SELECT index_name, page_type, COUNT(*) AS pages
FROM information_schema.innodb_buffer_page
WHERE table_name LIKE '%worker%' AND page_type = 'INDEX'
GROUP BY index_name, page_type;
```

> 想精确看到每一层的页号和 `PAGE_LEVEL`，需要外部工具（如 `innodb_ruby` 的
> `space-index-pages-summary`）直接解析 ibd 文件，MySQL 本身没有内置命令。
> 日常用第四章的公式估算就够了。

### 9.3 验证树高对性能的影响

```sql
-- 造数据后对比：窄表 vs 宽表在同样行数下的 IO 差异
EXPLAIN ANALYZE SELECT * FROM worker WHERE id = 8888888;   -- 8.0.18+ 给出真实耗时
```

> 注意：**空表或几十行的表上，优化器会认为全表扫更划算而不走索引**，
> 这不是索引建错了。验证任何索引结论前，先造够数据（至少几万行）。

## 十、一图总结

```
   磁盘 IO 慢 10 万倍
        ↓
   目标：用最少的 IO 次数定位数据
        ↓
   磁盘按页（16KB）读 → 一个节点就该占满一页 → 多路平衡树
        ↓
   非叶子节点不存数据 → 扇出 1170 → 树高只有 3 层  ┐
   数据全在叶子层     → 每次查询 IO 次数恒定        ├→ B+ 树
   叶子层双向链表     → 范围查询/排序顺序扫         │
   叶子层全局有序     → ORDER BY 免 filesort        ┘
        ↓
   ┌────────────────────────┬────────────────────────┐
   │ 聚簇索引：叶子 = 整行   │ 二级索引：叶子 = 主键   │
   └────────────────────────┴────────────────────────┘
        ↓                            ↓
   主键要自增（避免页分裂）      回表 → 所以追求索引覆盖
   主键要短（二级索引全跟着胖）  联合索引有最左前缀（排序的必然结果）
```

**一句话**：

> B+ 树的每一个设计——非叶子不存数据、叶子双向链表、按页组织——
> 都是为了同一件事：**把磁盘 IO 次数压到 3 次以内，并且让范围查询变成顺序扫**。
> 记住这两点，索引的所有"规则"都能自己推出来，不用背。
