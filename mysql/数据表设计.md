# 数据表设计：原则、经验与技巧

> 环境假设：MySQL 8.0 / InnoDB / `utf8mb4`。文中 DDL 都能直接跑。
> 这篇讲的是**建表之前**的事——表结构一旦上线、数据长到千万级，改一个字段类型的代价远超建表时多想的那十分钟。
>
> 全文由两条线组成：
> - **上半部分（原则）**：建表时该从哪六个维度思考
> - **下半部分（经验）**：踩过坑之后留下的四条硬规矩

```
              │  业务分析   │  面向未来             │  DB 约束    │  面向引擎
              └─────┬──────┘                      └─────┬──────┘
          ┌─────────┼─────────┐              ┌──────────┼──────────┐
          ▼         ▼         ▼              ▼          ▼          ▼

      │数据量  │ │数据关系│ │数据规范│      │命名规范│  │字段类型│  │ 索引  │
      └───────┘ └───────┘ └───────┘      └───────┘  └───────┘  └───────┘
       未来 3~5   1:1 1:N   公司/业务       统一、可     最小、      单列
       年的增长   N:N 冗余   的特殊约定      预测        可用       多列/唯一

                               ↓ 落地时受这四条约束

   经验 = 血泪教训，具体的红线
   ① 字段 ≤ 20 个，多了拆表或 JSON
   ② 全部 NOT NULL，空值用无意义值填充
   ③ 索引 ≤ 6 个，随业务迭代持续调整
   ④ 不追求严格精简，冗余换查询
```

两条线的区别在于**改错的成本**：

| | 业务分析 | DB 约束 |
|---|---|---|
| 决定什么 | 分不分表、几张表、字段冗不冗余 | 叫什么名、什么类型、建什么索引 |
| 改错的代价 | **极高**——迁数据、改代码、双写、灰度 | 中等——`ALTER TABLE` 一般能救回来 |
| 什么时候想 | 写第一行 DDL 之前 | 写 DDL 的时候 |

注意经验 ③ 和 ④ 有点反直觉：**索引要克制，冗余要放开**。原因很简单——索引是写入成本，每写一行要维护 N 棵树；冗余是存储成本，而磁盘是所有资源里最便宜的。

# 第一部分：设计原则

## 一、业务分析

### 1.1 数据量：按未来的增长预期设计

建表时最该问的不是"现在有多少数据"，而是**"三年后有多少"**。

先算一笔账，看看为什么大表会慢。InnoDB 的索引是 B+ 树，数据页固定 16KB：

```
   B+ 树 3 层能装多少行？（粗算）

   非叶子节点：一页 16KB，一条索引项 ≈ 主键 8B + 页号 6B = 14B
              → 一页约 16384/14 ≈ 1170 个子节点指针

   叶子节点：  一页 16KB，一行数据 ≈ 1KB
              → 一页约 16 行

   3 层：1170 × 1170 × 16 ≈ 2190 万行     ← 查一行只要 3 次 IO（上两层通常在内存里）
   4 层：再乘 1170 ≈ 256 亿行             ← 每次查询多一次磁盘 IO
```

这就是"单表 2000 万"这个经验数字的由来——**它不是硬阈值，而是行宽的函数**。行越宽（大 VARCHAR、TEXT 塞在主表里），一页装的行越少，树越早长到第 4 层。所以行窄的表几千万行照样很快，行宽的表几百万就开始难受。

**估算模板**：

| 要素 | 怎么估 | 例 |
|---|---|---|
| 日增量 | 日活 × 人均产生条数 | 10 万 DAU × 0.3 单 = 3 万单/天 |
| 3 年总量 | 日增 × 365 × 3 × 增长系数 | 3 万 × 1095 × 2 ≈ **6600 万** |
| 单行大小 | 各字段字节数相加 | ≈ 300 B |
| 表大小 | 总量 × 单行 × 1.5（索引/碎片） | 6600 万 × 300B × 1.5 ≈ **30 GB** |

**根据估算结果决定形态**：

```
   < 500 万         单表，把索引建对就行
   500 万 ~ 2000 万  单表 + 冷热分离（历史数据归档到 xxx_history）
   2000 万 ~ 1 亿    分区表 / 单库分表（按时间或 hash）
   > 1 亿            分库分表，此时分片键的选择 >> 一切
```

**分表要在建表时就留好后路**，哪怕现在不分：

- 主键别用 `AUTO_INCREMENT`——分表后全局 ID 会冲突。留好雪花 ID（`BIGINT`）的位置。
- 想好**分片键**：订单表按 `user_id` 分（C 端查"我的订单"快）还是按 `order_id` 分（按单号查快）？
  这个选择决定了哪类查询会变成"扫所有分片"，是分表设计里最贵的一个决定。
- 分片键必须出现在绝大多数查询的 `WHERE` 里，否则等于没分。

> 反过来也要克制：日活 1000 的内部系统别一上来就分 128 张表。**过度设计的成本是长期的复杂度。**

### 1.2 数据关系：1:1 / 1:N / N:N

先把 E-R 图理清楚，再决定几张表。三种关系的落地方式是固定的：

```
   1:1   用户 ── 用户详情       → 可以合成一张表；
                                 拆开的理由只有两个：字段太宽（拉低主表页密度）、
                                 或访问频率差异大（详情很少查）

   1:N   用户 ──< 订单          → 在"多"的一方存外键列 user_id
                                 （存的是列，不一定建 FOREIGN KEY，见下）

   N:N   订单 >──< 商品         → 必须有中间表 order_item(order_id, product_id, ...)
                                 中间表往往还带自己的业务字段：数量、单价快照
```

**关于范式**：三大范式先满足，再考虑破。

| 范式 | 一句话 | 违反的样子 |
|---|---|---|
| 1NF | 字段不可再分 | `address` 里塞 "省\|市\|区" 靠字符串切 |
| 2NF | 非主键字段完全依赖整个主键 | 联合主键 `(order_id, product_id)` 的表里放了 `order_time`（只依赖 order_id） |
| 3NF | 非主键字段之间不能传递依赖 | 订单表里存 `user_id` 又存 `user_level`（level 依赖 user 而非 order） |

什么时候该反范式，见下半部分的**经验 ④**。

**关于外键（`FOREIGN KEY`）**：互联网业务通常**不建**。

| 不建的理由 | 说明 |
|---|---|
| 性能 | 每次写入要检查父表，高并发下额外加锁 |
| 分库分表 | 跨库外键根本无法工作 |
| 变更 | 删数据、灌数据、迁库时外键处处掣肘 |

代价是**约束交给应用层**（Service 保证 + 定时对账脚本）。金融、内部管理系统数据量不大、正确性优先，那就该建。

### 1.3 数据规范：公司/业务的特殊约定

这一块**没有标准答案，只有团队约定**。但每个团队都应该把这几件事写死。

**(1) 每张表必备的公共字段**

```sql
id          BIGINT UNSIGNED  主键
created_at  DATETIME(3)      创建时间，DEFAULT CURRENT_TIMESTAMP(3)
updated_at  DATETIME(3)      更新时间，ON UPDATE CURRENT_TIMESTAMP(3)
created_by  BIGINT / VARCHAR 操作人（有审计要求时）
deleted_at  BIGINT           逻辑删除标记
version     INT              乐观锁版本号（有并发更新时）
```

**(2) 逻辑删除 vs 物理删除**

业务数据基本都用逻辑删除（可恢复、可审计）。但有个**经典的坑**：

```sql
-- ✗ 逻辑删除 + 唯一索引，天然冲突
is_deleted TINYINT NOT NULL DEFAULT 0,
UNIQUE KEY uk_email (email)
-- 用户 a@x.com 注销（is_deleted=1）后，再也注册不回来了——唯一索引不认 is_deleted

-- ✓ 方案：删除标记参与唯一键，且未删除时取固定值 0
deleted_at BIGINT NOT NULL DEFAULT 0 COMMENT '删除时间戳(ms)，0=未删除',
UNIQUE KEY uk_email_deleted (email, deleted_at)
-- 未删除的行 deleted_at 都是 0 → 邮箱唯一；删除时写入毫秒时间戳 → 让出位置
```

**(3) 状态字段用 `TINYINT` + 注释，不用 `ENUM`**

```sql
-- ✗ ENUM 加一个值要 ALTER TABLE，且各语言驱动处理不一致
status ENUM('CREATED','PAID','SHIPPED')

-- ✓ TINYINT + COMMENT 写清映射，Java 侧用枚举兜住
status TINYINT NOT NULL DEFAULT 0 COMMENT '订单状态 0待支付 1已支付 2已发货 3已完成 4已取消'
```

**(4) 其他常见约定**

- **金额**一律 `DECIMAL(N,2)`，或统一以"分"为单位存 `BIGINT`。**绝不用 `FLOAT`/`DOUBLE`**——二进制浮点存不下 0.1，对账会差钱。
- **时间**一律 `DATETIME(3)`，不用 `TIMESTAMP`（2038 年溢出 + 随会话时区变化）。
- **禁止在主表放大字段**：`TEXT`/`BLOB`/长 JSON 拆到附属表，保护主表的页密度。
- **所有表 / 所有字段必须有 `COMMENT`**——半年后的你和接手的人都需要它。
- 字符集 `utf8mb4`（`utf8` 是 3 字节的假货，存不了 emoji），排序规则全库统一，避免 JOIN 时因排序规则不同导致索引失效。

## 二、DB 约束

### 2.1 命名规范：统一、可预测

命名的唯一目标是**不用查文档就能猜对**。

| 对象 | 规范 | 例 |
|---|---|---|
| 库名 | 业务_模块 | `mall_order` |
| 表名 | 全小写 + 下划线，**单数**名词，模块前缀 | `order_item`、`user_account` |
| 字段 | 全小写 + 下划线，不加表名前缀 | `user.name` 而不是 `user.user_name` |
| 外键列 | `<关联表单数>_id` | `user_id`、`product_id` |
| 布尔 | `is_` / `has_` 前缀，`TINYINT` | `is_deleted`、`is_vip` |
| 时间 | `_at` 后缀（时刻）/ `_date`（日期） | `created_at`、`expire_date` |
| 数量 | `_count` / `_num` 后缀 | `comment_count` |
| 普通索引 | `idx_<列>_<列>` | `idx_user_id_status` |
| 唯一索引 | `uk_<列>` | `uk_email` |
| 分表 | `<表名>_<编号>`，编号定长 | `order_00` ~ `order_63` |

**硬性禁忌**：

- 不用 MySQL 保留字：`order`、`desc`、`key`、`group`、`system`……
  （表名叫 `order` 之后，每条 SQL 都得写反引号 `` `order` ``，写漏一次就报错。用 `shop_order`。）
- 不用大写和驼峰——Linux 下表名大小写敏感、Windows 下不敏感，跨环境迁移必炸。
- 不用中文、不用拼音缩写（`yhb` 是"用户表"还是"优惠包"？）。
- 同一个概念在所有表里必须同名：不要这张表叫 `user_id`、那张叫 `uid`、还有一张叫 `member_id`。

### 2.2 字段类型：最小、可用

**核心原则：能用小的就不用大的。** 字段窄 → 一页装的行多 → 树矮 → IO 少 → 快。这个收益在索引列上会被放大（二级索引的叶子节点还要额外存主键值）。

**整数**

| 类型 | 字节 | 无符号上限 | 用在哪 |
|---|---|---|---|
| `TINYINT` | 1 | 255 | 状态、类型、布尔 |
| `SMALLINT` | 2 | 65535 | 年龄、小计数 |
| `INT` | 4 | 约 42.9 亿 | 一般计数 |
| `BIGINT` | 8 | 极大 | 主键（推荐默认）、金额分、雪花 ID |

- 确定非负就加 `UNSIGNED`，上限翻倍。
- `INT(11)` 里的 11 **不是长度**，只是 `ZEROFILL` 时的显示宽度，和存储无关（MySQL 8.0.17 起已废弃）。别再纠结写几。

**字符串**

| 类型 | 说明 |
|---|---|
| `CHAR(N)` | 定长，长度**几乎不变**时用（MD5=32、手机号、国家码）。省下长度字节，无更新碎片 |
| `VARCHAR(N)` | 变长，N 是**字符数**不是字节数。按实际最大长度给，别一律 255 |
| `TEXT` | 只在真的可能超长时用（文章正文）。不能有默认值，且**不要放主表** |
| `JSON` | 存 schema 不定的扩展属性。别用它替代正经字段——JSON 内部检索能力弱 |

关于 `VARCHAR(255)` 的迷信：存储上确实按实际长度存，写 255 不比写 32 占空间。但有两个真实代价：

1. **临时表和排序**——`ORDER BY`/`GROUP BY` 用到内存临时表时，某些场景按**最大长度**分配内存，255 会浪费甚至逼出磁盘临时表。
2. **索引长度限制**——InnoDB `DYNAMIC` 行格式下单个索引最长 3072 字节，`utf8mb4` 一字符 4 字节，`VARCHAR(768)` 就顶到天花板了。

**时间**

| 类型 | 字节 | 范围 | 结论 |
|---|---|---|---|
| `DATETIME(3)` | 5+2 | 1000 ~ 9999 年 | **默认选它**，毫秒精度，不受时区影响 |
| `TIMESTAMP` | 4 | 1970 ~ **2038** | 有 2038 溢出问题；随会话时区自动转换（是特性也是坑） |
| `DATE` | 3 | — | 只到天的场景（生日、账期） |
| `BIGINT` 存时间戳 | 8 | — | 可读性差，SQL 里无法直接用日期函数。除非有强跨时区需求，否则别用 |

**金额**

```sql
-- ✓ 方案 A：定点数（可读性好）
amount DECIMAL(12,2) NOT NULL DEFAULT 0.00 COMMENT '金额，单位元'

-- ✓ 方案 B：整数分（运算最快，绝不丢精度，推荐）
amount_cent BIGINT NOT NULL DEFAULT 0 COMMENT '金额，单位分'

-- ✗ 永远不要
amount DOUBLE   -- 0.1 + 0.2 != 0.3，对账少一分钱能查一整天
```

**主键：`BIGINT UNSIGNED`，且必须单调递增**

```sql
   自增/雪花 ID（有序）              UUID / 随机字符串（无序）

   ┌─────────────────┐            ┌──────────────────────────┐
   │ 1 2 3 4 5 6 →   │            │ 插入 f3a.. 要塞进已满的页  │
   │ 顺序追加到页尾    │            │      ↓                   │
   │ 页写满 → 开新页   │            │ 页分裂：搬一半数据到新页   │
   │ 无分裂，无碎片    │            │ → 碎片、随机 IO、表膨胀    │
   └─────────────────┘            └──────────────────────────┘
```

InnoDB 表数据**按主键物理有序存放**（聚簇索引），所以：

- 主键必须**单调递增**：单库用 `AUTO_INCREMENT`，分库分表用雪花 ID（`BIGINT`）。
- 主键必须**短**：所有二级索引的叶子节点都存着主键值，主键每宽 1 字节，每个二级索引的每一行都跟着胖 1 字节。
- 必须显式定义主键：没主键时 InnoDB 会用唯一索引，再没有就自建一个隐藏的 6 字节 `row_id`，且这个隐藏列是**全局共享**的，高并发插入会成为竞争点。
- 业务字段（身份证、手机号）不做主键——业务会变，主键不能变。要唯一就加唯一索引。

### 2.3 索引：单列、多列、唯一

索引是**空间和写入速度换查询速度**。数量控制见下半部分的**经验 ③**，这里先讲怎么建对。

**三种形态**

```sql
KEY idx_user_id (user_id)                          -- 单列：单一条件过滤
KEY idx_user_status_time (user_id, status, created_at)  -- 多列（联合）：遵循最左前缀
UNIQUE KEY uk_order_no (order_no)                  -- 唯一：既是索引也是约束
```

**最左前缀原则**——联合索引 `(a, b, c)` 相当于同时有了 `(a)`、`(a,b)`、`(a,b,c)`：

```
   ✓ 能用上                    ✗ 用不上（或只用上一部分）
   WHERE a=1                   WHERE b=2             ← 跳过了 a
   WHERE a=1 AND b=2           WHERE b=2 AND c=3     ← 跳过了 a
   WHERE a=1 AND b=2 AND c=3   WHERE a=1 AND c=3     ← c 用不上，只走 a
   WHERE b=2 AND a=1
    ↑ WHERE 里的书写顺序无所谓，优化器会自动调整；缺不缺列才是关键
```

**联合索引的列序怎么定**：

1. **等值查询的列放前面，范围查询的列放最后**——范围条件之后的列无法再用索引定位。
   `WHERE user_id=1 AND created_at>'...' AND status=2` → 索引建 `(user_id, status, created_at)`，不是 `(user_id, created_at, status)`。
2. 剩下的按**区分度**从高到低排：`SELECT COUNT(DISTINCT col)/COUNT(*) FROM t;` 越接近 1 越该靠前。
3. 能顺带满足 `ORDER BY` 的排在后面，可以省掉 `filesort`。

**覆盖索引**——查询要的列全在索引里，不用回表：

```sql
KEY idx_user_status (user_id, status, amount)

SELECT amount FROM orders WHERE user_id=1 AND status=2;
-- EXPLAIN 的 Extra 出现 "Using index" → 覆盖索引生效，不回聚簇索引取数据，快一个量级
```

**索引失效的五种常见写法**：

```sql
-- ✗ 列上套函数              ✓ 改写成范围
WHERE DATE(created_at) = '2026-08-02'
  →  WHERE created_at >= '2026-08-02 00:00:00' AND created_at < '2026-08-03 00:00:00'

-- ✗ 列上做运算
WHERE amount / 100 > 5        →   WHERE amount > 500

-- ✗ 隐式类型转换（phone 是 VARCHAR，传了数字）
WHERE phone = 13800138000     →   WHERE phone = '13800138000'
   -- 字符串列和数字比较时 MySQL 把"列"转成数字 → 等于在列上套了函数 → 失效

-- ✗ 前导模糊
WHERE name LIKE '%明'          →   'x%' 才走索引；全文检索交给 ES

-- ✗ OR 两边不是都有索引
WHERE user_id=1 OR remark='x' →   remark 无索引则整体全表扫；拆成 UNION ALL
```

# 第二部分：经验和技巧

> 不论是经验还是技巧，都需要总结、回顾和复盘。

下面用一张**真实项目里常见的烂表**做主线，逐条改到能上线。

```sql
-- ✗ 某商城的用户表，字段 40+，这里只截了一部分
CREATE TABLE T_UserInfo (
  ID           INT AUTO_INCREMENT PRIMARY KEY,
  UserName     VARCHAR(255),
  Phone        VARCHAR(255),
  Email        VARCHAR(255),
  Sex          VARCHAR(10),          -- 存 "男"/"女"/"male"/NULL 四种值
  Age          INT,
  Balance      DOUBLE,               -- 余额用 DOUBLE
  RegTime      TIMESTAMP,
  ProvinceName VARCHAR(255),
  CityName     VARCHAR(255),
  ...
  Signature    TEXT,                 -- 个性签名，很少查
  Avatar       TEXT,                 -- 头像 base64
  Ext1 VARCHAR(255), Ext2 VARCHAR(255), Ext3 VARCHAR(255),  -- 预留字段
  INDEX idx_1(UserName), INDEX idx_2(Phone), INDEX idx_3(Email),
  INDEX idx_4(Sex), INDEX idx_5(Age), INDEX idx_6(ProvinceName),
  INDEX idx_7(CityName), INDEX idx_8(RegTime), INDEX idx_9(Ext1)
);
```

这张表**每一条经验都踩了**。

## 三、经验 ①：字段不宜过多（20 个），多了拆表或 JSON

### 为什么是 20 这个数

不是 MySQL 有限制，是 **InnoDB 的页装不下**。

```
   InnoDB 一页 = 16KB

   窄表：一行 200B  → 一页装 ~80 行 ┐
                                    ├─ 同样扫 1000 行
   宽表：一行 2KB   → 一页装 ~8 行  ┘

   窄表读 13 个页，宽表读 125 个页 —— 差 10 倍的 IO
```

更狠的是 `SELECT *`：宽表一次查询要把 40 个字段全搬进内存，而你其实只用了 3 个。Buffer Pool 就那么大，宽表会把有用的热数据挤出去。

### 例子：垂直拆分

用户表按**访问频率**切三块：

```sql
-- 主表：几乎每次请求都要读，保持窄
CREATE TABLE user (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  nickname   VARCHAR(32)  NOT NULL DEFAULT '',
  phone      CHAR(11)     NOT NULL DEFAULT '',
  status     TINYINT      NOT NULL DEFAULT 1  COMMENT '0禁用 1正常',
  created_at DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户主表';
-- 一行不到 100 字节，一页装 160+ 行

-- 扩展表（1:1）：进个人主页才读
CREATE TABLE user_profile (
  user_id    BIGINT UNSIGNED NOT NULL,
  signature  VARCHAR(255) NOT NULL DEFAULT '',
  avatar_url VARCHAR(255) NOT NULL DEFAULT '',
  bio        TEXT         NULL,
  PRIMARY KEY (user_id)                 -- 主键即外键，1:1
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户扩展信息';

-- 敏感表：单独存，权限单独控
CREATE TABLE user_secure (
  user_id   BIGINT UNSIGNED NOT NULL,
  id_card   VARCHAR(64) NOT NULL DEFAULT '' COMMENT '身份证，加密存',
  real_name VARCHAR(64) NOT NULL DEFAULT '',
  PRIMARY KEY (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户实名信息';
```

**拆分的判断标准**（不是数字，是这三条）：

| 信号 | 该拆 |
|---|---|
| 一半字段在 90% 的查询里用不到 | 拆冷字段 |
| 有 TEXT/BLOB/大 JSON | 一定拆出主表 |
| 部分字段更新频率远高于其他（如 `last_login_at`） | 拆出来，避免高频更新影响主表 |

### 例子：什么时候该用 JSON 而不是拆表

商品的属性是**不定的**——手机有内存/颜色，衣服有尺码/材质。硬建字段会变成 `attr1...attr20`：

```sql
-- ✗ 预留字段：三个月后没人知道 ext1 存的是什么
ext1 VARCHAR(255), ext2 VARCHAR(255), ext3 VARCHAR(255)

-- ✓ JSON：schema 不固定的扩展属性
CREATE TABLE product (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name        VARCHAR(128) NOT NULL DEFAULT '',
  category_id INT          NOT NULL DEFAULT 0,
  price_cent  BIGINT       NOT NULL DEFAULT 0,
  -- 品类特有属性：{"screen":"6.1寸","storage":"256G","color":"黑"}
  attrs       JSON         NULL COMMENT '扩展属性，键随品类变化',
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**JSON 的红线——凡是要 `WHERE` 过滤或 `ORDER BY` 的，绝不能放 JSON。**

```sql
-- ✗ 这条 SQL 只能全表扫，JSON 内部没有索引
SELECT * FROM product WHERE attrs->>'$.color' = '黑';

-- 真要按它查，MySQL 8.0 得建生成列 + 索引，等于变相加了个字段
ALTER TABLE product
  ADD COLUMN color VARCHAR(16) AS (attrs->>'$.color') STORED,
  ADD KEY idx_color (color);
```

判断标准很清楚：

```
   这个字段要不要用来查询/排序/聚合？
        ├─ 要   → 建成正经字段（必要时拆表）
        └─ 不要 → 只是展示用的一坨属性 → JSON 或 TEXT
```

## 四、经验 ②：全部 NOT NULL，空值用无意义值填充

### NULL 到底坑在哪

**坑 1：`!=` 会漏数据**（线上最常见的 bug）

```sql
-- 表里 3 行：status=1, status=2, status=NULL
SELECT COUNT(*) FROM t WHERE status != 1;
-- 你以为是 2，实际是 1 —— NULL != 1 的结果是 NULL 不是 true，行被过滤掉了
```

**坑 2：聚合函数悄悄跳过 NULL**

```sql
-- 4 行：score = 80, 90, NULL, NULL
SELECT COUNT(*), COUNT(score), AVG(score) FROM t;
-- 4,  2,  85.0
--     ↑        ↑ 平均分算出 85，但你以为是 4 个人的平均（应是 42.5）
```

**坑 3：拼接、比较全被污染**

```sql
SELECT CONCAT('Hi, ', nickname) FROM user;   -- nickname 为 NULL → 整个结果 NULL
WHERE a = NULL                                -- 永远不成立，必须写 IS NULL
NOT IN (SELECT x FROM t)                      -- 子查询里只要有一个 NULL，整个结果就是空
```

**坑 4**：索引里 NULL 要额外存标记位，优化器对含 NULL 列的基数估算也更不准。

### 正确写法：给每种类型定一个"无意义默认值"

```sql
CREATE TABLE shop_order (
  id         BIGINT UNSIGNED NOT NULL,
  user_id    BIGINT UNSIGNED NOT NULL DEFAULT 0   COMMENT '0=游客下单',
  remark     VARCHAR(255)    NOT NULL DEFAULT ''  COMMENT '备注，空串=无备注',
  coupon_id  BIGINT          NOT NULL DEFAULT 0   COMMENT '0=未使用优惠券',
  pay_amount BIGINT          NOT NULL DEFAULT 0   COMMENT '单位分',
  -- 时间的"空值"：用零值时间，而不是 NULL
  paid_at    DATETIME(3)     NOT NULL DEFAULT '1970-01-01 00:00:00.000' COMMENT '未支付时为零值',
  status     TINYINT         NOT NULL DEFAULT 0,
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

约定表（团队统一，写进规范文档）：

| 类型 | 空值填什么 | 语义 |
|---|---|---|
| 数值 | `0` | 未设置 / 无关联 |
| 字符串 | `''` | 未填写 |
| 外键 id | `0` | 未关联（0 号 id 永不使用） |
| 时间 | `'1970-01-01 00:00:00'` | 未发生 |
| JSON | `'{}'` | 无扩展属性 |

### "并在业务代码中特殊处理"是什么意思

代价转移到了应用层——**空串和 0 现在有了业务含义，代码里必须显式判断**：

```java
// ✗ 直接用，页面会显示 "1970-01-01"
view.setPaidAt(order.getPaidAt());

// ✓ 统一在转换层处理"零值 = 未发生"
private static final LocalDateTime ZERO_TIME = LocalDateTime.of(1970, 1, 1, 0, 0);

view.setPaidAtText(
    ZERO_TIME.equals(order.getPaidAt()) ? "未支付" : FMT.format(order.getPaidAt())
);

// 外键同理：0 表示没关联，不要拿 0 去查数据库
if (order.getCouponId() > 0) {
    coupon = couponService.getById(order.getCouponId());
}
```

**唯一该保留 NULL 的场景**：需要区分"没填"和"填了零值"。比如问卷评分，`0 分`和`没作答`是两件事——这时 NULL 有语义，该用。

## 五、经验 ③：索引不超过 6 个，且随业务迭代持续优化

### 为什么要克制

回头看那张烂表的 9 个索引：

```
   每 INSERT 一行 = 1 次聚簇索引写 + 9 次二级索引写 = 10 棵树都要动
   每 UPDATE 一个被索引的列 = 删旧索引项 + 插新索引项

   写入 QPS 直接掉一个档，磁盘占用可能比数据本身还大
```

而且其中一大半是**白建的**：

```sql
INDEX idx_4(Sex)           -- 区分度 2/1000万 ≈ 0，优化器根本不会选它
INDEX idx_5(Age)           -- 区分度低，且很少单独作为查询条件
INDEX idx_9(Ext1)          -- 给一个没人知道存什么的字段建索引
INDEX idx_6(ProvinceName)  -- 和 idx_7(CityName) 应该合成一个联合索引
```

### 例子：9 个索引压到 4 个

先看真实查询有哪些——**索引是为查询建的，不是为字段建的**：

```sql
-- Q1 登录：      WHERE phone = ?
-- Q2 邮箱找回：  WHERE email = ?
-- Q3 后台筛选：  WHERE province_id = ? AND city_id = ? ORDER BY created_at DESC
-- Q4 运营拉新：  WHERE status = ? AND created_at BETWEEN ? AND ?
```

对应四个索引，一个不多：

```sql
UNIQUE KEY uk_phone (phone),                                       -- Q1，顺便当唯一约束
UNIQUE KEY uk_email (email),                                       -- Q2
KEY idx_province_city_created (province_id, city_id, created_at),  -- Q3
KEY idx_status_created (status, created_at)                        -- Q4
```

注意 Q3 的联合索引**顺带覆盖了单查省份**（最左前缀），不需要再单独给 `province_id` 建索引。

### 再强调一次列序：等值在前，范围/排序在后

用 Q4 举例：

```sql
-- 查询：WHERE status = 1 AND created_at > '2026-01-01' ORDER BY created_at

-- ✗ 建 (created_at, status)
--   created_at 是范围条件 → 它后面的 status 用不上索引，要逐行过滤

-- ✓ 建 (status, created_at)
--   status 等值定位 → 在 status=1 的这一段里 created_at 天然有序
--   → 范围扫描直接命中，ORDER BY 还免了 filesort
```

### "随业务迭代逐步修改"具体怎么做

索引不是一次建好的，是**跟着慢查询日志长出来的**：

```sql
-- 1. 打开慢查询日志（生产环境常驻）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;      -- 超过 500ms 记录

-- 2. 新 SQL 上线前必须 EXPLAIN
EXPLAIN SELECT id, nickname FROM user WHERE phone = '13800138000';
```

看 `EXPLAIN` 只盯三列：

| 列 | 健康 | 危险 |
|---|---|---|
| `type` | `const` / `eq_ref` / `ref` / `range` | **`ALL`**（全表扫）、`index`（全索引扫） |
| `key` | 用上了预期的索引 | `NULL` |
| `Extra` | `Using index`（覆盖索引，不回表） | `Using filesort` / `Using temporary` |

```sql
-- 3. 定期清理没人用的索引（MySQL 8.0）
SELECT object_name, index_name, count_star
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_schema = 'your_db' AND index_name IS NOT NULL AND count_star = 0;
-- count_star = 0 → 上线以来一次没被用过，删掉
```

### 不该建索引的地方

- 区分度低的列（性别、是否删除）——除非作为联合索引的**非首列**参与过滤。
- 频繁更新的列——每次更新都要维护索引树。
- 很少出现在 `WHERE`/`ORDER BY`/`JOIN` 里的列。
- 已被其他索引最左前缀覆盖的列（有了 `(a,b,c)` 就别再建 `(a)`）。

## 六、经验 ④：不追求严格精简，用冗余换查询

范式（3NF）是学院派的正确，但**每消除一处冗余，就多一次 JOIN**。互联网业务里 JOIN 是最贵的操作之一，尤其分库分表后**跨库 JOIN 根本做不了**。

### 例子 1：快照冗余（这不是冗余，是业务正确性）

```sql
CREATE TABLE order_item (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_id     BIGINT UNSIGNED NOT NULL DEFAULT 0,
  product_id   BIGINT UNSIGNED NOT NULL DEFAULT 0,
  -- ↓ 严格范式说这是冗余，应该 JOIN product 表拿
  product_name VARCHAR(128) NOT NULL DEFAULT '' COMMENT '下单时的商品名快照',
  unit_price   BIGINT       NOT NULL DEFAULT 0  COMMENT '下单时的单价快照，单位分',
  quantity     INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  KEY idx_order_id (order_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**为什么必须冗余**：商品今天卖 99 元，明天调成 199 元、后天改了名字。如果订单详情靠 JOIN 实时取，用户翻开半年前的订单会看到**今天的价格**——这是事故，不是优化问题。

> 快照类冗余是最安全的冗余：**写入后永不更新**，天然不存在一致性问题。

### 例子 2：免 JOIN 冗余

订单列表页要显示用户昵称：

```sql
-- ✗ 每次列表查询都 JOIN，分库后直接跑不通
SELECT o.*, u.nickname
FROM shop_order o JOIN user u ON o.user_id = u.id
WHERE o.status = 1 ORDER BY o.created_at DESC LIMIT 20;

-- ✓ 冗余一列，单表搞定
ALTER TABLE shop_order
  ADD COLUMN user_nickname VARCHAR(32) NOT NULL DEFAULT '' COMMENT '冗余：下单用户昵称';

SELECT id, order_no, user_nickname, pay_amount
FROM shop_order WHERE status = 1 ORDER BY created_at DESC LIMIT 20;
```

代价是**用户改昵称后订单里的是旧值**。这里要做业务判断：订单场景显示下单时的昵称完全合理（甚至更好，不用同步）；如果业务要求实时，就得加同步逻辑（改昵称时发消息异步刷订单表），这时要掂量值不值。

### 例子 3：计数器冗余

```sql
-- ✗ 帖子列表每行都执行一次 COUNT，20 行 = 20 次统计
SELECT p.*, (SELECT COUNT(*) FROM comment c WHERE c.post_id = p.id) AS comment_count
FROM post p LIMIT 20;

-- ✓ 冗余计数列
ALTER TABLE post ADD COLUMN comment_count INT NOT NULL DEFAULT 0 COMMENT '冗余：评论数';

-- 写评论时同步 +1（放在同一个事务里）
UPDATE post SET comment_count = comment_count + 1 WHERE id = ?;
```

计数器一定会因为并发、异常、补数据而偏差，所以配套**必须有对账**：

```sql
-- 每天凌晨跑一次修正
UPDATE post p SET p.comment_count = (SELECT COUNT(*) FROM comment c WHERE c.post_id = p.id);
```

### 冗余的纪律

加之前回答三个问题：

```
   1. 谁负责更新它？          → 答不上来就别冗余
   2. 不一致时业务能忍吗？     → 能忍（订单快照）→ 放心加
                              → 不能忍（账户余额）→ 别冗余，老实算
   3. 有对账/修复手段吗？      → 计数器类必须有定时校准脚本
```

风险排序：

```
   快照类（写完不变）      ← 最安全，随便用
   计数类（可定时对账）    ← 可用，但要配对账任务
   实时同步类（要求强一致）← 最危险，能不做就不做
```

# 第三部分：落地

## 七、把烂表改完的最终版

```sql
CREATE TABLE user (
  -- 主键：BIGINT 而非 INT（42 亿会用完）；单调递增，避免页分裂
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  -- 命名：小写下划线；表名已是 user，字段不再加 user_ 前缀
  nickname     VARCHAR(32)  NOT NULL DEFAULT ''  COMMENT '昵称',
  -- 类型最小可用：手机号定长用 CHAR，不用 VARCHAR(255)
  phone        CHAR(11)     NOT NULL DEFAULT ''  COMMENT '手机号',
  email        VARCHAR(64)  NOT NULL DEFAULT ''  COMMENT '邮箱',
  -- 状态用 TINYINT + COMMENT，不用 ENUM、不用中文字符串
  gender       TINYINT      NOT NULL DEFAULT 0   COMMENT '0未知 1男 2女',
  status       TINYINT      NOT NULL DEFAULT 1   COMMENT '0禁用 1正常',
  -- 金额：整数分，绝不用 DOUBLE
  balance_cent BIGINT       NOT NULL DEFAULT 0   COMMENT '余额，单位分',
  -- 地区存 id 不存名字（名字会改，且 INT 比 VARCHAR 索引效率高）
  province_id  INT          NOT NULL DEFAULT 0   COMMENT '省 id',
  city_id      INT          NOT NULL DEFAULT 0   COMMENT '市 id',
  -- 逻辑删除参与唯一键：注销的手机号能让位给新注册
  deleted_at   BIGINT       NOT NULL DEFAULT 0   COMMENT '删除时间戳(ms)，0=未删除',
  -- 时间用 DATETIME(3)，不用 TIMESTAMP（2038 溢出 + 随时区变化）
  created_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_phone_deleted (phone, deleted_at),
  UNIQUE KEY uk_email_deleted (email, deleted_at),
  KEY idx_province_city_created (province_id, city_id, created_at),
  KEY idx_status_created (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户主表';
-- 字段 13 个、索引 4 个、全部 NOT NULL、大字段已拆到 user_profile
```

对照改动：

| 原问题 | 改法 | 对应条目 |
|---|---|---|
| 40+ 字段 | 拆成 user / user_profile / user_secure，主表 13 个 | 经验 ① |
| `Signature`、`Avatar` 是 TEXT | 移到 user_profile | 经验 ① |
| `Ext1/2/3` 预留字段 | 删掉，真要扩展用 JSON | 经验 ① |
| 全部可 NULL | 全 `NOT NULL DEFAULT` | 经验 ② |
| 9 个索引，一半没用 | 按 4 条真实查询建 4 个 | 经验 ③ |
| 省市存名字要 JOIN 地区表 | 存 id，展示时按需冗余名字 | 经验 ④ |
| `Balance DOUBLE` | `BIGINT` 存分 | 字段类型 |
| `RegTime TIMESTAMP` | `DATETIME(3)` | 字段类型 |
| `T_UserInfo` 大写驼峰 | 小写下划线 `user` | 命名规范 |
| `VARCHAR(255)` 一把梭 | 按实际长度给 | 字段类型 |

## 八、一套完整的电商建表示例

```sql
-- ─────────────────────────────────────────────
-- 订单表（1:N —— 一个用户多个订单）
-- ─────────────────────────────────────────────
CREATE TABLE shop_order (                       -- 命名：不叫 order，那是保留字
  -- 数据量：预估 3 年 6600 万行 → 主键用雪花 ID，为将来按 user_id 分表留后路
  id            BIGINT UNSIGNED NOT NULL           COMMENT '主键，雪花 ID',
  order_no      CHAR(24)        NOT NULL DEFAULT '' COMMENT '订单号，对外展示',
  -- 数据关系：1:N 在"多"的一方存 user_id；不建 FOREIGN KEY，约束由应用层保证
  user_id       BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '下单用户 id',
  user_nickname VARCHAR(32)     NOT NULL DEFAULT '' COMMENT '冗余：免列表页 JOIN',
  -- 类型：金额用整数分
  total_amount  BIGINT          NOT NULL DEFAULT 0 COMMENT '订单总额，单位分',
  pay_amount    BIGINT          NOT NULL DEFAULT 0 COMMENT '实付金额，单位分',
  status        TINYINT         NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已发货 3已完成 4已取消',
  -- 数据规范：收货地址是下单当时的快照，用户改地址不影响历史订单
  receiver_snapshot JSON        NULL               COMMENT '收货信息快照，仅展示不查询',
  paid_at       DATETIME(3)     NOT NULL DEFAULT '1970-01-01 00:00:00.000' COMMENT '零值=未支付',
  version       INT             NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
  created_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  -- 索引：覆盖"我的订单"列表 —— WHERE user_id=? AND status=? ORDER BY created_at DESC
  --      等值列在前，范围/排序列在后
  KEY idx_user_status_created (user_id, status, created_at),
  -- 索引：运营按时间段捞单
  KEY idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';


-- ─────────────────────────────────────────────
-- 订单明细表（N:N —— 订单 <-> 商品 的中间表）
-- ─────────────────────────────────────────────
CREATE TABLE order_item (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  order_id     BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '订单 id',
  product_id   BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '商品 id',
  -- 反范式：商品改名/调价后，历史订单必须显示下单当时的值
  product_name VARCHAR(128) NOT NULL DEFAULT ''    COMMENT '商品名快照',
  unit_price   BIGINT       NOT NULL DEFAULT 0     COMMENT '成交单价快照，单位分',
  quantity     INT          NOT NULL DEFAULT 0     COMMENT '数量',
  created_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_order_id (order_id),                     -- 查订单详情的主路径
  KEY idx_product_created (product_id, created_at) -- 按商品统计销量
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单明细表';


-- ─────────────────────────────────────────────
-- 商品详情表（1:1 拆分 —— 大字段不进主表）
-- ─────────────────────────────────────────────
CREATE TABLE product_detail (
  product_id  BIGINT UNSIGNED NOT NULL COMMENT '商品 id，与 product 一对一',
  -- 详情富文本可能几十 KB，留在主表会把 product 的页密度拉垮
  detail_html MEDIUMTEXT      NULL     COMMENT '商品详情富文本',
  PRIMARY KEY (product_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品详情表';
```

## 九、建表 Checklist

DDL 提交评审前逐条对一遍。

**业务分析**
- [ ] 算过 3 年的数据量和表大小了吗？超过 2000 万有没有分表/归档方案？
- [ ] 如果将来要分表，分片键定了吗？主键还能用自增吗？
- [ ] E-R 关系（1:1 / 1:N / N:N）落成表结构了吗？N:N 有中间表吗？

**结构（经验 ①）**
- [ ] 主表字段 ≤ 20 个？超了按访问频率垂直拆分？
- [ ] TEXT / BLOB / 大 JSON 已经移出主表？
- [ ] 不定 schema 的属性用了 JSON，且**没有**放需要 WHERE 过滤的字段进去？
- [ ] 没有 `ext1/ext2` 这种预留字段？

**字段（经验 ② + 字段类型/命名规范）**
- [ ] 全部 `NOT NULL` + `DEFAULT`？保留 NULL 的几个有明确语义理由？
- [ ] 应用层处理了"零值 = 未发生"的转换？
- [ ] 金额是 `DECIMAL` 或整数分？（搜一遍有没有 `FLOAT`/`DOUBLE`）
- [ ] 时间是 `DATETIME(3)`？（`TIMESTAMP` 2038 年溢出）
- [ ] 状态是 `TINYINT` + `COMMENT` 而不是 `ENUM` / 中文字符串？
- [ ] 主键 `BIGINT UNSIGNED` 且单调递增？没拿手机号/身份证当主键？
- [ ] 每张表、每个字段都有 `COMMENT`？
- [ ] 表名不是保留字（`order`/`desc`/`key`），全小写下划线？
- [ ] 同一概念全库同名（不要 `user_id`/`uid`/`member_id` 混用）？
- [ ] 逻辑删除和唯一索引的冲突处理了吗？

**索引（经验 ③）**
- [ ] 索引数量 ≤ 6？
- [ ] 每个索引都能对应到一条**真实查询**？
- [ ] 联合索引：等值列在前、范围/排序列在后？
- [ ] 没有被其他索引最左前缀覆盖的冗余索引？
- [ ] 没给性别、是否删除这类低区分度列单独建索引？
- [ ] 核心 SQL 都跑过 `EXPLAIN`，`type` 不是 `ALL`、`Extra` 没有 `filesort`？

**冗余（经验 ④）**
- [ ] 每个冗余字段都能说清"谁负责更新它"？
- [ ] 快照类字段（订单里的商品名/价格）冗余了？
- [ ] 计数器类冗余配了定时对账脚本？

**引擎**
- [ ] `ENGINE=InnoDB`、`CHARSET=utf8mb4`，全库排序规则统一？

## 十、一句话总纲

> **业务分析决定表长什么样，DB 约束决定表跑多快。**
> 落到手上就四句话：**字段克制（≤20），NULL 消灭（全 NOT NULL），索引克制（≤6，跟着慢查询长），冗余放开（磁盘最便宜，JOIN 最贵）。**
