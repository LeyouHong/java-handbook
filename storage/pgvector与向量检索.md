# pgvector 与向量检索：当"精确"不再可能

> 环境：PostgreSQL 16 + pgvector 0.8.x。本篇 SQL 为**示例**，未附实测输出。
>
> **一句话主线：向量检索是三类索引里唯一放弃「精确」的那一类——它用召回率换速度。**

这一篇和仓库里另外两篇索引原理构成一组对照：

```
   ┌─ B+ 树 ──────────┐  牺牲【写】（页分裂）  换   精确 + 有序范围查询
   │  《B+ 树原理》     │
   └───────────────────┘

   ┌─ LSM ────────────┐  牺牲【读】（查多层）  换   顺序写、高写入吞吐
   │  《LSM Tree 原理》 │
   └───────────────────┘

   ┌─ 向量索引 ────────┐  牺牲【精确】          换   在高维空间里还能快
   │   （本篇）         │       ↑
   └───────────────────┘   前两个都保证"找到的就是对的"，
                            这一个【不保证】。
```

最后一句是全篇的分界线。理解了它，后面的召回率、参数调优、过滤的坑，全都是推论。

## 一、为什么需要向量：从"匹配字"到"匹配意思"

```sql
SELECT * FROM docs WHERE content LIKE '%笔记本电脑%';
```

这条 SQL 找不到一篇通篇写着"手提电脑"的文档——**它匹配的是字，不是意思**。

向量检索换了个思路：先把文本交给一个模型，变成一串数字。

```
   "笔记本电脑"  →  [ 0.21, -0.43,  0.88, ... ]   ┐
   "手提电脑"    →  [ 0.19, -0.41,  0.90, ... ]   ┘ 两个点几乎重合
   "红烧肉"      →  [-0.62,  0.11, -0.25, ... ]     离得很远
                     └────── 1536 个数 ──────┘
```

这串数字叫 **embedding（嵌入向量）**，模型保证了一件事：

```
   ┌──────────────────────────────────────────────────────────┐
   │  语义相似  ⟺  向量在空间中的距离近                        │
   │                                                           │
   │  于是"找意思相近的文档"变成了一个纯几何问题：              │
   │  【在 N 维空间里，找离查询点最近的 k 个点】                │
   └──────────────────────────────────────────────────────────┘
```

这个问题叫 **KNN（k 近邻）**。听起来简单，但维度一高就完全变味了。

## 二、维度诅咒：B+ 树为什么在这里彻底失效

### 2.1 根本原因：高维空间没有"顺序"

> ⤵ **依据**：《[B+ 树原理 · 第二章](../mysql/B+树原理.md)》——B+ 树能快，靠的是**有序 → 可二分**。

```
   一维数据可以排序：      15 < 18 < 20 < 30      → 能二分 → 能建树

   1536 维向量呢？
      [0.2, -0.4, 0.9, ...]  和  [0.3, 0.1, -0.2, ...]  谁大？
                              ↑
                       【没有全序关系】
```

没有顺序就没有二分，没有二分就没有 B+ 树。哈希索引也不行——哈希只能判"相等"，而我们要的是"相近"。

```
   B+ 树 ✗   需要全序
   哈希  ✗   只能等值，不能"接近"
   → 传统索引在这里【一个都用不了】
```

### 2.2 更糟的是：高维下"距离"这个概念本身在退化

这是"维度诅咒"的核心：

```
   随机取一堆点，看它们两两之间的距离：

   2 维    最近的点和最远的点，距离差别很大        → "最近"有意义
   100 维  差别开始缩小
   1536 维 【几乎所有点到查询点的距离都差不多】
           最远距离 / 最近距离 → 趋近于 1
```

```
   后果：任何"用某个划分把空间切开、只搜一半"的策略都失效了 ——
        因为几乎每个划分区域都可能包含答案。

   数学上的结论很残酷：
   高维空间里的【精确】KNN，没有比暴力全扫更好的通用算法。
```

### 2.3 于是只能退让：ANN

既然精确解要付出全扫描的代价，那就**不要精确解**：

```
   ANN = Approximate Nearest Neighbor（近似最近邻）

   我不保证返回的一定是最近的 k 个，
   但我保证【绝大多数时候】返回的就是它们，而且快几百倍。
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  这是数据库世界里一个罕见的让步。                          │
   │                                                           │
   │  B+ 树查 id=100，要么找到，要么确实不存在 —— 没有第三种。  │
   │  向量索引查"最像的 10 条"，可能给你 8 条对的 + 2 条次优的。│
   │                                                           │
   │  所以向量检索多了一个传统数据库没有的指标：【召回率】。      │
   └──────────────────────────────────────────────────────────┘
```

## 三、距离怎么算

pgvector 支持几种度量，各有专属运算符：

| 运算符 | 度量 | 含义 | 什么时候用 |
|---|---|---|---|
| `<->` | L2（欧氏距离） | 两点间直线距离 | 向量未归一化、关心绝对位置 |
| `<=>` | 余弦距离 | `1 - cos(θ)`，只看**方向**不看长度 | **文本 embedding 最常用** |
| `<#>` | 负内积 | `-(a·b)`，取负是为了"越小越相似" | 向量已归一化时，等价于余弦且更快 |
| `<+>` | L1（曼哈顿距离） | 各维差的绝对值之和 | 少见 |

```
   ┌──────────────────────────────────────────────────────────┐
   │  铁律：查询用的度量，必须和 embedding 模型训练时用的一致。 │
   │                                                           │
   │  用错了不会报错 —— 它会安静地返回一堆不相干的结果。        │
   │  这是最难排查的一类 bug。                                  │
   └──────────────────────────────────────────────────────────┘
```

```
   实践提示：OpenAI 系列的 embedding 是【已归一化】的（模长为 1），
            此时余弦距离和内积完全等价，用 <#> 会略快。
            但如果你不确定模型有没有归一化，就用 <=>，它总是对的。
```

## 四、pgvector 上手

### 4.1 装上、建表

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE items (
  id        bigserial PRIMARY KEY,
  content   text,
  category  text,
  embedding vector(1536)        -- 维度必须写死，和模型输出一致
);
```

pgvector 0.7+ 还有几个省空间的类型：

```
   vector(n)      float4，每维 4 字节        默认
   halfvec(n)     float2，每维 2 字节        省一半空间，精度损失通常可忽略
   sparsevec(n)   稀疏向量，只存非零维
   bit(n)         二值向量，配 <~> 汉明距离
```

### 4.2 写入与查询

```sql
INSERT INTO items (content, embedding)
VALUES ('一台轻薄的手提电脑', '[0.19, -0.41, 0.90, ...]');

-- 找最像的 5 条
SELECT id, content, embedding <=> '[0.21, -0.43, 0.88, ...]' AS distance
  FROM items
 ORDER BY embedding <=> '[0.21, -0.43, 0.88, ...]'
 LIMIT 5;
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  必须是 ORDER BY <距离运算符> ... LIMIT n 的形式，          │
   │  向量索引才会被用上。                                      │
   │                                                           │
   │  ✗ WHERE embedding <=> $1 < 0.5    → 用不上索引，全表扫    │
   │  ✓ ORDER BY embedding <=> $1 LIMIT 10                     │
   │                                                           │
   │  想要"距离小于阈值"，先按上面取 top-k，再在外层过滤。      │
   └──────────────────────────────────────────────────────────┘
```

用 `EXPLAIN` 确认：

```sql
EXPLAIN ANALYZE SELECT ... ORDER BY embedding <=> $1 LIMIT 5;
--  看到 Index Scan using items_embedding_idx  → 用上了 ✓
--  看到 Seq Scan + Sort                       → 没用上 ✗
```

## 五、两种索引

### 5.1 IVFFlat：先分片区，再只搜几个片区

```
   建索引时：把所有向量用 k-means 聚成 lists 个簇，记下每个簇的中心点
   查询时：  先看查询点离哪几个簇中心最近，【只在这几个簇里搜】
```

```
        ●  ●        ○ ○              ● 簇 A 的点
      ●  ⊕  ●     ○  ⊕  ○            ⊕ 簇中心
        ●  ●        ○ ○
                              ★ ← 查询点
          ▲ ▲        ✦ ✦ ✦
        ▲  ⊕  ▲    ✦  ⊕  ✦
          ▲ ▲        ✦ ✦

   查询点 ★ 离右下那个簇中心最近 → probes=1 时只搜那一个簇
   → 扫描量从"全部"降到"1/lists"
```

**近似性从哪来**：如果真正的最近邻恰好落在**没被搜的那个簇**里（比如就在簇边界外侧），就漏了。

```sql
CREATE INDEX ON items USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 1000);

SET ivfflat.probes = 32;      -- 会话级，搜几个簇
```

```
   参数经验值：
     lists   ≤ 100 万行  →  行数 / 1000
             > 100 万行  →  sqrt(行数)
     probes  ≈ sqrt(lists)    ← 从这里起调，看召回率再加
```

**致命限制**：

```
   ✗ 必须【表里已经有代表性数据】才能建索引 —— 它要跑 k-means。
     空表上建的索引，等于没建。

   ✗ 数据持续写入后，簇的划分会逐渐失真（新数据都往几个簇里挤）
     → 需要【定期 REINDEX】
```

### 5.2 HNSW：高维空间里的跳表

这个结构对读过 LSM 篇的人来说是免费的——**它的思想和跳表几乎一模一样**。

> ⤵ 跳表见《[LSM Tree 原理 · 插曲：跳表](LSM树原理.md)》：
> "上层跳得远、下层走得细，走不动了就下一层"。

```
   跳表（一维）                      HNSW（高维）
   ────────────────────────────────────────────────────────
   有序链表 + 多层稀疏索引            邻居图 + 多层稀疏图
   上层跨度大，快速逼近               上层连远处的点，快速逼近
   下层跨度小，精确定位               下层连近处的点，精确定位
   "能往右就往右，太大就下一层"        "能靠近就走过去，走不动就下一层"
```

```
   Layer 2   ●───────────────────────●          只有少数点，边跨度极大
             │                       │
   Layer 1   ●──────────●────────●───●          中等密度
             │          │        │   │
   Layer 0   ●──●──●──●─●──●──●──●───●──●──●    【全部点】，只连最近的邻居

   查询过程：
     ① 从最高层的入口点出发
     ② 看当前点的邻居里，谁离查询点更近 → 走过去（贪心）
     ③ 邻居都不比当前点更近了 → 下降一层，继续
     ④ 到 Layer 0 走完 → 返回找到的 top-k
```

**近似性从哪来**：贪心走法可能卡在**局部最优**——周围邻居都更远，但翻过这个"山头"还有更近的点。`ef_search` 就是用来缓解这个的：它维护一个候选队列，同时探索多条路径。

```sql
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

SET hnsw.ef_search = 100;     -- 会话级，查询时的候选队列大小
```

```
   m               每个节点保留多少邻居（默认 16）
                   ↑ 大 → 图更密 → 召回率高、内存大、建索引慢

   ef_construction 建索引时的候选队列（默认 64）
                   ↑ 大 → 图质量高 → 建得慢，但查询时更准

   ef_search       查询时的候选队列（默认 40）
                   ↑ 大 → 召回率高、查询慢
                   ★ 这是【线上唯一需要经常调】的参数，改它不用重建索引
```

### 5.3 怎么选

| | IVFFlat | HNSW |
|---|---|---|
| 建索引速度 | **快** | 慢（常见 10 倍以上差距） |
| 内存占用 | **小** | 大 |
| 查询速度 | 中 | **快** |
| 召回率 | 中 | **高** |
| 空表能建吗 | **不能** | 能 |
| 持续写入 | 会退化，要定期 REINDEX | **友好** |

```
   ┌──────────────────────────────────────────────────────────┐
   │  默认选 HNSW。                                             │
   │                                                           │
   │  只有在这两种情况下才考虑 IVFFlat：                        │
   │    · 内存实在放不下 HNSW 的图                              │
   │    · 数据量巨大且能接受离线重建（比如每天全量重导）         │
   └──────────────────────────────────────────────────────────┘
```

## 六、召回率：向量检索独有的指标

### 6.1 它是什么

```
   精确答案（暴力扫描算出来的真 top-5）：  [A, B, C, D, E]
   索引返回的 top-5：                      [A, B, C, X, Y]

   召回率 = 命中数 / k = 3 / 5 = 60%
```

### 6.2 怎么测

```sql
-- ① 拿精确答案：关掉索引扫描，强制暴力算
SET enable_indexscan = off;
SELECT id FROM items ORDER BY embedding <=> $1 LIMIT 10;   -- 真值

-- ② 拿索引答案
SET enable_indexscan = on;
SET hnsw.ef_search = 40;
SELECT id FROM items ORDER BY embedding <=> $1 LIMIT 10;

-- ③ 两个结果集求交集大小 / 10，对几百条查询取平均
```

### 6.3 调优循环

```
   召回率不够 → 调大 ef_search（HNSW）或 probes（IVFFlat）
              → 再测召回率和 P99 延迟
              → 直到"召回率达标 且 延迟可接受"

   ┌────────────────────────────────────────────────────────┐
   │  这是向量数据库最核心的调优动作，                        │
   │  而传统数据库里【根本没有这个概念】——                    │
   │  没人会问"你这个 WHERE id=100 的召回率是多少"。          │
   └────────────────────────────────────────────────────────┘
```

```
   经验：先定业务能接受的召回率（比如 95%），
        再找满足它的最小 ef_search —— 而不是反过来。
```

## 七、最大的坑：过滤 + 向量

实战里几乎一定会遇到：

```sql
SELECT * FROM items
 WHERE category = 'tech'              -- 元数据过滤
 ORDER BY embedding <=> $1            -- 向量检索
 LIMIT 10;
```

问题在于：**向量索引不认识 `category`**。

```
   ① 先走向量索引，取候选，再过滤
        ef_search = 40 → 拿 40 个候选 → 过滤 category='tech'
        如果 tech 只占全库 1% → 40 个里可能【一个都不是 tech】
        → 返回不足 10 条，甚至【0 条】，而库里明明有几万条 tech

   ② 先过滤，再暴力算距离
        过滤完还剩 100 万行 → 等于没有索引
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  症状：结果条数莫名其妙地少，过滤条件越窄少得越离谱。       │
   │  很多人第一反应是"数据有问题"，其实是索引机制决定的。       │
   └──────────────────────────────────────────────────────────┘
```

四种解法：

### 7.1 迭代扫描（pgvector 0.8+，首选）

```sql
SET hnsw.iterative_scan = relaxed_order;      -- 或 strict_order
SET hnsw.max_scan_tuples = 20000;             -- 上限，防止退化成全扫
```

```
   原理：候选不够就【继续往下扫】，直到凑够 LIMIT 或触及上限。
        专门为解决这个问题而生。

   relaxed_order  允许结果顺序略有偏差，更快      ← 通常够用
   strict_order   严格按距离排序，慢一些
```

IVFFlat 对应的是 `ivfflat.iterative_scan = relaxed_order`。

### 7.2 部分索引

过滤值固定且不多时，给每个值建一个专属索引：

```sql
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
  WHERE category = 'tech';
```

```
   ✓ 索引里只有 tech 的数据 → 完全没有过滤丢失问题
   ✗ 只适合取值少且稳定的场景（几十个以内）
```

### 7.3 分区表

```sql
CREATE TABLE items (...) PARTITION BY LIST (category);
-- 每个分区各自建 HNSW 索引
```

```
   查询带 category → 分区裁剪 → 只在那个分区的索引里搜
```

> 分区裁剪的原理和 MySQL 一样：**查询必须带分区键，否则等于没分**。
> 见《[分区表与分库分表 · 第 4 步](../mysql/分区表与分库分表.md)》。

### 7.4 调大候选数

最粗暴的办法：把 `ef_search` 调到远大于 `LIMIT`（比如 500），赌候选里有足够的目标。

```
   ✗ 治标不治本，过滤率一变就又不够
   → 有 0.8+ 的话优先用迭代扫描
```

## 八、RAG：向量检索最常见的落地形态

```
   ┌─ 离线：把知识灌进去 ────────────────────────────────┐
   │  文档 → 切块 → 每块算 embedding → 存进 items 表      │
   └──────────────────────────────────────────────────────┘

   ┌─ 在线：回答问题 ────────────────────────────────────┐
   │  用户提问 → 算 embedding → 向量检索 top-k            │
   │           → 把检索到的原文拼进 prompt → 交给 LLM      │
   └──────────────────────────────────────────────────────┘
```

三个实践要点：

### 8.1 切块大小是个权衡

```
   块太小  语义不完整，检索到了也没用（"它"指代谁？）
   块太大  一块里混了多个主题，向量被"平均"掉，谁都不像

   常见做法：500~1000 字符 + 10~20% 重叠，
            并优先按段落/标题等自然边界切
```

### 8.2 混合检索：向量 + 全文

纯向量检索有个短板：**专有名词、型号、人名这类"必须精确匹配"的东西，它反而不擅长**。

```sql
-- PostgreSQL 自带全文检索，和 pgvector 在同一个库里
SELECT id,
       1.0 / (60 + vec_rank)  + 1.0 / (60 + txt_rank) AS score   -- RRF 融合
  FROM (
    SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS vec_rank, ...
  ) v
  FULL JOIN (
    SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank(tsv, query) DESC) AS txt_rank, ...
  ) t USING (id)
 ORDER BY score DESC LIMIT 10;
```

```
   RRF（Reciprocal Rank Fusion）：不比较两种打分的绝对值
   （它们量纲根本不同），只融合【排名】—— 简单且鲁棒。
```

### 8.3 重排序

```
   向量检索取 top-50（快、粗）
        ↓
   用 cross-encoder 重排模型精算这 50 条（慢、准）
        ↓
   取 top-5 送进 prompt

   → 用"粗筛 + 精排"两段式，兼顾速度和质量
```

## 九、pgvector 还是专用向量库

```
   ┌─ pgvector 够用 ─────────────────────────────────────────┐
   │  · 向量规模在千万级以内                                   │
   │  · 已经在用 PostgreSQL                                    │
   │  · 需要向量和业务数据【在同一个事务里】、能 JOIN          │
   │  · 想复用现成的备份 / 复制 / 权限 / 监控体系              │
   └──────────────────────────────────────────────────────────┘

   ┌─ 考虑 Milvus / Qdrant / Weaviate ───────────────────────┐
   │  · 亿级以上向量                                           │
   │  · 需要复杂的多字段元数据过滤                             │
   │  · 需要水平扩展 / 分布式                                  │
   │  · 需要更多量化压缩手段（PQ、SQ 等）                      │
   └──────────────────────────────────────────────────────────┘
```

```
   ┌──────────────────────────────────────────────────────────┐
   │  pgvector 最大的价值不是"性能最强"，而是【少一个组件】。   │
   │                                                           │
   │  向量和业务表在同一个库里 →                                │
   │    · 写业务数据和写向量可以在【一个事务】里，不会不一致     │
   │    · 可以直接 JOIN 用户表、权限表                          │
   │    · 备份、主从、监控全都是现成的                          │
   │                                                           │
   │  额外维护一个分布式向量库的成本，常常高于它带来的性能收益。 │
   └──────────────────────────────────────────────────────────┘
```

## 十、运维要点

### 10.1 向量非常占空间

```
   vector(1536) = 1536 × 4 字节 ≈ 6 KB / 行

   而 PostgreSQL 的页是 8 KB，超过约 2 KB 的字段就会被 TOAST
   （挪到附属表，主表里只留指针）

   → 单个 1536 维向量【必然被 TOAST】
   → 100 万行 ≈ 6 GB 裸数据，还不算索引
```

省空间的手段：

```
   halfvec(1536)     每维 2 字节，直接【减半】，精度损失通常可忽略  ← 优先试这个
   降维               很多模型支持输出更短的向量（如 1536 → 512）
   sparsevec          向量稀疏时才有意义
```

### 10.2 索引必须放得进内存

```
   HNSW 的图结构如果放不进 shared_buffers / 系统缓存，
   查询会退化成大量随机磁盘 IO —— 性能不是变慢，是【崩塌】。

   估算索引大小：先在 10% 的数据上建一次索引，
                pg_relation_size() 看大小，再线性外推。
```

### 10.3 建索引很慢，把资源给足

```sql
SET maintenance_work_mem = '8GB';           -- 给够，否则会落磁盘，慢几倍
SET max_parallel_maintenance_workers = 7;   -- 并行建索引
CREATE INDEX CONCURRENTLY ...               -- 线上加索引别锁表
```

```
   顺序建议：【先灌数据，再建索引】。
   边插边建索引会慢很多 —— 这一点和 B+ 树一致。
```

### 10.4 索引维度上限

```
   vector   最多 16000 维，但【建索引最多 2000 维】
   halfvec  建索引最多 4000 维

   → 用了 3072 维的模型（如 text-embedding-3-large）想建索引？
     要么降维，要么转 halfvec。
```

## 十一、速查

### 三类索引的取舍

```
   ┌────────────────────────────────────────────────────────────┐
   │  B+ 树      精确 · 有序范围      代价：写时页分裂            │
   │  LSM        顺序写 · 高吞吐      代价：读要查多层            │
   │  向量索引   高维下依然快         代价：【结果只是近似】       │
   └────────────────────────────────────────────────────────────┘
```

### 运算符

```
   <=>   余弦距离    文本 embedding 首选
   <#>   负内积      向量已归一化时等价于余弦，略快
   <->   L2          未归一化、关心绝对距离
   <+>   L1

   ⚠️ 必须和 embedding 模型一致，用错不报错、只是结果不对
```

### 建索引

```sql
-- HNSW（默认选它）
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;              -- 线上调这个换召回率

-- IVFFlat（内存紧张时）
CREATE INDEX ON items USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 1000);                 -- ≈ 行数/1000，百万以上用 sqrt(行数)
SET ivfflat.probes = 32;               -- ≈ sqrt(lists)
```

### 查询形态

```sql
-- ✓ 唯一能用上索引的写法
SELECT ... ORDER BY embedding <=> $1 LIMIT 10;

-- ✗ 用不上索引
SELECT ... WHERE embedding <=> $1 < 0.5;

-- 带过滤时（0.8+）
SET hnsw.iterative_scan = relaxed_order;
```

### 排查清单

```
   结果条数比预期少        →  过滤+向量的候选丢失（第七节），开迭代扫描
   结果不相干             →  距离运算符和模型不匹配（第三节）
   走了 Seq Scan          →  查询不是 ORDER BY ... LIMIT 形式（4.2）
   突然变很慢             →  索引放不进内存（10.2）；或 IVFFlat 簇失真了，REINDEX
   召回率上不去           →  调大 ef_search / probes（第六节）
   建索引巨慢             →  maintenance_work_mem 太小 / 没并行（10.3）
   建索引报维度错误        →  超过 2000 维，改 halfvec 或降维（10.4）
```
