# 乐观锁与悲观锁：从一次超卖说起

> 一句话主线：**这不是两种锁，是两种面对冲突的态度。**
> 悲观锁认为"一定有人和我抢"，所以先把门锁上；乐观锁认为"多半没人和我抢"，所以直接干，提交时再检查有没有被人插队。
>
> 严格讲，**乐观锁根本不是锁**——它没有任何加锁动作，只有一次"你动过没有"的检查。

选型的唯一依据是**冲突概率**，不是"哪个更高级"。全文围绕这一句展开。

> 环境：MySQL 8.0 / InnoDB，默认隔离级别 **REPEATABLE READ**（隔离级别会实质影响第三节的加锁范围）。
> 本篇 SQL 均为**示例**，未附实测日志。

## 一、先看 bug：为什么会超卖

库存 100 件，代码看起来毫无问题：

```java
int stock = selectStock(id);          // ① 读
if (stock > 0) {                      // ② 判断
    updateStock(id, stock - 1);       // ③ 写回
}
```

两个线程一起跑：

```
   时间    线程 A                      线程 B                 数据库 stock
   ────────────────────────────────────────────────────────────────────
    t1     读到 100                                              100
    t2                                 读到 100                  100
    t3     判断 100 > 0  ✓                                       100
    t4                                 判断 100 > 0  ✓           100
    t5     写回 99                                                99
    t6                                 写回 99                    99   ← 【出事了】

           卖出去 2 件，库存只扣了 1 件
```

问题的名字叫 **读-改-写竞态（read-modify-write race）**：

```
   ┌── 读 ──┐        ┌── 写 ──┐
   │  100   │  ....  │   99   │
   └────────┘   ↑    └────────┘
                └─ 这段空隙里，别人也读到了 100
```

**空隙是万恶之源。**所有的解法都是在处理这段空隙：

```
   悲观锁  →  不许任何人进入这段空隙
   乐观锁  →  允许你进入，但写的时候检查空隙里有没有别人来过
   条件更新 →  【干脆消灭这段空隙】（4.3，最容易被忽略的一条路）
```

还有一种同构的 bug，形态是"**查-插**"（先查有没有，没有就插入）——它的空隙一模一样，
但因为"记录还不存在"，**锁和 version 都用不上**，得靠唯一索引。见第五节。

## 二、两种态度

```
   ┌─────────────────────────────────────────────────────────────┐
   │  悲观锁 Pessimistic                                          │
   │                                                              │
   │  "我改这条数据的时候，一定会有人来抢"                          │
   │                                                              │
   │   ┌──────┐                                                  │
   │   │ 上锁 │ → 读 → 改 → 写 → 解锁                             │
   │   └──────┘                                                  │
   │      ↑ 别人从这里就开始等了                                   │
   │                                                              │
   │  代价：等待、连接占用、死锁风险                                │
   │  收益：一次成功，不用重试；逻辑简单                            │
   └─────────────────────────────────────────────────────────────┘

   ┌─────────────────────────────────────────────────────────────┐
   │  乐观锁 Optimistic                                           │
   │                                                              │
   │  "多半没人和我抢，真撞上了我就重来"                            │
   │                                                              │
   │   读（记下版本）→ 改 → 写【带上版本条件】                       │
   │                          │                                   │
   │                          ├─ 影响 1 行 → 成功                  │
   │                          └─ 影响 0 行 → 有人插队 → 重来        │
   │                                                              │
   │  代价：要重试；冲突多时反而更慢                                │
   │  收益：没有等待、没有死锁、不长时间占用连接                     │
   └─────────────────────────────────────────────────────────────┘
```

对照表：

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 有没有真的加锁 | 有 | **没有**（只有一次条件检查） |
| 冲突什么时候发现 | 进门时（提前挡住） | 提交时（事后发现） |
| 冲突了怎么办 | 等 | 重试 |
| 死锁 | **可能** | 不可能 |
| 长事务的影响 | 灾难（锁一直不放） | 几乎没有 |
| 冲突多时 | 排队，但都能成 | 反复重试，CPU 空转 |
| 冲突少时 | 白白付出加锁开销 | 几乎零成本 |
| 跨服务/跨库 | 要分布式锁 | 天然可用 |

## 三、悲观锁怎么写

### 3.1 前提：普通 SELECT 是不加锁的

这一点必须先说清楚，否则后面全是误会。

InnoDB 里普通 `SELECT` 是 **快照读（MVCC）**——它读的是一个历史版本，**不加任何锁，也拦不住任何人**：

> ⤵ **依据**：《[事务与 MVCC · 第四、五节](../mysql/事务与MVCC.md)》——每行都带着 `trx_id`/`roll_ptr`，沿 undo 版本链能走出它的全部历史；读哪一个版本由 ReadView 判定。这就是"读不加锁"的实现方式。

```sql
SELECT stock FROM product WHERE id = 100;   -- 锁？没有。一把都没有。
```

所以想用悲观锁，必须显式转成 **当前读**：

```sql
SELECT stock FROM product WHERE id = 100 FOR UPDATE;   -- 排他锁 X
SELECT stock FROM product WHERE id = 100 FOR SHARE;    -- 共享锁 S（8.0 语法）
```

> `LOCK IN SHARE MODE` 是 `FOR SHARE` 的旧写法，8.0 仍兼容，新代码用 `FOR SHARE`。

两者的区别：

```
   FOR SHARE   （S 锁）  别人还能读，但不能改。多个 S 锁可以共存。
   FOR UPDATE  （X 锁）  别人既不能加 S 也不能加 X。独占。
```

**扣库存必须用 `FOR UPDATE`**。用 `FOR SHARE` 会死锁——两个事务都拿着 S 锁，都想升级成 X 锁，互相等对方先放手。

### 3.2 完整写法

```sql
BEGIN;

SELECT stock FROM product WHERE id = 100 FOR UPDATE;   -- ① 锁住这一行
-- 应用层判断 stock > 0

UPDATE product SET stock = stock - 1 WHERE id = 100;   -- ② 改

COMMIT;                                                 -- ③ 锁在这里才释放
```

Java：

```java
@Transactional(rollbackFor = Exception.class)
public void deduct(long productId) {
    Product p = productMapper.selectForUpdate(productId);   // FOR UPDATE
    if (p.getStock() <= 0) {
        throw new BizException("库存不足");
    }
    productMapper.updateStock(productId, p.getStock() - 1);
}
```

```
   时间     线程 A                       线程 B
   ─────────────────────────────────────────────────────────
    t1      BEGIN
    t2      SELECT ... FOR UPDATE  ✓
    t3                                    BEGIN
    t4                                    SELECT ... FOR UPDATE
    t5                                       ↓ 【阻塞】
    t6      UPDATE stock = 99                ↓ 还在等
    t7      COMMIT ──────────────────────▶   ✓ 读到 99（不是 100）
    t8                                    UPDATE stock = 98
    t9                                    COMMIT

            结果正确：卖 2 件，扣 2 件
```

**关键：锁的生命周期 = 事务的生命周期。**`@Transactional` 掉了，锁在 `SELECT` 返回的一瞬间就没了，代码看着有锁，实际裸奔。

### 3.3 三个真实的坑

#### 坑一：WHERE 没走索引 → 锁的远不止一行

```sql
-- product.name 上没有索引
SELECT * FROM product WHERE name = '茅台' FOR UPDATE;
```

InnoDB 的**行锁是加在索引记录上的**。没有索引可用时，只能全表扫描，**扫到的每一行都会被锁上**——效果接近锁表。

> ⤵ **依据**：《[B+ 树原理 · 第七章](../mysql/B+树原理.md)》——二级索引的叶子存的是主键值，行锁本质上锁的就是这些索引记录。没有索引，就没有可以精确锁定的目标。

这里还有一个和**隔离级别**相关的放大效应（隔离级别的定义见《[事务与 MVCC · 第三节](../mysql/事务与MVCC.md)》，间隙锁的形态见《[InnoDB 锁 · 2.2](../mysql/InnoDB锁.md)》）：

```
   READ COMMITTED    扫描后会把不匹配的行锁释放掉（半一致性读）
                     —— 但"先锁后放"这个过程本身已经产生了争用

   REPEATABLE READ   【默认级别】不匹配的行锁也【一直持有到事务提交】
                     —— 而且是 next-key 锁，连间隙一起锁
```

也就是说，在 MySQL 的默认隔离级别下，这个坑比大多数人以为的更严重。结论：**悲观锁的 WHERE 条件必须走索引**，上线前用 `EXPLAIN` 确认（见《[索引优化 · 第五章](../mysql/索引优化.md)》）。

#### 坑二：死锁

两个事务按不同顺序锁同样两行：

```
   线程 A                        线程 B
   ─────────────────────────────────────────────
   锁 id=1  ✓                    锁 id=2  ✓
   想锁 id=2 → 等 B              想锁 id=1 → 等 A
              └────── 死锁 ──────┘
```

InnoDB 会检测到并回滚其中一个，报 `Deadlock found when trying to get lock`。

**解法是固定加锁顺序**——比如永远按主键升序锁：

```java
ids.stream().sorted().forEach(id -> mapper.selectForUpdate(id));
```

#### 坑三：事务里调外部接口

```java
@Transactional
public void deduct(long id) {
    Product p = mapper.selectForUpdate(id);   // 锁住了
    riskService.check(id);                    // ← 调用外部接口，300ms ~ 超时 5s
    mapper.updateStock(id, p.getStock() - 1);
}                                             // 锁到这里才放
```

这一行会把行锁和数据库连接同时占住好几秒。高并发下瞬间打满连接池，**整个库跟着挂**。

```
   悲观锁的铁律：加锁到解锁之间，只能有纯数据库操作。
                 任何 RPC、HTTP、消息发送、文件 IO 都必须挪到事务外。
```

### 3.4 `SKIP LOCKED`：任务队列的专用武器

多个 worker 抢同一张任务表时，普通 `FOR UPDATE` 会让它们排成一队——明明有一堆任务，却只有一个人在干活。

```sql
SELECT * FROM task WHERE status = 'PENDING'
ORDER BY id LIMIT 10
FOR UPDATE SKIP LOCKED;        -- 【跳过】已被别人锁住的行
```

```
   普通 FOR UPDATE              SKIP LOCKED
   ──────────────────────────────────────────────
   worker1 锁 1~10              worker1 拿 1~10
   worker2 等 worker1           worker2 【跳过】1~10，直接拿 11~20
   worker3 等 worker1           worker3 拿 21~30
       ↑ 串行                        ↑ 真并行
```

MySQL 8.0 / PostgreSQL 都支持。做数据库任务队列时这一条能顶掉半个中间件。

### 3.5 别把 `synchronized` 当悲观锁用

这是最高频的错误：

```java
public synchronized void deduct(long id) {   // ← 一上集群就废了
    ...
}
```

```
   单机                              集群（3 个实例）
   ┌──────────┐                  ┌──────┐ ┌──────┐ ┌──────┐
   │  JVM     │                  │JVM 1 │ │JVM 2 │ │JVM 3 │
   │ synchron │  ✓ 有效           │ sync │ │ sync │ │ sync │
   └──────────┘                  └──────┘ └──────┘ └──────┘
                                     ↑ 三把【互不相干】的锁，等于没锁
```

`synchronized` / `ReentrantLock` 的作用域是**单个 JVM**。跨进程必须用数据库行锁或分布式锁（Redis / ZooKeeper）。

## 四、乐观锁怎么写

### 4.1 版本号法（标准解法）

加一列 `version`：

```sql
ALTER TABLE product ADD COLUMN version INT NOT NULL DEFAULT 0;
```

读的时候把 `version` 一起读出来，**写的时候把它当条件**：

```sql
-- ① 读（普通 SELECT，不加锁）
SELECT stock, version FROM product WHERE id = 100;
-- 假设读到 stock = 100, version = 7

-- ② 写
UPDATE product
   SET stock = stock - 1,
       version = version + 1          -- ← 千万别漏这句
 WHERE id = 100
   AND version = 7;                   -- ← 这就是"乐观锁"的全部
```

然后**看影响行数**：

```
   affected rows = 1  →  成功。version 从 7 变成 8
   affected rows = 0  →  version 已经不是 7 了，说明有人在我之前改过 → 重试
```

时序：

```
   时间     线程 A                          线程 B                stock/version
   ──────────────────────────────────────────────────────────────────────────
    t1      读 stock=100, v=7                                        100 / 7
    t2                                      读 stock=100, v=7        100 / 7
    t3      UPDATE ... WHERE v=7  ✓ 1 行                              99 / 8
    t4                                      UPDATE ... WHERE v=7
    t5                                         ↓ 影响 0 行 ✗          99 / 8
    t6                                      重新读：stock=99, v=8
    t7                                      UPDATE ... WHERE v=8 ✓    98 / 9

            结果正确，且【全程没有任何等待】
```

### 4.2 乐观锁其实借用了一把锁

一个常被含糊带过的点：**"检查 version" 和 "更新" 为什么是原子的？**

答案是——它们本来就在**同一条 SQL** 里。InnoDB 执行这条 `UPDATE` 时，会给匹配到的行加排他锁，在锁的保护下完成"比较 version + 写入"。

```
   ┌────────────────────────────────────────────────┐
   │  UPDATE ... WHERE id=100 AND version=7         │
   │                                                 │
   │  InnoDB 内部：加 X 锁 → 比较 version → 写 → 放锁 │
   │                └──────── 原子 ────────┘         │
   └────────────────────────────────────────────────┘
```

所以准确的说法是：

```
   乐观锁不是"没有锁"，
   而是把锁的范围【从"读到写的整段业务逻辑"压缩到了"一条 SQL 语句"】。

   悲观锁持锁：  SELECT ──────── 业务判断 ──────── UPDATE ── COMMIT   （毫秒~秒级）
   乐观锁持锁：                                    UPDATE            （微秒级）
```

这才是它快的真正原因——不是消灭了锁，是把持锁时间缩短了几个数量级。

### 4.3 更好的路：把校验挪进 SQL，连重试都省了

**很多号称"需要乐观锁"的场景，其实一条 SQL 就够了。**

回头看超卖：我们真正关心的是"库存不能扣成负数"，而**不是**"库存值有没有被别人改过"。那就直接写：

```sql
UPDATE product
   SET stock = stock - 1
 WHERE id = 100
   AND stock > 0;              -- ← 约束的是【结果合法】，不是【值没变】
```

```
   affected rows = 1  →  扣成功
   affected rows = 0  →  库存真的没了（不是冲突！）→ 直接返回"售罄"，【不需要重试】
```

对比三种写法：

| 写法 | 需要额外列 | 需要重试 | 无谓失败 |
|---|---|---|---|
| `FOR UPDATE` 悲观锁 | 否 | 否 | 无（但要排队等） |
| `WHERE version = 7` | 要 `version` | **要** | **有**（别人改了别的字段也会失败） |
| `WHERE stock > 0` | 否 | **不要** | **无** |

```
   ┌──────────────────────────────────────────────────────────┐
   │  能写成"单条 UPDATE + 业务条件"的，就不要上乐观锁。         │
   │  乐观锁是给"必须先读出来、在应用层算一算才能写"的场景准备的。│
   └──────────────────────────────────────────────────────────┘
```

什么时候必须用 version 法？当新值**不能由 SQL 自己算出来**时。比如：

```java
// 新状态取决于一坨业务规则，SQL 表达不了
Order o = mapper.select(id);
OrderStatus next = stateMachine.next(o.getStatus(), event);   // 应用层计算
mapper.updateStatus(id, next, o.getVersion());                // 这时才需要 version
```

### 4.4 用业务字段当版本？小心 ABA

省掉 `version` 列，直接拿旧值当条件：

```sql
UPDATE product SET stock = stock - 1
 WHERE id = 100 AND stock = 100;      -- 用 stock 自己当版本
```

看着能用，但有 **ABA 问题**：

```
   我读到 stock = 100
        ↓
   线程 B 卖出 1 件  → 99
   线程 C 退货 1 件  → 100
        ↓
   我 UPDATE ... WHERE stock = 100  → 成功了！
        ↑ 我以为"没人动过"，实际上被动了两次
```

对扣库存来说 ABA 通常无害（结果数值仍然对）。但如果中间那两次操作触发了别的副作用（发券、记流水、改状态），你的判断就是错的。

**`version` 单调递增，永不回头，天生没有 ABA。**这就是要单独加一列的理由。

### 4.5 重试怎么写

```java
private static final int MAX_RETRY = 3;

public void deduct(long id) {
    for (int i = 0; i < MAX_RETRY; i++) {
        // 【必须重新读】——拿旧 version 重试是无限失败
        Product p = mapper.select(id);
        if (p.getStock() <= 0) {
            throw new BizException("库存不足");
        }

        int rows = mapper.updateWithVersion(id, p.getStock() - 1, p.getVersion());
        if (rows == 1) {
            return;                                   // 成功
        }

        backoff(i);                                   // 退避后再来
    }
    throw new BizException("系统繁忙，请重试");         // 【必须有上限】
}

private void backoff(int attempt) {
    try {
        // 指数退避 + 随机抖动，避免一堆线程同时重试撞在一起
        Thread.sleep((1L << attempt) * 10 + ThreadLocalRandom.current().nextInt(10));
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new BizException("被中断");
    }
}
```

三条硬要求：

```
   ① 每次重试都要【重新读】     拿旧 version 重试 100 次也只会失败 100 次
   ② 重试次数【必须有上限】     无限重试 = 冲突高峰时把 CPU 和数据库一起打死
   ③ 退避要加【随机抖动】       否则失败的线程会同步苏醒、再次撞车
```

### 4.6 重试和 `@Transactional` 的冲突（高级坑）

这个坑很隐蔽：

```java
@Transactional                        // ← 事务在【外面】
public void deduct(long id) {
    for (int i = 0; i < 3; i++) {     // ← 重试在【里面】
        ...
    }
}
```

问题有两个：

```
   ① 三次重试全在【同一个事务】里。
      失败的那次读到的仍是【同一个 MVCC 快照】——
      重新 SELECT 也读不到别人的新值，于是必然一直失败到耗尽次数。
      ⤵ 机制见《事务与 MVCC · 第六节》：RR 下 ReadView 只在
        第一次快照读时生成，之后【一直复用】—— 这正是重试读不到新值的原因。

   ② 如果中间抛过异常被 catch 住，事务可能已被标记 rollback-only，
      最后 COMMIT 时直接甩 UnexpectedRollbackException。
```

正确的结构是**重试在外，事务在内**——每次重试开一个全新的事务：

```java
// 外层：不加事务，只管重试
public void deduct(long id) {
    for (int i = 0; i < 3; i++) {
        if (txService.tryDeduct(id)) return;         // 每次调用 = 一个新事务
        backoff(i);
    }
    throw new BizException("系统繁忙");
}

@Service
class TxService {
    @Transactional(rollbackFor = Exception.class)
    public boolean tryDeduct(long id) {              // 内层：一次尝试 = 一个事务
        ...
        return rows == 1;
    }
}
```

> 注意 `tryDeduct` 必须是**另一个 Bean 的方法**，否则自调用会让 `@Transactional` 失效——见《[Spring 事务 · 6.4](../spring/Spring-事务.md)》。

### 4.7 JPA / Hibernate 的 `@Version`

不用自己写条件，加个注解就行：

```java
@Entity
public class Product {
    @Id
    private Long id;

    private Integer stock;

    @Version                          // ← 就这一行
    private Integer version;
}
```

Hibernate 会自动把 `UPDATE` 改写成带 `WHERE version = ?` 的形式，并自动 `version + 1`。冲突时抛 `OptimisticLockException` / `ObjectOptimisticLockingFailureException`。

MyBatis-Plus 的对应物是 `@Version` + `OptimisticLockerInnerInterceptor`。

## 五、第三条路：唯一索引，让数据库直接拒绝

前面四节全部围绕一个动作——**改**。但还有一类并发 bug，形态是**插**，上面那些锁一个都不管用。

### 5.1 同构的 bug：查-插

```java
// 一人一张券
if (couponMapper.countByUser(userId, actId) == 0) {   // ① 查：没领过
    couponMapper.insert(userId, actId);               // ② 插
}
```

```
   时间    线程 A                      线程 B              DB 里的记录数
   ─────────────────────────────────────────────────────────────────
    t1     count = 0                                          0
    t2                                count = 0               0
    t3     insert  ✓                                          1
    t4                                insert  ✓               2   ← 领了两张
```

和第一节的超卖是**一模一样的空隙**，只是"读-改-写"换成了"查-插"。

### 5.2 为什么锁在这里不好使

**因为没有行可以锁。**

```
   悲观锁  SELECT ... FOR UPDATE   →  锁哪一行？记录还不存在
   乐观锁  WHERE version = 7       →  version 在哪？记录还不存在
```

锁和 `version` 都是**加在已存在的行上**的机制。而"防止重复插入"面对的是一行**还不存在**的数据。

> RR 隔离级别下的**间隙锁**确实能挡住，但你得精心设计一条能锁住正确间隙的查询，而且并发插入不同 key 时极易死锁。属于能用但不该用。
>
> ⤵ 间隙锁为什么能挡住插入、以及"并发插入同一个 key 为什么会死锁"，见《[InnoDB 锁 · 2.2 / 4.1 / 5.2](../mysql/InnoDB锁.md)》。

### 5.3 正确做法：把约束交给数据库

```sql
ALTER TABLE coupon_record
  ADD UNIQUE KEY uk_user_act (user_id, activity_id);
```

**然后不要先查再插，直接插，靠异常分支**：

```java
public String draw(long userId, long actId) {
    try {
        couponMapper.insert(new CouponRecord(userId, actId));
        return "领取成功";
    } catch (DuplicateKeyException e) {   // Spring 把 MySQL 1062 翻译成这个
        return "您已领取过";
    }
}
```

```
   时间    线程 A                      线程 B
   ─────────────────────────────────────────────────────────
    t1     INSERT  ✓                   INSERT
    t2                                    ↓ Duplicate entry ✗
                                       捕获异常 → "您已领取过"
```

```
   ✗ 先 SELECT 判断再 INSERT ──── 中间有空隙，防不住并发
   ✓ 直接 INSERT，撞了再说 ────── 判断和写入由数据库【原子完成】
```

思路和乐观锁完全一致：**把"检查"和"写入"塞进同一条语句**，让数据库在它自己的锁保护下一次做完（对照 4.2）。

### 5.4 和 4.3 是一对

```
   ┌──────────────────────────────────────────────────────────┐
   │  条件更新   管住【改】   UPDATE ... WHERE stock > 0        │
   │  唯一索引   管住【插】   UNIQUE KEY (user_id, act_id)      │
   │                                                           │
   │  共同点：不用锁、不用重试、不用额外的 version 列            │
   │          都是把校验下沉到数据库，消灭那段空隙               │
   └──────────────────────────────────────────────────────────┘
```

**这两条应该是最先考虑的**，锁是它们表达不了时才上的。

唯一索引还有三条锁给不了的好处：

```
   ① 不依赖应用代码
      代码写错了、有人手工执行 SQL、跑了个补数据脚本 —— 约束照样生效

   ② 不依赖运行时状态
      不怕重启、不怕扩容、不怕集群（对比 3.5 的 synchronized 一上集群就废）

   ③ 它是【最后一道防线】
      上面所有的锁都是"尽量别撞"，唯一索引是"撞了也进不去"
```

所以正确的定位不是"用它替代锁"，而是——**即使用了锁，唯一索引也该加上当兜底**。

### 5.5 它内部靠什么保证

> ⤵ **依据**：《[B+ 树原理 · 第七章](../mysql/B+树原理.md)》——**唯一索引本身就是一棵 B+ 树**。

InnoDB 插入时必须先在这棵树上定位插入位置，顺带就完成了唯一性检查：

```
   插入 (user_id=7, act_id=99)
        ↓
   在 uk_user_act 这棵 B+ 树上查找位置
        ↓
   ┌─ 位置上已经有相同的 key  →  报 1062，插入失败
   └─ 没有                    →  写进去
        ↑ 这两步在【页锁保护下原子完成】
          应用层的"先查后插"永远做不到
```

这也解释了 5.6 坑三的那个副作用：**唯一性检查必须把页读进内存**。

### 5.6 五个坑

#### 坑一：NULL 不参与唯一性检查 ⚠️

```sql
UNIQUE KEY uk_user_act (user_id, activity_id)
```

```
   插入 (7, NULL)   ✓
   插入 (7, NULL)   ✓   ← 又成功了！
   插入 (7, NULL)   ✓   ← 还能成功！
```

SQL 标准规定 `NULL != NULL`，所以多个 NULL 在唯一索引里**可以共存**，唯一约束等于没有。

> 这正好印证《[数据表设计 · 四条经验②](../mysql/数据表设计.md)》的"**全部 NOT NULL，空值用无意义值填充**"。
> 唯一索引涉及的列，`NOT NULL` 不是风格问题，是**正确性问题**。

#### 坑二：软删除会撞唯一键

```
   用户领了券 → (7, 99, is_deleted=0)
   券被作废   → (7, 99, is_deleted=1)
   用户再领   → INSERT (7, 99) → 【撞唯一键】，可他明明该能领
```

解法是把"删除"编进唯一键，且**不能用 0/1 标志**（那样只能删一次，删第二次又撞）：

```sql
deleted_at BIGINT NOT NULL DEFAULT 0 COMMENT '0=未删除，否则为删除时间戳(ms)',
UNIQUE KEY uk_user_act (user_id, activity_id, deleted_at)
```

```
   未删除的永远是 deleted_at = 0  →  同一 (user,act) 只能有一条活的  ✓
   删除后变成时间戳               →  不再和新记录冲突               ✓
```

《数据表设计》里那个 `deleted_at BIGINT NOT NULL DEFAULT 0` 正是为这个准备的。

#### 坑三：唯一索引的写入比普通索引慢

InnoDB 有个 **change buffer** 优化：写二级索引时，如果目标页不在内存里，先把改动记在 change buffer 里攒着，以后合并，**省掉一次随机读**。

> ⤵ **依据**：《[InnoDB 的内存 · 第四节](../mysql/BufferPool与内存.md)》——那里有 change buffer 的完整机制，以及它在什么业务形态下才真正划算。

唯一索引用不上它：

```
   普通二级索引  →  不用管重不重复  →  可以先记账，页不必读进来   ✓ 能用
   唯一索引      →  必须确认重不重复 →  【必须把页读进内存】      ✗ 用不了
```

所以：**只在真的需要唯一约束的地方加 UNIQUE**，别为了"顺便快一点"乱加。

#### 坑四：分库分表后只在分片内唯一

```
   UNIQUE KEY (user_id, act_id)  +  按 user_id 分片   →  仍然全局唯一  ✓
   UNIQUE KEY (order_no)         +  按 user_id 分片   →  【不唯一】    ✗
                                                          两个分片各插一条，谁也不知道
```

唯一键必须**包含分片键**，否则约束只在单个物理表内成立。

#### 坑五：异常捕获别捞过头

```java
try {
    insert(...);
} catch (Exception e) {          // ✗ 把所有异常都当成"已领取过"
    return "您已领取过";           //   连接断了、字段超长也这么报
}
```

必须精确捕获 `DuplicateKeyException`。三个替代语法各有代价：

| 写法 | 问题 |
|---|---|
| `INSERT IGNORE` | 连**其他**错误（截断、类型不符）一起吞掉，容易掩盖真 bug |
| `ON DUPLICATE KEY UPDATE` | 可以用，但要清楚影响行数：插入=1，更新=2 |
| `REPLACE INTO` | **危险**——实际是 DELETE + INSERT，其他列被清空、自增 id 变了、外键可能级联删 |

### 5.7 真正的用武之地：幂等

这个手段的价值远不止发券，它是**做幂等的标准解法**：

| 场景 | 唯一键加在哪 |
|---|---|
| 防止重复下单 | `UNIQUE (user_id, request_id)`，request_id 由前端生成 |
| 支付回调重复通知 | `UNIQUE (pay_no)` |
| MQ 消息重复消费 | 消费记录表 `UNIQUE (msg_id)` |
| 一人一张券 | `UNIQUE (user_id, activity_id)` |
| 用户手机号唯一 | `UNIQUE (phone)` |

```
   幂等的本质 = "这件事只能发生一次"
   而"只能有一条记录"正是唯一索引的原话
```

## 六、同一个思想的三层实现

乐观锁不是数据库特有的，它在三个层次上是**同一件事**：

```
   ┌──────────────────────────────────────────────────────────────────┐
   │  CPU 指令层     cmpxchg                                           │
   │                 "如果这个内存地址还是旧值，就换成新值"              │
   │                 由硬件保证原子                                     │
   ├──────────────────────────────────────────────────────────────────┤
   │  JVM 层         AtomicInteger.compareAndSet(expect, update)       │
   │                 失败就【自旋】重来                                  │
   ├──────────────────────────────────────────────────────────────────┤
   │  数据库层        UPDATE ... WHERE version = ?                      │
   │                 失败（0 行）就【重试】                              │
   └──────────────────────────────────────────────────────────────────┘

           读旧值 → 算新值 → 【带着旧值做条件】写回 → 失败就重来
                              ↑ 三层一模一样
```

JVM 层的样子：

```java
AtomicInteger stock = new AtomicInteger(100);

stock.decrementAndGet();     // 内部就是一个 CAS 自旋循环
```

展开看它的本质：

```java
int prev, next;
do {
    prev = stock.get();              // 读（相当于读 version）
    next = prev - 1;                 // 算
} while (!stock.compareAndSet(prev, next));   // 带着旧值写，失败就重来
```

**ABA 在这一层也存在**，解法同样是加版本号：

```java
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(100, 0);
//                                                                      ↑ stamp 就是 version
```

```
   数据库的 version 列   ≡   AtomicStampedReference 的 stamp
```

> 顺带一提：LSM 这类**只追加**的存储引擎，在存储层根本没有"写-写冲突"的概念——两个人同时写同一个 key，只是各自追加一个版本，序号大的赢，谁都不用等谁（见《[LSM Tree 原理](../storage/LSM树原理.md)》的序号与墓碑机制）。这意味着冲突检测必须由**上层**负责，而**乐观锁就是那个上层**：TiKV / Percolator 的事务模型正是把版本检查做在 KV 引擎之上。

## 七、怎么选：只看冲突概率

### 7.1 判断依据

```
                    ┌──────────────────────┐
                    │  同一条数据上的冲突率  │
                    └──────────┬───────────┘
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
         低（< 10%）                        高（> 20%）
              │                                 │
         【乐观锁】                          【悲观锁】
      没有等待、没有死锁                   排队但一次成功
      不占连接                            避免重试风暴
```

**最容易犯的错：拿 QPS 当冲突率。**

```
   10000 QPS 分散在 10000 个 SKU 上
      → 每个 SKU 大约 1 QPS，几乎不冲突     → 【乐观锁】

   10000 QPS 全砸在 1 个秒杀商品上
      → 每次都冲突，乐观锁会疯狂重试         → 悲观锁也顶不住，
                                             要上 Redis 预扣 / 队列串行化
```

```
   冲突率看的是【单个 key 上的并发】，不是整个接口的 QPS。
```

### 7.2 其他一票否决项

| 情况 | 结论 |
|---|---|
| 事务中间要调外部接口 / 发消息 | **禁用悲观锁**（锁和连接会被占死） |
| 跨库、跨服务 | 悲观锁用不了，走乐观锁或分布式锁 |
| 用户在 UI 上编辑几分钟再保存 | **只能乐观锁**（不可能锁几分钟） |
| 必须"读到就一定能改" | 悲观锁 |
| 批量操作、抢任务 | `FOR UPDATE SKIP LOCKED` |
| 新值能由 SQL 自己算出来 | **两个都不要**，直接条件更新（4.3） |

### 7.3 决策顺序

```
   ⓪ 要防的是【重复插入】吗？（一人一张、幂等、防重复提交）
         是 → 唯一索引 + 捕获 DuplicateKeyException，收工（第五节）
              锁在这里根本用不上 —— 记录还不存在，没有行可锁
         否 ↓
   ① 能写成一条 UPDATE + 业务条件吗？（WHERE stock > 0）
         是 → 就这么写，收工。既不用锁也不用重试（4.3）
         否 ↓
   ② 事务里有外部调用 / 需要长时间持有吗？
         是 → 乐观锁（悲观锁会拖垮连接池）
         否 ↓
   ③ 同一条数据上冲突频繁吗？
         否 → 乐观锁
         是 → 悲观锁 FOR UPDATE（务必确认 WHERE 走索引）
         极高（秒杀）→ 都不够，Redis 预扣库存 + 异步落库
```

前两步是"**不用锁**"的路，能走就别往下走。真上了锁，唯一索引仍建议加上当兜底（5.4）。

## 八、典型场景对照

| 场景 | 选择 | 为什么 |
|---|---|---|
| **普通商品扣库存** | 条件更新 `WHERE stock >= n` | 新值 SQL 能算，不需要锁也不需要重试 |
| **秒杀** | Redis 预扣 + 异步落库 | 单 key 冲突率接近 100%，数据库层怎么搞都是瓶颈 |
| **账户转账** | 悲观锁 `FOR UPDATE`，**按账户 ID 升序加锁** | 涉及两行、必须成功、冲突不低；固定顺序防死锁 |
| **订单状态机流转** | 乐观锁（用 `status` 当版本） | `WHERE status = 'PAID'` 天然防重复流转 |
| **后台运营编辑商品** | 乐观锁 `@Version` | 两个人同时编辑，后保存的不该覆盖先保存的；提示"数据已被他人修改，请刷新" |
| **抢任务 / 消费队列表** | `FOR UPDATE SKIP LOCKED` | 让多个 worker 真并行，而不是排队 |
| **JVM 内计数器** | `AtomicLong`（CAS） | 单机、单地址，CAS 就是最优解 |
| **发放优惠券（一人一张）** | 唯一索引（第五节） | 要防的是重复**插入**，没有行可锁 |
| **防重复提交 / 幂等** | 唯一索引（5.7） | "只能发生一次" = "只能有一条记录" |

后两行是同一件事：**唯一索引是最被低估的并发控制手段**。它不参与"谁先谁后"的博弈，直接让第二条记录进不了库。

## 九、坑速查

```
   ✗ 用 synchronized 防超卖 ─────────── 一上集群就失效（3.5）
   ✗ FOR UPDATE 的 WHERE 没走索引 ───── 锁的远不止一行（3.3 坑一）
   ✗ 忘了 @Transactional ───────────── FOR UPDATE 返回即解锁，等于没锁（3.2）
   ✗ 事务里调外部接口 ──────────────── 锁 + 连接占死，打满连接池（3.3 坑三）
   ✗ 多行加锁顺序不固定 ────────────── 死锁（3.3 坑二）
   ✗ UPDATE 忘了 version = version + 1  版本永远不变，乐观锁形同虚设（4.1）
   ✗ 重试时不重新读 ──────────────── 拿旧 version 重试，必然一直失败（4.5）
   ✗ 无限重试 ────────────────────── 冲突高峰时把数据库和 CPU 一起拖死（4.5）
   ✗ 重试写在 @Transactional 内部 ──── 同一快照读不到新值，重试必然失败（4.6）
   ✗ 用业务字段当版本 ────────────── ABA（4.4）
   ✗ 只判断异常不看影响行数 ────────── 乐观锁失败【不抛异常】，
                                       返回 0 行而已，不检查就静默丢数据（4.1）
   ── 唯一索引 ──────────────────────────────────────────────────
   ✗ 先 SELECT 判断再 INSERT ──────── 中间有空隙，防不住并发（5.3）
   ✗ 唯一索引的列允许 NULL ────────── NULL != NULL，
                                       多个 NULL 共存，约束等于没有（5.6 坑一）
   ✗ 软删除用 is_deleted 0/1 ──────── 删第二次就撞唯一键，
                                       要用 deleted_at 时间戳（5.6 坑二）
   ✗ 为了"顺便快点"乱加 UNIQUE ────── 唯一索引用不了 change buffer，
                                       写入更慢（5.6 坑三）
   ✗ 唯一键不含分片键 ─────────────── 分库分表后只在分片内唯一（5.6 坑四）
   ✗ catch (Exception e) 当成重复 ─── 连接断了也报"您已领取过"，
                                       要精确捕获 DuplicateKeyException（5.6 坑五）
   ✗ 用 REPLACE INTO 去重 ─────────── 实为 DELETE + INSERT，
                                       其他列被清空、自增 id 变了（5.6 坑五）
```

倒数第一条最阴险：

```java
mapper.updateWithVersion(id, newStock, version);   // ← 返回值没接
// 以为成功了，其实是 0 行。数据没改，用户以为下单成功了。
```

**乐观锁的 UPDATE，返回值必须检查。**

## 十、一页速查

```
   ┌─ 悲观锁 ────────────────────────────────────────────────┐
   │  SELECT ... FOR UPDATE      排他，扣库存/转账用这个       │
   │  SELECT ... FOR SHARE       共享，8.0 语法（旧：LOCK IN  │
   │                             SHARE MODE）                 │
   │  ... FOR UPDATE SKIP LOCKED 跳过被锁的，任务队列专用      │
   │  ... FOR UPDATE NOWAIT      锁不到立刻报错，不干等        │
   │                                                          │
   │  前提：① 必须在事务里  ② WHERE 必须走索引                 │
   │        ③ 加锁到解锁之间不许有 RPC                         │
   └──────────────────────────────────────────────────────────┘

   ┌─ 乐观锁 ────────────────────────────────────────────────┐
   │  UPDATE t SET v = ?, version = version + 1               │
   │   WHERE id = ? AND version = ?                           │
   │                                                          │
   │  影响 1 行 → 成功                                        │
   │  影响 0 行 → 冲突，【重新读】后重试（有上限 + 退避）        │
   │                                                          │
   │  前提：① 检查返回行数  ② 别漏 version + 1                │
   │        ③ 重试在事务【外面】                               │
   └──────────────────────────────────────────────────────────┘

   ┌─ 优先考虑：不用锁的两条路（往往这两个就够了）────────────┐
   │                                                          │
   │  管住【改】  条件更新                                     │
   │      UPDATE t SET stock = stock - 1                      │
   │       WHERE id = ? AND stock > 0                         │
   │      影响 0 行 = 库存真没了，不是冲突，【不用重试】         │
   │                                                          │
   │  管住【插】  唯一索引                                     │
   │      UNIQUE KEY uk (user_id, activity_id)                │
   │      直接 INSERT，catch DuplicateKeyException             │
   │      别先查后插；列必须 NOT NULL；软删除用 deleted_at      │
   │                                                          │
   │  共同点：不用锁、不用重试、不用 version 列                 │
   │          把校验下沉到数据库，消灭那段空隙                  │
   └──────────────────────────────────────────────────────────┘
```
